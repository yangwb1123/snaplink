# Design: Credential-Aware Recovery for `interfaces/snapshot`

Scope: the three improvements from `docs/auto/interfaces-snapshot-analysis.md`
方向 2 — (1) fresh-node client secret regeneration, (2) WebAuthn passkey
portability, (3) encrypted opt-in TOTP seed portability. All changes stay
inside `interfaces/snapshot` plus optional, type-asserted SPI seams on
existing stores. No credential material enters the default snapshot body.

Invariant that gates every decision below: **a snapshot artifact must never
carry a plaintext credential**. Client secrets stay `json:"-"` as today;
WebAuthn records travel because they are public-key material only; TOTP seeds
travel only inside a purpose-separated sealed envelope behind an explicit
operator flag. Every decision also carries a `Report`-level marker so recovery
outcomes are observable instead of discovered by lockout.

---

## Decision 1: Fresh-node client secret regeneration

After a restore onto a node with no live record to backfill from
(`preserveClientSecrets` hits `ErrNoSuchClient` and returns `cl` untouched),
every confidential client is left with an empty secret and the
`client_secret` grant silently breaks. The restorer regenerates secrets for
these clients via the already-existing `ClientStore.RotateSecret` SPI and
surfaces the new credentials through the restore RPC response only.

### API surface

- New capability interface in `interfaces/snapshot` (restorer.go), asserted
  from `r.Clients` — mirrors the `TenantScopedClientStore` pattern in
  `shared/core/spi.go`:

  ```go
  // SecretRotator is the optional capability the Restorer uses to
  // regenerate secrets for clients that a fresh-node restore left
  // secret-less. Structurally satisfied by every sso.ClientStore (the base
  // interface already carries RotateSecret); declared separately so the
  // restorer's dependency is explicit and a future base-interface shrink
  // cannot silently break the recovery path.
  type SecretRotator interface {
      RotateSecret(ctx context.Context, clientID string) (string, error)
  }
  ```

- `Report` gains:

  ```go
  // CredentialRecovery names one client whose secret was regenerated by
  // this restore, plus the new plaintext. The secret is an RPC-response-only
  // value: audit and operations records must carry client IDs, never the
  // secret (admin_clients.go:37 "secrets are never echoed").
  CredentialRecovery []CredentialRecovery   // new Report field

  type CredentialRecovery struct {
      ClientID string
      Secret   string
  }
  ```

- `CategoryCounts` gains `RequiresRotation int` — the count of clients left
  in "needs rotation" state (dry-run: predicted; non-dry-run: actually still
  broken because the capability is missing or rotation failed).

- `proto/admin/v1/snapshots.proto`: `RestoreReport` gains
  `repeated CredentialRecovery credential_recovery = 9;` (new message
  `CredentialRecovery { string client_id = 1; string secret = 2; }`) and
  `CategoryCounts` gains `int32 requires_rotation = 5;`.

### Storage model / mutation semantics

- No snapshot schema change: `Client.Secret` remains `json:"-"`; the
  artifact is byte-identical in scope to today.
- Rotation runs **inside the clients stage**, per client, immediately after
  that client's insert/upsert, in both non-dry-run modes (Merge inserts and
  Overwrite/Replace upserts) — a fresh-node Merge restore has the same
  breakage as Replace and must be remediated the same way.
- Eligibility rule (the resulting live record decides, not the snapshot):
  the client was **written by this restore** (inserted, or upserted) and its
  post-write live record is `Active && Secret == ""`. Merge never rotates a
  pre-existing client ("leave existing untouched" stays intact); Overwrite/
  Replace touches every snapshot client, so all of them are eligible.
- Mechanics: type-assert `SecretRotator`; call `RotateSecret`; record
  `{ClientID, Secret}` into `CredentialRecovery`. Dry-run never mutates: it
  probes `Get` exactly as the write path would and predicts
  `RequiresRotation` (absent client that would insert with an empty secret,
  or present client whose live secret is empty under Overwrite/Replace).
- Ordering inside `Restore()`: rotation happens in Phase A (clients stage),
  which is **before** `InvalidateRestoredControlPlane()` — the restore's
  existing full control-plane invalidation covers the rotated secrets, so no
  new invalidation mechanism is needed.
- Errors never abort the plan: a per-call `restoreSession` (allocated by
  `Restore()`, passed by parameter down the stage call chain — no mutable
  fields on the shared `Restorer`) collects per-client rotation errors into
  `Report.Errors` while the stage loop continues with the next client. The
  category runner returns `(counts, nil)` for rotation failures, so
  `runPlan`'s abort-on-error contract is untouched.

### Failure modes

| Mode | Behavior |
|---|---|
| `RotateSecret` fails for one client | Recorded in `Report.Errors`; that client stays in `RequiresRotation`; remaining clients still rotate; restore completes. |
| Store lacks `SecretRotator` | No rotation, no panic; clients restored with empty secrets exactly as today; `RequiresRotation` counts them so the backlog is visible. |
| Dry-run | Zero store mutations; `RequiresRotation` predicts the exact set the real run would rotate. |
| Rollback (orchestrator re-applies safety snapshot) | The safety artifact also carries no secrets, so rollback backfills the *rotated* secret via `preserveClientSecrets` — the rotation survives rollback, which is correct (the secret is already live; never revert to a broken state). Documented, not a bug. |

### What could break this design

- **Merge contract drift**: if eligibility were computed on live state alone
  (instead of "written by this restore"), a pre-existing broken client on a
  Merge destination would be silently mutated. The write-set bookkeeping in
  `restoreSession` is the guard; the dry-run must mirror it exactly or the
  preview lies.
- **Disabled clients**: the `Active` gate (per the requirement) excludes
  `Active=false` clients, which are restored secret-less and *stay* secret-less
  when later enabled — a latent trap. Accepted for now; the report does not
  flag them, so operators re-enabling a client should rotate it (documented in
  the §6 runbook addition).
- **Secret leakage into audit**: the RPC response carries plaintext secrets,
  so `reportToProto`-adjacent code that persists `result_json` or audit events
  must strip `CredentialRecovery[].Secret` (client IDs only). Needs a test
  asserting the ledger row contains no rotated secret.
- **Rotation vs. client lifecycle stores**: the gRPC admin path honors
  `RotateSecretWithLifecycle`/`WithOverlap` wrappers; the restorer calls the
  plain SPI, so `client_secret_expires_at` policy is store-internal. Restored
  secrets get whatever the destination store's default is. Fine for DR, but
  must be documented.

## Decision 2: WebAuthn credential portability (`webauthn_credentials`)

Passkey records (credential ID, COSE public key, sign counter, AAGUID,
flags) contain no secret material; they currently die with the node. A new
category exports and replays them per user. `VerifyLogin` needs only
`credential.PublicKey`, `AttestationFormat` (string), `Flags`, and the
counter (verified against go-webauthn v0.17.4 `login.go`), so the exported
record is a small verification-relevant projection.

### API surface

- Domain side (`domains/authenticators/webauthn` — capability guards live
  with implementations, per AGENTS.md):

  ```go
  // UserCredentialRecord is one user's exported passkey state: identity
  // (username + handle + display name) plus the verification-relevant
  // credential projection and SDK-captured extension metadata.
  type UserCredentialRecord struct {
      UserName    string
      Handle      []byte
      DisplayName string
      Credential  gw.Credential   // Attestation blob zeroed on export
      Extensions  CredentialExtensions
  }

  // CredentialLister is the OPTIONAL capability a webauthn.UserStore may
  // implement to enumerate every user's credentials for snapshot export.
  type CredentialLister interface {
      ListCredentials(ctx context.Context) ([]UserCredentialRecord, error)
  }

  // HandlePreservingUserCreator is OPTIONAL: preserves the exported handle
  // on restore. Absent → restorer falls back to CreateUser (handle
  // re-minted; assertions still verify — the handle is not in the
  // assertion signature, the session is).
  type HandlePreservingUserCreator interface {
      CreateUserWithHandle(ctx context.Context, name, displayName string, handle []byte) (*User, error)
  }
  ```

  Implemented by `MemoryUserStore`, `webauthnpostgres`, `webauthnsqlite`
  (deep-copying credentials out of live records — never hand out live
  pointers). The exporter returns a copy of the credential with the bulky
  `Attestation` blob (ClientDataJSON / AttestationObject / attestation
  certificate) zeroed; `AttestationFormat` is preserved (needed by
  `GetAppID`).

- Snapshot side:

  - `ResourceCategory` gains `CategoryWebAuthn = "webauthn_credentials"`;
    appended to `AllCategories()` and to the `stagePlan` runner list right
    after `CategoryUsers` (credentials depend on restored users).
  - `Resources` gains `WebAuthnCredentials []webauthn.UserCredentialRecord`
    `json:"webauthn_credentials,omitempty"`.
  - `Snapshotter` gains optional field `WebAuthn webauthn.UserStore`; export
    type-asserts `webauthn.CredentialLister`; absent exporter ⇒ category
    silently omitted (the existing "optional store ⇒ category omitted"
    pattern).
  - `Restorer` gains optional field `WebAuthn webauthn.UserStore`; nil ⇒
    category silently skipped on restore.
  - Redactor: no redaction rules needed — records are public-key material;
    `SnapshotRedactSecrets` deliberately leaves them intact.

### Storage model / mutation semantics

- No new tables anywhere: the durable stores already persist this state; the
  exporter is a read-only projection query, the restorer replays through the
  existing `GetByName` / `CreateUser` / `AddCredential` / `UpdateCredential`
  / `SetCredentialExtensions` SPI. No schema migration.
- Restore replay, per record:
  1. `GetByName(user)` → `ErrUserUnknown` ⇒ create the webauthn user
     (`CreateUserWithHandle` when available, else `CreateUser`), then insert
     the credential.
  2. Credential ID unknown for an existing user ⇒ `AddCredential` (insert).
  3. Credential ID present: compare counters. `live.SignCount >
     snapshot.SignCount` ⇒ **skip + count** (fail-closed: never write the
     counter backwards — the "production clocks slew" discipline). Otherwise
     `UpdateCredential` (converge; equal counter counts as updated, matching
     the upsert-counting convention elsewhere).
  4. Extension metadata replayed through the optional
     `credentialExtensionSetter` capability; absent ⇒ silently nil
     ("unknown"), the documented safe default.
- Dry-run: identical probes, zero writes.
- **No Phase B prune** for this category, by decision: credential deletion is
  destructive (a replace-restore would delete passkeys enrolled *after* the
  snapshot was taken — the destination is the authority on newer
  credentials), and the counter-regression guard already prevents backwards
  overwrites. Replace mode therefore converges but never wipes credentials.
  Counts make the additive behavior observable.

### Failure modes

| Mode | Behavior |
|---|---|
| `ListCredentials` fails | Export aborts — all-or-nothing, consistent with every other category. |
| User-create / AddCredential / UpdateCredential fails | Category aborts via `runPlan`; replay-safe (re-running converges). |
| Counter regression (live newer) | Credential skipped, `Skipped +1`; live counter intact. |
| Record's user absent from restored users | Skipped + counted (orphan record; the users category owns identity). |
| Store lacks exporter | Category absent from the artifact; restore of a v3 artifact without a wired `WebAuthn` store silently skips the category (optional-backend semantics). |
| Rollback | Replays the safety artifact; additive inserts are reverted by the safety snapshot's own users/prune semantics — no credential-specific hazard. |

### What could break this design

- **go-webauthn JSON coupling**: the record embeds `gw.Credential`, whose
  JSON tags are library-owned. A future library bump changing tags would
  skew v3 artifacts across binaries. Mitigation: verification touches only
  `PublicKey`/`AttestationFormat`/`Flags`/`SignCount`, which have been stable
  since v0.17.x; the v3 version gate protects old binaries from decoding
  unknowns (see Decision 4).
- **Handle regeneration fallback**: stores without
  `HandlePreservingUserCreator` re-mint handles. Assertions still verify
  (server looks up by session handle, not response), but a platform
  authenticator that pins the old handle sees divergence. Cosmetic, flagged
  in the runbook.
- **User-recreate orphan credentials**: replace-mode user pruning deletes
  the `sso.User` but not the webauthn store's records (separate stores). A
  later re-created username inherits the orphaned passkeys. Real but minor;
  documented as a known interaction and a candidate future optional prune.
- **Live-store aliasing**: an exporter that returns live pointers lets a
  restore-time mutation or redaction corrupt the running server's in-memory
  credentials. The exporter contract must deep-copy; test asserts
  export-then-mutate leaves the store intact.

## Decision 3: Encrypted, opt-in TOTP seed portability (`totp_seeds`)

TOTP seeds are MUST-encrypt material. They are exported only when the
operator explicitly asks, a sealer is configured, and the store can enumerate
seeds — and they ride inside a **purpose-separated nested envelope** that the
snapshot body key cannot open. Restore is opt-in; without it the report flags
every affected user as needing re-enrollment instead of leaving the operator
to discover lockouts.

### API surface

- Domain side (`domains/authenticators`):

  ```go
  type SeedRecord struct {
      UserID string
      Secret []byte
  }

  // SeedExporter / SeedImporter are OPTIONAL TOTPStore capabilities.
  type SeedExporter interface {
      ExportSeeds(ctx context.Context) ([]SeedRecord, error)
  }
  type SeedImporter interface {
      ImportSeed(ctx context.Context, userID string, secret []byte) error
  }
  ```

  Implemented by `MemoryTOTPStore` and the durable `TOTPEnrollmentStore`
  backends (which already satisfy `TOTPStore.GetSecret`).

- Sealer side — new **optional** capability on `snapshot.Sealer`, keeping
  the base interface untouched:

  ```go
  // PurposeSealer derives a purpose-separated Sealer from this one.
  // encryptionaesgcm / encryptionpassphrase implement it (HKDF-SHA256 over
  // the master key with info=purpose); encryptionnone does not, which is
  // exactly the fail-closed gate: no real encryption, no seeds.
  type PurposeSealer interface {
      DeriveSealer(purpose string) (Sealer, error)
  }
  ```

  Purpose constant: `"snapshot:totp_seeds:v1"`. Deriving a *key* per purpose
  (rather than an AD tag) means cross-purpose ciphertexts cannot be swapped
  or opened; each derived sealer mints its own random nonces, so the AES-GCM
  nonce domain stays per-purpose.

- Snapshot side:

  - `ResourceCategory` gains `CategoryTotpSeeds = "totp_seeds"`; appended to
    `AllCategories()` and `stagePlan` after users/webauthn.
  - `Resources` gains the opaque nested envelope:

    ```go
    // SeedEnvelope is the purpose-separated ciphertext carrying TOTP seeds
    // inside an otherwise-plaintext body. Decrypting the body does NOT
    // decrypt seeds.
    type SeedEnvelope struct {
        Algorithm string `json:"algorithm"`
        Params    []byte `json:"params"`
        Cipher    []byte `json:"cipher"`
    }
    ```

  - `Snapshotter` gains optional fields `TOTP authenticators.TOTPStore` and
    `Sealer Sealer` (cmd wires the same sealer instance the pipeline uses;
    nil = no encryption configured).
  - `ExportOptions` gains `IncludeCredentialSeeds bool`.
  - `Restorer` gains optional `TOTP authenticators.TOTPStore` and
    `Sealer Sealer`; `RestoreOptions` gains `RestoreCredentialSeeds bool`.
  - `Report` gains `MFAReenrollmentRequired []string` (user IDs).

- Export gating (all three gates required; the explicit-flag cases fail
  closed rather than silently):

  | Condition | Outcome |
  |---|---|
  | `IncludeCredentialSeeds` unset | Category silently absent — default export is byte-identical in scope to today. |
  | Flag set, sealer nil | **Error** `ErrSnapshotSeedsRequireEncryption` (explicit ask cannot be honored safely). |
  | Flag set, sealer present, store lacks `SeedExporter` | **Error** (same sentinel family): an operator who explicitly asked must not get silent absence — that is how DR incidents happen. |
  | Flag set, sealer present, store lacks `PurposeSealer` | **Error** (fail-closed): no key separation, no seeds. |
  | Redaction effective (per-call or `DefaultExportRedactor`) **and** seeds present | **Error** `ErrSnapshotSeedsWithRedaction`, raised in `Export` between `exportResources` and `applyRedaction` — the `Redactor` interface cannot return errors and cannot scrub opaque ciphertext, so the pipeline refuses rather than silently dropping the category or shipping seeds in a redacted artifact. |

  Note the interpretation choice: the requirement's "silently absent without
  all three" is read as the *flag-unset default*; once the operator sets the
  flag, every missing gate is a hard error (the stricter contract, and the
  only reading consistent with the acceptance check's "fails closed with an
  explicit error").

- Export mechanics: `ExportSeeds` → JSON-marshal records → seal with
  `DeriveSealer(purpose)` → `SeedEnvelope{Algorithm, Params, Cipher}`. The
  plaintext bytes exist only transiently in the exporter's memory; they never
  touch the artifact.

- Restore mechanics:

  - Open the envelope with `DeriveSealer(purpose)` and decode records. The
    envelope is a per-category dependency: the totp_seeds stage runs after
    users (import targets must exist as restored identities; seeds for
    unknown users are inert, so membership is not a hard gate).
  - `RestoreCredentialSeeds` **unset**: restore succeeds for every other
    category; `Report.MFAReenrollmentRequired` lists every user found in the
    envelope; category counts them as `Skipped`. If the envelope cannot be
    opened (no sealer / wrong key / tamper), the report records a category
    error **and** conservatively flags *all* users from the snapshot's users
    category (over-flagging beats silent lockout).
  - `RestoreCredentialSeeds` **set**: per record, `ImportSeed` (byte-copy in,
    byte-identical out — existing TOTP verification passes). First import
    error aborts the category via `runPlan` and is reported — fail-closed,
    never silently half-applied (records already imported stay, matching the
    documented partial-apply semantics of every other category).
  - Missing `SeedImporter` with opt-in ⇒ category error (cannot honor the
    request).

### Storage model / mutation semantics

- Seeds persist in the destination store exactly as the source had them —
  raw bytes, store's own at-rest protection. No snapshot-side schema change
  beyond the additive `SeedEnvelope`.
- The artifact contains seed plaintext **nowhere**: not in `Resources` (only
  ciphertext), not in the codec bytes (nested seal), not in redacted exports
  (refused). An acceptance test scans the sealed payload for a known seed
  substring.

### Failure modes

| Mode | Behavior |
|---|---|
| Export: flag + missing sealer / exporter / PurposeSealer | Hard error before any artifact is produced. |
| Export: redaction + seeds | Hard error; operator chooses redaction XOR seeds (cmd's `snapshot.redact_secrets` default makes seed exports fail loudly unless disabled per call — documented). |
| Restore opted-in: open fails (wrong key, tamper, sealer nil) | Category aborts, error reported. |
| Restore opted-in: import fails | Category aborts, error reported, prior imports visible in counts. |
| Restore not opted-in | Success + `MFAReenrollmentRequired` backlog (or conservative all-users flag when undecryptable). |
| Snapshot key rotated between export and restore | Seed envelope undecryptable (derived key changed) — same property as the body key; operators must retain the sealing key until the artifact is restored or re-export. Parity with existing behavior, documented. |

### What could break this design

- **Wiring drift in cmd**: if `Snapshotter.Sealer` is left nil while the
  pipeline has a sealer, seed exports hard-fail — safe direction, but the
  wiring must be added in the same change or the feature is invisible.
- **`Redact` can't error**: the refusal lives in `Export`, not in the
  `Redactor` — any future export path that calls `Redact` directly (outside
  `Snapshotter.Export`) could bypass it. All in-repo paths go through
  `Export`; the doc must say the check lives there.
- **Over-flagging on undecryptable envelopes**: flagging every user is
  deliberately conservative; an operator could over-re-enroll. Mitigation:
  the category error entry explains the cause (key mismatch vs. tamper).
- **HKDF dependency**: `DeriveSealer` needs `crypto/hkdf` (stdlib, FIPS-safe
  SHA-256); the passphrase sealer must derive from its KDF output, not the
  raw passphrase, or purpose separation is illusory (two nodes with
  different passphrases must not open each other's envelopes — KDF output
  derivation keeps that true).
- **Audit cardinality**: `MFAReenrollmentRequired` is user IDs — bounded by
  enrollment count, fine for audit; `CredentialRecovery` secrets must be
  stripped before any persisted record (shared guard with Decision 1).

## Decision 4: Schema version and wire compatibility

- `SchemaVersion` bumps `"2" → "3"` once, covering both new categories
  (webauthn_credentials, totp_seeds). `IsValidSchemaVersion` accepts
  `"1" | "2" | "3"`.
- v1/v2 artifacts remain fully readable by v3 builds (`legacyCategories`
  unchanged — v1 manifests cannot claim the new categories; a nil v2
  manifest keeps its in-process compatibility semantics, and the new
  categories join the default include set for v3 in-process callers).
- v3 artifacts are refused by ≤v2 binaries at the version check — the
  documented rule, and what protects the `DisallowUnknownFields` codec from
  choking on the two new `Resources` fields.
- No `SealedEnvelope` header change; `Kind` travel is untouched.

## Decision 5: Contract updates in the same change (AGENTS.md §5)

- `proto/admin/v1/snapshots.proto`: `ExportSnapshotRequest.
  include_credential_seeds`; `RestoreSnapshotRequest.restore_credential_seeds`;
  `RestoreReport.credential_recovery` + `mfa_reenrollment_required`;
  `CategoryCounts.requires_rotation`; new `CredentialRecovery` message.
  Regenerate protos; extend `reportToProto` and the REST mapping.
- `docs/error-codes.md`: `ErrSnapshotSeedsRequireEncryption`,
  `ErrSnapshotSeedsWithRedaction` (both map to `failed_precondition` on the
  RPC surface).
- `docs/dr-framework.md`: §1 (MFA enrollments are now partially covered —
  webauthn unconditionally, TOTP opt-in behind encryption); §6 runbook gains
  the remediation steps (rotate flagged clients, re-enroll or re-issue seeds
  for `MFAReenrollmentRequired` users).
- `docs/openapi.yaml`: the two new request fields; `docs/feature-matrix.md`
  row for the new categories.
- Audit guard: restore operation records/audit events carry client IDs and
  user IDs, never rotated secrets (test-enforced).

## What could break the overall design (cross-cutting)

1. **Dry-run honesty**: three separate predictions (rotation set,
   webauthn counts, re-enrollment list) must each mirror the non-dry-run
   decision exactly, or operators approve based on a preview that lies. Each
   acceptance test asserts zero store mutations on dry-run *and* equal counts.
2. **Category-order coupling**: webauthn/totp stages depend on users being
   staged first; the replace-mode dependency ordering is load-bearing
   (documented in `restorer_stage.go`). Adding the two runners in the middle
   of `stagePlan` must not disturb the tenant→clients→users order.
3. **Optional-backend drift**: three capabilities (SecretRotator,
   CredentialLister, SeedExporter/Importer) mean a store can silently lack a
   feature. The report markers (`RequiresRotation`, absent category,
   `MFAReenrollmentRequired`) are the observability net — the design treats
   "category absent" and "user flagged" as first-class outcomes, not
   accidents.
4. **Scope creep**: no prune for webauthn/totp, no interface churn on
   `Sealer`/`Redactor`/`TOTPStore`/`webauthn.UserStore` base interfaces, no
   new config knobs — every seam is a type assertion, so existing stores and
   callers are untouched. The no-prune decision is the one deliberate
   semantic deviation from "replace wipes the category" and is documented in
   Decision 2.
5. **Test surface**: acceptance tests live in
   `interfaces/snapshot/restore_preserve_secret_test.go` (rotation),
   `snapshot_v3_test.go` (webauthn round-trip with the
   `softwareAuthenticator` from `assertion_regression_test.go`, counter
   regression, exporter-less store), and a TOTP round-trip test with a
   payload substring scan of the sealed envelope. Cross-server integration
   stays in `test/` where a full restore RPC matters.
