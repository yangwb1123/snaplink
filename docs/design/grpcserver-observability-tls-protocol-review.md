# Identity-Protocol Review: gRPC Observability + TLS Design

**Review target:** `docs/design/grpcserver-observability-tls.md` (design only — no code modified; the reviewed revision is the current working tree, commit fbf91c52). **Role:** advisory identity-protocol reviewer per `ai-dev/prompts/README.md`. **Checks actually run for this revision:** static verification only — `read`/`grep`/`sed` over the cited files, `test/` harnesses, `Makefile`, docs, and the grpc v1.80.0 module cache (`go env GOMODCACHE`). No `go test` was executed (design stage; no `.go` changed). All design line citations were re-verified and are accurate; the load-bearing ones are listed under the matrix. Statuses below: **Verified** (code read this revision), **Proposed** (design), **Gap** (design misses or is wrong).

The design is Direction 3 of `docs/auto/interfaces-grpcserver-analysis.md`: health + reflection registration, per-RPC metrics/tracing interceptors, and fail-closed TLS on the gRPC listener. It does **not** touch the OAuth/OIDC/CAEP/WebAuthn endpoint surface — no new `Err*`, no `docs/openapi.yaml` change, `interfaces/sso` untouched. The identity protocols actually in scope are the gRPC health-checking protocol, gRPC server reflection, the existing bearer-authenticated gRPC data/admin plane (`AuthzService.Check`, discovery, admin services), and TLS transport posture.

## 3. Findings (severity-sorted)

**F1 — Medium, MUST-resolve (readiness-signal parity; availability).**
`docs/design/grpcserver-observability-tls.md` Decision 2 covers `checks == nil`, nil map, and empty map, but not **nil functions inside a non-empty map**. `WithReadyCheckTimeout` pre-registers `namedReadyCheck{Name, Timeout, Check: nil}` (`interfaces/sso/options_misc.go:407-425`), and the orphan survives until a same-named `WithReadyCheck`/`AddReadyCheck` arrives; a typo'd or retired check name leaves it nil for the process lifetime. `handleReadyz` explicitly skips nil-Check entries (`interfaces/sso/server_health.go:104-107`), but the `BuildHandlerDeps` accessor copies `rc.Check` unconditionally (`interfaces/sso/accessors_handlers.go:343-348`) — the map the poller receives can contain nil funcs. Calling one panics; the design's per-evaluation `recover` converts that into NOT_SERVING **permanently**, while `/readyz` returns 200 and load balancers drain a healthy node. The two readiness signals disagree in the failure direction on a supported option path. **Impact:** availability (LB mis-drain) and an unexplained `/readyz` vs gRPC-health divergence; the design's own parity claim ("same check closures") does not hold for this state. **Corrective:** the poller must skip nil check funcs exactly like `handleReadyz` (they are "metadata, not checks"), and the acceptance test must include the orphan-timeout state asserting SERVING == `/readyz` 200. **Validation:** `obs_test.go` — register `WithReadyCheckTimeout("never-added")` via the real option chain, poll, assert `Check` = SERVING and `/readyz`-equivalent evaluation = ok.

**F2 — Medium, SHOULD (RFC 6819 §4.4.1 posture; carryover from requirements-stage F4(a)).**
Decision 5's decision function is invoked only from `grpcServerOptions` ← `newGRPCServer` ← `startGRPCServer`, i.e. the real boot path. `-validate-only` (`cmd/sso-server/main_wiring.go:62`, `main.go:96-98`) loads and validates config and exits **before** `run()` reaches the gRPC server construction. A stock deployment preflighted with `sso-server -validate-only` gets a green result, then the real boot fails with the new fail-closed TLS error. The prior stage review (`docs/proposals/protocol_expert.md`, F4) raised exactly this gap; the design does not address it. **Impact:** operational — the documented preflight path stops predicting boot success; the breaking default-change lands without a preflight warning. **Corrective:** run the pure decision function (listen addr + resolved cert flags) in the validate-only path and report the posture result, or explicitly document that `-validate-only` cannot catch gRPC TLS posture failures. **Validation:** CLI-level test asserting `-validate-only` with `-grpc-listen :8081` and no material reports the failure.

**F3 — Low (reflection surface; metric-bucket hygiene).**
Stock `reflection.Register` registers **both** `grpc.reflection.v1.ServerReflection` and `grpc.reflection.v1alpha.ServerReflection` (module cache `reflection/serverreflection.go:62-65`, "Many clients may only support v1alpha"). The design's banner claims parity with `grpcurl list` but lists only the v1 name, and the metrics denylist names only the v1 service — legacy grpcurl/grpcreflect clients speaking v1alpha would be counted under `"other"`, polluting the unknown-service bucket with probe noise (the exact class of traffic Decision 3 says it excludes). **Impact:** low — banner mismatch and label-bucket pollution; no security effect. **Corrective:** denylist by service prefix (`grpc.reflection.v1`) or enumerate both names in the const table, and list both in the startup banner. **Validation:** `metrics_test.go` — send reflection requests via the v1alpha descriptor set, assert zero increments.

**F4 — Low (deviation from requirements acceptance).**
`docs/proposals/requirements.md` §3 acceptance asked for `docs/config-reference.md` to gain **gRPC TLS config keys** plus the insecure opt-out. The design deliberately keeps the knobs runtime-only flags (Decision 5, 8.8) to keep the docscheck config-keys gate green by construction. The reasoning is sound (HTTP TLS flag precedent, per-node material paths, `-grpc-listen` is already a flag), and the deviation is disclosed in Decision 8.8 — but the consequence is that the centralized etcd config path (`--etcd-endpoints`, `cmd/sso-server/main_wiring.go:64-67`) cannot manage gRPC transport posture, and `docs/config-reference.md` today documents no gRPC transport flags at all (the design's new subsection will be the first). **Impact:** low — operator discoverability and central-config coverage for the fail-closed default. **Corrective:** keep flags; ensure the config-reference subsection documents all four flags (`-grpc-tls-cert/-key/-insecure` and the pre-existing `-grpc-listen ''` escape hatch) and records the "flags not Config keys" decision so it survives review. **Validation:** docscheck gate + a config-reference grep for the four flags.

**F5 — Info (two design-statement accuracy issues).**
(a) Decision 2.6/7: `health.Server.Shutdown()` "ends all Watch streams" overstates grpc v1.80.0 behavior — it sets every status to NOT_SERVING and ignores subsequent `SetServingStatus` (module cache `health/server.go:161-172`), but open `Watch` streams are not closed by it; they end when the server's `GracefulStop`/`Stop` completes. The draining signal (NOT_SERVING delivered to Watch clients) is exactly what the design needs, so the fix is wording, not design. (b) The gate paragraph lists `grpcurl -plaintext localhost:8081 list` under `make ci`; `make ci` (`Makefile:244`) has no grpcurl step, and after this change a stock run with default flags **fails to boot** — the enumeration is a manual step against a TLS-enabled or loopback run and should be worded as such. **Impact:** none functional. **Corrective:** reword both statements.

**F6 — Info (code_class mapping verified complete).**
All 17 gRPC codes are covered: `ok` for nil error; 11 client-class; 5 server-class. `Canceled → client`, `DeadlineExceeded → server`, `Unimplemented → client` are judgment calls (a server-returned `Unimplemented` often means server misconfiguration; `DeadlineExceeded` is frequently client-side deadline pressure). Either classification is defensible provided the table is fixed, documented (the design reproduces it in `docs/observability.md`), and never per-code — which the design does. No change required.

**Info (pre-existing, out of scope):** `AuthzService.Check` returns `status.Errorf(codes.Internal, "permissions lookup: %v", err)` (`interfaces/grpcserver/authz.go:31`) and `DiscoveryService` `"register: %v"` (`discovery.go:33`) — error text that can distinguish backend causes on the data plane. This matches the requirements-stage F1 finding on the admin middleware. Not touched by this design (no handler changes, no new `Err*`), but with per-RPC metrics now exposing these surfaces' error rates, a follow-up to constant error text (Recovery's `"internal error"` wording is the house pattern) is recommended.

## 4. Priority conformance tests, declared unsupported, certification evidence

**Priority tests (design's list, plus F1–F3 additions, in design order):**
1. `obs_test.go`: bufconn `Check`/`Watch` — SERVING all-pass; NOT_SERVING on failure; recovery flips back; `Watch` streams the transition; `Check("")` overall status.
2. **F1 parity test**: orphan `WithReadyCheckTimeout` entry (nil check func) → gRPC SERVING must equal `/readyz` 200; nil map / empty map → SERVING.
3. **F2 preflight test**: `-validate-only` with `-grpc-listen :8081`, no material → posture failure surfaced.
4. `metrics_test.go`: ok and `PermissionDenied` RPCs increment with correct `code_class`; duration histogram populated; synthetic panic → `code_class=server` (chain-order regression lock); unknown methods collapse to `"other"`; health/reflection (v1 **and** v1alpha, F3) excluded.
5. Decision-5 matrix table test (6 rows + `-grpc-listen ''` disabled case) and one bufconn TLS handshake test exercising the TLS1.2 floor.
6. `stop()` test: Watch client receives NOT_SERVING; assert the transition, not stream termination (F5a).

**Declared unsupported / out of scope (should be explicit in the final docs):** per-check `WithReadyCheckTimeout` semantics on the gRPC signal (documented divergence — aggregate 3 s bound only); cert rotation without restart (pre-existing); reflection on plaintext (mitigated by TLS-by-default; unauthenticated health/reflection is the standard gRPC convention, correctly documented in Decision 8.5); v1alpha reflection clients (F3); gRPC DPoP/mTLS client auth (no coverage — future direction, consistent with the requirements-stage declaration); HTTP-side asymmetric-cert silent plaintext fallback (pre-existing, out of scope).

**Certification:** No OIDF or other certification result for this surface exists in-tree; nothing in this review changes that, and no certification claim should be made. All conformance statements above are against the gRPC protocol docs, RFC text, and repo-internal contracts — not certification programs. The gRPC plane here is an internal machine-to-machine surface, not an OIDF-certifiable endpoint profile.

**Bottom line:** The design is sound on protocol choice (stock `health.Server` and `reflection.Register` — protocol-conformant, no hand-rolled health), on TLS fail-closed posture, on bounded-cardinality metrics, and on the chain-order amendment being test-locked. F1 (nil-check parity) and F2 (`-validate-only` preflight) should be resolved before implementation; F3–F4 are small, bounded corrections; F5 is wording. The design should not proceed to implementation with F1 open — it silently breaks the design's own `/readyz`-parity claim on a supported option path.
