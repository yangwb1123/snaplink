## 2. 用户故事

### 2.1 自适应动态认证（F01）

**作为** 企业安全官，  
**我希望** 系统能根据登录请求的风险等级自动决定是否需要多因素认证，  
**以便** 低风险用户（来自受信网络/已知设备）能快速登录，而高风险访问（新设备/异地登录）必须经过 MFA 验证，而不是对所有人使用一刀切的策略。

**验收标准 1：低风险场景免 MFA**

- **Given** 用户 Alice 从受信 IP（公司办公网络）使用已知设备登录
- **When** Alice 提交正确的用户名和密码
- **Then** 系统直接签发令牌，无需 MFA 挑战

**验收标准 2：中风险场景提升认证等级**

- **Given** 用户 Alice 从新的地理区域（如出差国家）使用新设备登录
- **When** 风险引擎评估为"中等风险"
- **Then** 系统要求 Alice 完成 MFA（TOTP/SMS 验证码）
- **And** 仅在 MFA 通过后才签发令牌

**验收标准 3：高风险场景直接阻断**

- **Given** 用户 Alice 的账户在过去 5 分钟内已有 10 次失败登录尝试，且当前请求来自 Tor 出口节点
- **When** 风险引擎评估为"高风险"
- **Then** 系统返回 `access_denied` 错误
- **And** 记录详细的审计事件（风险等级、触发因子）

**验收标准 4：评估超时容错**

- **Given** 风险引擎因后端故障超出 50ms 同步评估窗口
- **When** 超时发生
- **Then** 系统 Fail-Open：允许登录但记录降级审计事件（`risk_engine_timeout`）
- **And** 安全操作面板标记该登录为"未评估"

### 2.2 令牌交换 Scope 默认收窄（F02）

**作为** 微服务安全架构师，  
**我希望** 令牌交换时默认仅授予"客户端被授权 scope 与被交换令牌 scope 的交集"，  
**以便** 防止权限在服务链中逐跳膨胀——一个仅有 `email` scope 的微服务不应该通过令牌交换获得 `admin` 权限。

**验收标准 1：默认收窄**

- **Given** 被交换令牌 scope = `["openid", "email", "admin"]`，交换客户端 A 的授权 scope = `["openid", "email"]`
- **When** 客户端 A 发起令牌交换请求且未指定 `scope` 参数
- **Then** 新令牌 scope = `["openid", "email"]`（交集），不含 `admin`

**验收标准 2：显式 scope 缩减**

- **Given** 被交换令牌 scope = `["openid", "email", "profile"]`，客户端 A 授权 scope = `["openid", "email", "profile"]`
- **When** 客户端 A 在交换请求中指定 `scope=openid email`
- **Then** 新令牌 scope = `["openid", "email"]`（请求参数进一步收窄）

**验收标准 3：scope 扩展需显式 Opt-in**

- **Given** 客户端 A 的配置中 `actor.allow_scope_expansion = false`（默认）
- **When** 客户端 A 试图将 scope 扩展到超过被交换令牌的 scope
- **Then** 交换请求被拒绝，返回 `invalid_scope`

- **Given** 客户端 B 的配置中 `actor.allow_scope_expansion = true`
- **When** 客户端 B 请求的 scope 包含超过被交换令牌的新 scope
- **Then** 交换成功，但审计事件标记 `scope_expanded: true`，并记录扩展内容

### 2.3 Act 链循环检测（F03）

**作为** 安全运维工程师，  
**我希望** 令牌交换系统能自动检测并阻断 act 链中的循环引用（A→B→C→A），  
**以便** 防止配置错误或恶意攻击导致的无限令牌交换循环，避免 JWT 超出 HTTP 头大小限制或造成 DoS。

**验收标准 1：直接自引用**

- **Given** 客户端 A 持有令牌 T1
- **When** 客户端 A 使用自身签发的令牌作为 subject_token，请求交换新令牌
- **Then** 请求被拒绝，返回 `invalid_grant`，原因标记为 `circulation_detected`

**验收标准 2：多跳回环**

- **Given** 已存在 act 链 [A → B → C]
- **When** 当前访问令牌的 actor 是 C，客户端 A 请求交换
- **Then** 检测到 A 已在链中出现，拒绝请求

**验收标准 3：不同 sub 但同 client_id 的回环**

- **Given** act 链中已有 `{client_id: "srv-A", sub: "alice"}`
- **When** `srv-A` 以 `sub: "bob"` 出现在交换请求的 actor 位置
- **Then** 仍然检测到回环（client_id 匹配已足够触发），拒绝请求

### 2.4 通用事件订阅与 Webhook 推送（F06）

**作为** 安全运营中心（SOC）工程师，  
**我希望** 能够订阅关键身份事件（登录失败、令牌撤销、凭据到期）并通过 Webhook 实时推送到 SIEM 系统，  
**以便** 在安全事件发生的第一时间做出响应，而不是等到下次审计查询才发觉。

**验收标准 1：事件订阅配置**

- **Given** SOC 工程师有 `admin:write` 权限
- **When** 通过管理 API 创建事件订阅：`{url: "https://siem.example.com/webhook", events: ["login.failed", "token.revoked", "credential.expiring"], secret: "whsec_..."}`
- **Then** 订阅被创建并返回订阅 ID
- **And** 推送测试事件到端点验证可达性

**验收标准 2：事件推送与签名验证**

- **Given** 用户登录失败事件发生
- **When** 订阅系统检测到匹配的事件类型
- **Then** 推送包含完整事件负载的 HTTP POST 请求到订阅 URL
- **And** 请求头包含 `X-Signature: sha256=<HMAC>` 和 `X-Event-ID: <uuid>`
- **And** 目标端点返回 200 确认接收

**验收标准 3：失败重试与死信**

- **Given** 订阅端点在 10 秒内返回非 2xx 状态码
- **When** 第一次推送失败
- **Then** 系统在 10 秒后重试第一次，30 秒后第二次，90 秒后第三次
- **And** 三次均失败后，事件进入死信队列
- **And** 管理面板显示"投递失败"状态和失败原因

**验收标准 4：取消订阅**

- **Given** 存在活跃的事件订阅
- **When** 通过管理 API 删除该订阅
- **Then** 订阅被立即删除，不再推送事件到该 URL

### 2.5 推送式撤销通知（F10）

**作为** 资源服务器运维工程师，  
**我希望** 在令牌被撤销后能立即收到推送通知，  
**以便** 及时更新自省缓存，避免已撤销的令牌在缓存 TTL 窗口内仍被接受。

**验收标准 1：撤销事件推送**

- **Given** RS 实例已在客户端注册中启用推送通知（`Client.Attributes["introspect_push_enabled"] = "true"`）
- **When** 令牌 T1 被用户或管理员撤销
- **Then** 系统通过 WebSocket/SSE 连接向所有已订阅的 RS 推送撤销事件
- **And** 事件包含令牌的 `jti` 和撤销时间戳

**验收标准 2：推送驱动缓存失效**

- **Given** RS 本地缓存中存有令牌 T1 的自省结果（标记为 active）
- **When** RS 收到 T1 的撤销推送
- **Then** RS 立即将 T1 的缓存标记为 inactive，无需等待 TTL 到期
- **And** 在下一次自省调用时返回正确的 `active: false`

**验收标准 3：连接断开恢复**

- **Given** RS 与 SSO 服务器之间的推送连接意外断开
- **When** 连接恢复后
- **Then** 系统推送断连期间发生的所有撤销事件（最多保留最近 1000 条）
- **And** RS 可在恢复后同步状态

### 2.6 签名自省响应（F08）

**作为** 微服务平台工程师，  
**我希望** 自省响应经过签名（JWS），  
**以便** 资源服务器可以安全地缓存自省结果，无需信任中间代理——我可以验证签名来确认响应未被篡改。

**验收标准 1：签名响应**

- **Given** 自省请求头包含 `Accept: application/jose+json`
- **When** 自省端点处理请求
- **Then** 返回 JWS 签名负载：`{"payload": <base64>, "signatures": [...]}`
- **And** 签名使用专用的 introspection signing key（非令牌签发 key）

**验收标准 2：RS 缓存签名结果**

- **Given** RS 收到签名自省响应，valid 直到 `exp`
- **When** RS 验证签名通过
- **Then** RS 缓存整个 JWS 对象，在 `exp` 之前无需再次调用自省端点
- **And** 即使中间缓存被篡改，RS 也能通过签名验证发现

**验收标准 3：签名密钥轮换**

- **Given** 自省签名密钥被轮换
- **When** RS 使用旧密钥验证新签名的响应
- **Then** 验证失败，RS 重新获取最新签名密钥（通过 JWKS 端点）
- **And** 旧密钥在轮换后至少保留 2× 缓存 TTL 的宽限期

## 3. 边界场景分析

### 3.1 异常输入和错误处理

| 场景 | 功能入口 | 风险描述 | 建议处理 |
|------|---------|---------|---------|
| 设备指纹 JS 被浏览器隐私模式阻止 | 自适应认证① | 缺少设备指纹 → 错误评估为高/低风险 | 降级：缺少设备指纹时不做风险降级（不因此拒绝），但审计标记 `device_fingerprint: unavailable` |
| 交换请求同时携带循环链 + 超大 payload | 令牌交换② | act 链过大导致内存/CPU 压力 | 链深度检查在签名验证之前；超过 `maxActChainDepth` 直接拒绝（已实现 10 跳上限） |
| 订阅 URL 是 SSO 自身（回调循环） | 事件订阅④ | 事件 → webhook → SSO 自身 → 触发新事件 → 死循环 | 创建订阅时校验 URL 不指向 SSO 已知端点列表；循环检测（event ID 去重） |
| 批量自省请求 10000 个 token | 自省增强⑤ | 高内存使用、长响应时间 | 设置批量上限（如 500/批次）；超过上限返回 413 或分块处理 |
| 自省响应签名密钥被泄露 | 自省增强⑤ | 攻击者可伪造自省响应 | 密钥轮换后立即失效；JWKS 端点支持 `?prefix=<kid>` 快速查询；宽限期限制为 2× TTL |
| 风险引擎依赖的外部异常检测服务超时 | 自适应认证① | 整个登录流程被阻塞 | 同步阶段仅使用确定性信号（GeoIP、设备指纹哈希、账户锁定状态）；异步信号（行为异常）作为审计附加，不阻塞认证 |

### 3.2 并发和竞态条件

| 场景 | 功能入口 | 风险 | 建议防护 |
|------|---------|------|---------|
| 同一令牌交换请求被两个客户端同时处理 | 令牌交换② | 双重交换 → 两条 act 链 | subject_token 单次消费 + act 链操作加写锁 |
| 会话中枢在多副本间同时接收登出请求 | 会话中枢③ | 竞态：一个副本销毁会话，另一个副本同时刷新 | 乐观锁 + 版本号；跨副本通过 cluster bus 协调 |
| 推送撤销与自省缓存的并发窗口 | 自省增强⑤ | RS 在收到推送前 1ms 完成缓存写入 | 推送采用至少一次交付；RS 端去重（jti + 撤销时间戳）；缓存 TTL 作为最终保险 |
| 多个 RS 同时订阅同一事件类型的"订阅风暴" | 事件订阅④ | 令牌撤销事件 → 1000 个 RS 同时被推送 | 扇出模式：事件总线一次处理，按订阅分发；每订阅独立 goroutine + 有界缓冲区 |
| 风险评分缓存击穿（热点用户同时登录） | 自适应认证① | 用户 Alice 的评分缓存过期 + 100 个并发请求 | `singleflight` 模式：同一用户的风险评估请求合并为 1 个 |

### 3.3 性能瓶颈场景

| 场景 | 功能入口 | 风险 | 建议优化 |
|------|---------|------|---------|
| 50ms 同步评估窗口内的风险引擎 | 自适应认证① | 策略评估 + 信号收集超过 50ms → 全量登录延迟 | 分层策略：确定性信号（allowlist/blocklist）<1ms 短路；启发式信号（评分模型）异步更新预热缓存 |
| Mesh 场景中 10K+ RPS 批量自省 | 自省增强⑤ | 签名 JWS 的 CPU 成本（每响应 RSA/ECDSA 签名） | 专用签名 key 支持 Ed25519（最快）；批量端点按 (RS, TTL) 预计算 |
| 事件订阅引擎的推送吞吐 | 事件订阅④ | 高事件率（每秒 10000+ 令牌撤销）压垮推送引擎 | 异步管道 + 批量推送（同一订阅的多事件合并为批次）；慢订阅自动降速 |
| 令牌交换 act 链序列化 | 令牌交换② | act 链 10 跳 → 每次 prepend 拷贝整个链表 | 不可变链（immutable chain）：新节点引用旧节点，不拷贝；仅序列化时遍历 |
| 中枢会话表按用户扇出 | 会话中枢③ | 用户有 100+ 跨协议会话 → 全文扫描 | 两级索引：(tenant_id, user_id) 哈希索引 + 协议类型过滤 |

### 3.4 安全和权限边界

| 场景 | 功能入口 | 风险 | 建议 |
|------|---------|------|------|
| 自适应认证策略绕过——攻击者伪装设备指纹 | 自适应认证① | 浏览器 JS 指纹可伪造 | 服务器端信号（TLS 握手参数、IP 信誉、HTTP 头顺序）作为不可伪造的补充信号 |
| 事件订阅 Secret 泄露 | 事件订阅④ | 攻击者可伪造事件推送 | 支持 dual-secret 滚动（current/next）；所有推送经过 HMAC 签名验证 |
| 自省签名响应被重放到其他 RS | 自省增强⑤ | 攻击者截获一份签名响应，用于其他未授权的 RS | 响应中绑定 `aud`（目标 RS client_id 或 audience）；验证方必须检查 `aud` |
| 令牌交换链中恶意客户端注入虚假 act 节点 | 令牌交换② | 伪造前序链节点 | 新签发的令牌由 SSO 签名，act 链是声明级不可篡改的（JWS 签名保护） |
| 批量自省被用作令牌存在性探测（Oracle） | 自省增强⑤ | 攻击者批量提交哈希探测有效令牌 | 不存在的令牌统一返回 `active: false`（与单个自省相同的 Oracle-leak 防护） |

### 3.5 配置和部署场景

| 场景 | 涉及方向 | 描述 | 建议 |
|------|---------|------|------|
| 新部署时自适应认证默认策略 | ① | 初始安装无风险评分规则，所有请求被降级为"无风险" | 默认关闭（Fail-Open 模式）；配置开启后所有策略从"拒绝未知"开始 |
| 从无签名自省迁移到签名自省 | ⑤ | 存量 RS 期望 JSON 响应，新的 RS 期望 JWS | 通过 `Accept` 头协商格式；默认返回 JSON，`Accept: application/jose+json` 触发签名响应 |
| 多区域部署下的事件订阅一致性 | ④ | 区域 A 的事件的应在区域 A 的推送通道中投递 | 事件按区域标签分发；跨区域事件通过 cluster bus 传递但仅本地推送 |
| 令牌交换治理的渐进采用 | ② | 存量客户端期望 scope 全量继承，新策略默认收窄 | 按客户端 Opt-in 模式：`token_exchange_policy: strict | legacy`；新客户端默认 strict |
| 会话中枢回退——中枢故障时各协议独立运行 | ③ | 中枢服务不可用 | Fail-Open：各协议回退到独立的会话管理（退化到当前的隔离模式）；中枢恢复后增量同步 |

### 6.3 回滚策略

| 功能 | 回滚难度 | 回滚方式 | 注意事项 |
|------|---------|---------|---------|
| **F02: Scope 收窄** | **中** | 将 `token_exchange.scope_policy = narrow` 切换为 `legacy` | 切换期间可能已因为 scope 收窄而失败的交换请求需要重试；存量客户端不受影响（strict vs legacy 按客户端配置） |
| **F03: 循环检测** | **低** | 关闭特性开关 | 纯安全功能，关闭后回到无检测状态——建议永不为 false |
| **F06: 事件订阅** | **中** | 关闭特性开关；已创建的订阅和死信数据保留 | 推送会停止，已入死信的事件在回滚后不可恢复 |
| **F10: 推送撤销** | **低** | 关闭 WebSocket 端点 | RS 回退到轮询模式（退化到当前行为——无推送） |

**关键回滚原则**：
1. **F02 一旦有存量客户端配置为 `strict`，切换回 `legacy` 不影响已有 strict 客户端**（按客户端独立配置）
2. **F03** 是纯加法安全逻辑，建议永不回滚
3. 回滚前必须有灰度期的指标验证（错误率、延迟、投诉量）
4. 所有回滚需要通知已启用的 Beta 客户

## 总体评价与建议

### 产品健康度评估

这 5 个方向整体上反映了产品从"功能完备的身份协议 SDK"向"企业级认证平面平台"跃升的关键桥梁。当前代码库在协议覆盖和基础安全上已非常成熟，但在**跨功能集成**和**运维/安全平面**上存在结构性缺口。

### 一句话总结

> **Snaplink 已经是一个卓越的认证引擎，但缺少让它与周围生态系统（SIEM、服务网格、多协议身份）对话的"神经系统"——这 5 个方向就是搭建这个神经系统所需的骨干线路。**

### 关键发现

| 维度 | 亮点 | 风险 |
|------|------|------|
| **代码复用度** | 方向② 在现有 token exchange SPI 上扩展（~XS 到 S 工作量） | 方向① 需要完整的新 SPI + 策略引擎（L 工作量） |
| **安全影响** | 方向②③⑤ 直接填补安全缺口；方向①④ 提升安全纵深 | 方向① 的同步评估窗口（50ms）是架构级约束 |
| **产品差异化** | 方向③（跨协议会话中枢）是竞品未覆盖的独特价值 | 方向⑤ 与 Envoy/服务网格生态耦合，需确保独立于特定网格 |
| **企业采纳壁垒** | 方向④（事件订阅）是最低门槛——无此功能就无 SIEM 集成 | 方向① 需要客户投入策略定义——需要提供默认策略模板 |
