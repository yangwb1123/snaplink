## 1. 架构评估

### 当前文档架构的优势

| 方面 | 评价 |
|---|---|
| **分离关注点** | `.github/SECURITY.md` 面向外部报告者（策略 + 流程），`docs/SECURITY.md` 面向内部开发者（架构 + 实现细节）—— 意图合理 |
| **安全架构表质量高** | `docs/` 中的 Hardened Areas 矩阵和 Fail-Open/Closed 决策表是稀缺资产，直接关联代码行为与安全决策，远超普通 OSS 项目水平 |
| **Developer Checklist 可落地** | 9 项检查中 6 项可直接映射到 `make` 目标或 `go test`，工业化程度高 |

### 关键设计缺陷（架构债务）

1. **SLA 冲突是最高优先级 bug**：`24h` vs `3 business days` — 这不是风格差异，而是可承诺性的契约差异。安全研究员严格按照更紧的 `docs/` 版本来预期，未兑现会直接损害项目信誉。在任何生产系统中，**两个节点声明相互矛盾的 SLA = Sev-0 故障**。

2. **单源原则（Single Source of Truth）违反**：一份策略信息分布在两个文件中，且无同步机制。这是典型的文档架构债务，类比于代码中同一常量在两个文件中以不同值定义。

3. **PGP 密钥承诺未经验证**：引用 `https://snaplink.dev/.well-known/pgp-key.txt` 但该端点尚未确认存在。在安全策略中做出无法兑现的技术承诺是危险的——报告者花时间获取密钥后发现无效，会降低信任。

4. **Operator Checklist 放在 GitHub 专属位置**：`.github/SECURITY.md` 中的 8 项加固检查清单是运维指南，放在项目根文档中比放在 GitHub 专属策略中更合理（Operator 更可能读 `docs/` 而非 `.github/`）。

### 文档架构 vs 代码架构的映射

当前的安全文档没有反映出代码的物理分层结构：

```
代码架构：                          文档覆盖：
interfaces/sso/  ← HTTP 端点     ──→  ✅ 部分覆盖（no-store 头）
protocols/oauth/ ← 协议逻辑       ──→  ✅ Oracle-leak / DELETE RETURNING
protocols/oidc/  ← OIDC 协议      ──→  ❌ 几乎没有文档
security/        ← 安全原语       ──→  ✅ JWT/JWE/DPoP
infrastructure/  ← 集成层         ──→  ❌ Redis/KMS 安全未涉及
```

**遗漏**：`oidc/`、`federation/`、`caep/`、`selfservice/`、`fapi/` 的安全属性在文档中完全未提及。

## 2. 扩展方向（5 个高价值方向）

### 方向 1：安全架构与代码的活链接（P0）

**为什么需要**：当前安全架构表是静态 Markdown。新增一个安全机制时，开发者需要手动更新两个位置（代码 + 文档），容易遗漏。

**核心挑战**：Go 没有标准的文档注解系统（类似 Java `@param` / Python docstring 的三斜线注释标记）。

**预期架构变更**：
- 在 `security/` 和 `oauth/` 下的核心安全函数上方，使用标准 Go 注释约定 `// Security: ...` 标注安全属性
- 引入一个轻量级文档扫描工具（纯 Go，无第三方依赖），从注释生成安全架构矩阵
- 在 CI 中运行：生成的矩阵与 `docs/SECURITY.md` 中声明的矩阵 diff，不一致则告警

**对现有系统的影响**：低。仅新增注释和 CI 步骤，不修改任何运行时行为。

### 方向 2：威胁模型文档化（P1）

**为什么需要**：当前安全策略描述了"做什么"（no-store、Oracle-leak、PKCE），但没有描述"防什么"（防止什么具体攻击场景）。没有威胁模型，新贡献者无法判断某个新增端点是否需要同样的防护。

**核心挑战**：威胁模型容易变成一次性文档。需要保持与代码演进同步。

**预期架构变更**：
- 新增 `docs/security/threat-model.md`
- 采用 **STRIDE** 分类法（每个端点/存储/协议的威胁分类）
- 每条威胁映射到具体的缓解措施和对应的测试
- 将威胁模型链接到 `docs/feature-matrix.md`：新 OAuth 授权类型必须通过威胁模型评审

**对现有系统的影响**：无。纯新增文档，不影响构建。

### 方向 3：Operator 安全审计模式（P1）

**为什么需要**：当前 Operator Checklist 是静态文本。Operator 无法自动化验证是否满足。

**核心挑战**：Go 应用层面的安全检查无法覆盖部署环境（TLS 终止、网络策略、密钥管理）。

**预期架构变更**：
- 新增 `GET /readyz` 或 `GET /security/health` 端点（已有 `/livez`/`/readyz`），报告安全配置健康度：
  - 签名算法是否为 allowlist 子集
  - JTI 重放保护是否启用
  - 是否配置了持久化审计 Sink
  - 锁定后端是否为 `file` / `etcd`（非 `noop`）
- 新增 `security/health.go`：无业务调用路径，仅读取配置状态

**对现有系统的影响**：低新增。不改变现有健康检查行为，仅扩展 `/readyz` 的返回信息。

### 方向 4：依赖供应链安全（P2）

**为什么需要**：项目有嵌套模块（`kms/*`、`saml/`、`ldap/`），依赖树复杂。没有 SBOM 或漏洞扫描策略。

**核心挑战**：多模块 `go.sum` 文件分散，统一扫描需要每个模块单独运行。

**预期架构变更**：
- 在 CI 中集成 `govulncheck`（Go 官方漏洞扫描器）
- 新增 `make vulncheck` 目标
- 将结果发布为 CI artifact
- 文档化第三方依赖的安全评估标准（见下节）

**对现有系统的影响**：仅 CI 变更，无运行时影响。

### 方向 5：安全变更的可审计 PR 工作流（P2）

**为什么需要**：影响安全边界的 PR（新端点、新存储、新协议）需要特殊审核流程，但当前没有标识机制。

**核心挑战**：自动检测"安全的变更"是 NP-hard（不是所有安全变更都有明显签名）。

**预期架构变更**：
- 定义 `SECURITY.md` 中开发者检查清单的标签系统：每个 PR 标签 `security/xxx` 自动触发安全审查
- 新增 `scripts/detect-security-changes.sh`：检测以下模式并提议标签
  - 新增 `_handler.go` / 路由注册 → `security/endpoint`
  - 修改 `*spi.go` → `security/interface`
  - 修改 `DELETE RETURNING` / `GetAndDelete` → `security/oracle-leak`
  - 新增 authenticator → `security/authn`
- 与 GitHub Actions / GitLab CI 集成

**对现有系统的影响**：低。仅 CI + 脚本，不改变运行时。

## 3. 接口设计建议

### 文档的"接口"设计原则

安全文档本质上是一个**多读者接口系统**。不同读者对同一文档有不同 SLA：

| 读者角色 | 关心的信息 | 消费方式 |
|---|---|---|
| 安全研究员 | 报告流程、SLA、PGP 密钥 | 一次性阅读 |
| 贡献者/开发者 | 安全检查清单、必须遵循的模式 | 每次提交前参考 |
| Operator/运维 | 部署加固清单、默认值 | 部署时对照 |
| 安全审计员 | 威胁模型、安全决策依据 | 定期审查 |
| CVE 协调员 | 受支持版本、披露流程 | 事件触发 |

**设计原则**：

1. **单一权威原则**：每段信息只在一个文件中声明，其他位置通过引用指向它。对于策略信息，`.github/SECURITY.md` 是权威。对于技术信息，`docs/SECURITY.md` 是权威。

2. **可验证性原则**：任何声称（"端点 X 设置了 no-store 头"）必须可由自动化检查验证。无法验证的声明标记为 `[manual]`。

3. **变更联动原则**：安全文档的变更与代码变更应处于同一个 PR 中（如同期更新 `docs/openapi.yaml`）。不允许单独提交安全文档变更而不涉及代码。

### 是否需要新的抽象层

**不建议引入新的抽象层**。当前的两文件结构本身不是问题。问题是：
- 职责边界不清晰（两份都试图做策略声明）
- 无同步保障（没有护栏防止 drift）

解决方案**不是引入第三份文件或新的文档框架**，而是：
1. 明确职责边界（如上所述）
2. 在 CI 中加入轻量级检查（可选方案 B 中的 `check-docs`）

### 向后兼容性

对于安全策略，向后兼容意味着**已公开声明的 SLA 不可收紧而不通知**。如果此前 `docs/SECURITY.md` 声明了 "24h 确认"，而新版本改为 "3 工作日"：

- **需要**：在 README 和仓库 About 中发布变更说明
- **需要**：在旧版本上保留一个标签的快照以备引用
- **不需要**：维持错误声明

## 4. 技术选型

### 是否需要引入新的技术栈

| 方向 | 是否需要新技术 | 建议 |
|---|---|---|
| 文档 SSOT 检查 | ❌ 不需要 | 纯 shell (`grep` + `diff`) 即可实现 |
| 安全注释活链接 | ⚠️ 可选 | 自研小型 Go 工具（< 100 行）或基于 `go/doc` |
| 威胁模型 | ❌ 不需要 | Markdown + 图表（Mermaid 格式，无需渲染器） |
| 安全健康端点 | ❌ 不需要 | 复用现有 `echo` / `grpc` 框架 |
| SBOM 生成 | ⚠️ 可选 | `go-sbom` 或 `syft`（作为 CI 工具引入，非运行时依赖） |

**结论**：本次重构**不需要引入新的运行时依赖**。所有工具链需求都可以用 shell 脚本或现有 Go 工具链满足。

### 第三方依赖评估标准

如果未来决定引入安全相关的第三方工具，评估标准如下：

| 标准 | 说明 |
|---|---|
| **纯 Go / CGO-free** | 与项目 `CGO_ENABLED=0` 构建策略一致 |
| **BSD/MIT/Apache 2.0 许可** | GPL/AGPL 排除（与项目现有依赖许可策略一致） |
| **依赖树 ≤ 5 级传递** | 避免深层依赖的漏洞面 |
| **维护活跃度** | 最近 6 个月内有提交；有明确的发布 tag |
| **不引入新的 HTTP 客户端或 TLS 栈** | 复用项目已有的 `net/http` / `crypto/tls` |

### 自建 vs 采购

| 场景 | 建议 | 理由 |
|---|---|---|
| 安全注释提取器 | **自建**（~80 行 Go） | 需求非常简单：扫描 `// Security:` 注释；无商业工具适合 |
| SBOM 生成 | **采购**（`syft` / `go-sbom`） | CNCF 生态成熟工具；自建会重复造轮子 |
| 威胁模型工具 | **两者都不**（Markdown 即可） | OWASP Threat Dragon 等工具太重，不适合此规模项目 |
| 漏洞扫描 | **采购**（`govulncheck`，官方） | Go 团队维护，零集成成本：`go install golang.org/x/vuln/cmd/govulncheck@latest` |

## 5. 实施路线图

### 优先级排序

```
P0 ─────────────────────────────────────────────────►
    SLA 冲突修复         不能有两个 SLA 版本同时存在
    内容合并             防止信息丢失
    职责边界划分         明确 .github/ vs docs/ 角色
                        预期完工：1 个 PR

P1 ─────────────────────────────────────────────────►
    安全架构表增强       每项映射到代码包 + 测试文件
    Fail-Open/Closed ADR 引用
    开发者检查清单 [auto]/[manual] 标记
    威胁模型初稿（STRIDE）
    安全健康端点扩展     /readyz 增加安全状态
                        预期完工：2-3 个 PR

P2 ─────────────────────────────────────────────────►
    make check-docs      文档一致性自动化检查
    govulncheck 集成     CI 漏洞扫描
    安全变更检测脚本     PR 标签自动提议
    SBOM 生成
    安全注释活链接工具   注释 → 文档自动化
                        预期完工：持续（低优先级）
```

### 阶段划分

#### 阶段 1：止血（SLA 冲突修复）— 1 个 PR

```
步骤 1:  裁定 SLA → 统一为 .github/SECURITY.md 的版本
步骤 2:  合并两份文档内容，消除重复
步骤 3:  重写 docs/SECURITY.md 为安全架构参考（引用而非重复策略）
步骤 4:  git mv 保留历史
```

**验证**：
```bash
# 检查两份文档是否仍有冲突声明
grep -c "24 hours" docs/SECURITY.md  # 必须返回 0
grep "Acknowledgement" .github/SECURITY.md  # 必须包含 3 business days
```

#### 阶段 2：增强（安全架构活文档）— 2-3 个 PR

```
PR 2.1:  安全架构表增强，每项添加包路径 + 测试文件
PR 2.2:  开发者清单 [auto]/[manual] 标记 + 威胁模型初稿
PR 2.3:  /readyz 安全健康扩展（可选，若需要）
```

#### 阶段 3：自动化（持续）— 独立 PR

```
PR 3.1:  scripts/check-docs.sh → make check-docs
PR 3.2:  CI 集成 govulncheck
PR 3.3:  安全变更检测脚本
PR 3.4:  安全注释活链接（若决定推进）
```

### 风险矩阵

| 风险 | 概率 | 影响 | 阶段 | 缓解措施 |
|---|---|---|---|---|
| SLA 从 24h 改为 3 工作日引发社区不满 | 低 | 中 | 1 | 在 Release Notes 中充分沟通变更原因；保留历史版本可见性 |
| PGP 端点不存在导致策略不实 | 高 | 低 | 1 | 移除引用或添加"将上线"标注；不走 PR 之外的流程 |
| 维护者不熟悉新流程 | 中 | 低 | 2 | 安全变更 PR 标签以 Webhook 形式通知维护者（无需手动） |
| 安全注释活链接工具版本漂移 | 低 | 低 | 3 | 将工具纳入项目 vendor 目录或用 `go install` 固定版本 |
| 威胁模型无人更新 | 中 | 中 | 2 | 将威胁模型更新纳入安全变更 PR 检查清单；CI 检查 `docs/security/` 目录的修改时间与代码变更时间差 |

### Key Decisions 快速总结

| 决策 | 选项 | 推荐 | 理由 |
|---|---|---|---|
| 文档架构 | 单源 / 双源+检查 / symlink | **单源**（引用机制） | 消除 drift 的最简洁方案 |
| SLA | 24h / 3 工作日 | **3 工作日** | 更可承诺；匹配 GitHub Advisory 工作流 |
| PGP 密钥 | 保留 / 移除 / 标注待上线 | **标注待上线** | 不丢失有价值的提议，但不做出无法兑现的承诺 |
| 安全健康端点 | 新增 / 复用 /readyz | **复用 /readyz** | 保持简单；安全状态是健康状态的一部分 |
| 检查清单自动化 | 全部 [auto] / 混合 [auto]+[manual] | **混合** | 部分检查（如审计日志使用模式）无法自动化 |
| 威胁模型 | STRIDE / 自定义 / 不做 | **STRIDE** | 行业内广泛认可；学习成本低于自定义模型 |

---

**总结**：这是一个典型的文档架构重构——不涉及 Go 代码修改，但涉及**信息架构**的重新设计。最大风险是 SLA 冲突（已确认为 P0），其次是 PGP 承诺未验证（P1）。推荐的实施方案将一个 PR 修复冲突，后续演化逐步增加自动化程度。整个路线图可以在 3-5 个 PR 内完成，无需引入新的运行时依赖。
