## 1. Architecture Assessment

### 1.1 Current Architecture Strengths

| Dimension | Strength | Evidence |
|-----------|----------|----------|
| **Layer isolation** | Physically layered tree with enforced import direction | `architecture_layer_test.go` blocks upward imports |
| **Hexagonal core** | All business logic in free functions (`oauth.HandleXxx`), root is thin wiring | `accessors.go` + `handlers.go` pattern |
| **SPI-first storage** | Every concern = interface + memory impl ± sqlite | No mocks in tests; real `MemoryProvider`/`MemorySink` |
| **Audit mechanism** | `SetMeta` only, W3C TraceID/SpanID in events, hash chain | Bounded cardinality, no `e.Metadata = map{...}` |
| **Security posture** | Oracle-leak hardening, anti-enumeration, bcrypt dummy cost | All committed gate tests |

### 1.2 Current Architecture Limitations

The review identifies five specific blind spots. They fall into three categories:

**Category A: Missing Defensive Layers** (immediate risk)

| Gap | Risk | Severity |
|-----|------|----------|
| No CSP on any SPA (`index.html` ×3, `form_post.html` ×1) | XSS at any SPA → full session theft | **High** |
| No Permissions-Policy / `clear-site-data` on logout | Federated logout leaves browser state | **Medium** |
| No `Referrer-Policy` on auth endpoints | Referer header leaks auth codes in URL | **Medium** |

**Category B: Missing Engineering Infrastructure** (degradation risk)

| Gap | Risk | Severity |
|-----|------|----------|
| 0 of 4 benchmark files wired to CI | Silent perf regression, no P99 budget | **High** |
| No JSON Schema for config | Operator misconfiguration at deploy time | **Medium** |
| Audit tracer and OTel share TraceID but not span hierarchy | Async failures (CAEP push, cluster events) invisible in trace view | **Medium** |

**Category C: Missing Market Enabler** (opportunity risk)

| Gap | Risk | Severity |
|-----|------|----------|
| No FIPS 140-3 build mode | Cannot enter FedRAMP/FISMA market | **High** (strategic) |

### 1.3 Architectural Debt

**Debt 1: `form_post.html` inline script** — The OIDC form_post response mode uses
`document.forms[0].submit()` inline JavaScript. Adding CSP without addressing this
creates a chicken-and-egg problem: CSP blocks the exact script needed for the
feature to function. This is the single highest-priority architectural debt because
it blocks the CSP fix.

**Debt 2: Audit-OTel span isolation** — The audit system's `TraceContext` parses
the same W3C `traceparent` header that OTel middleware writes, producing identical
TraceID. But the audit system generates its own SpanID independently and never
calls `otel.Span.SpanContext()`. The result is a "half-bridge": trace identity is
shared, but span hierarchy is fractured. This means any async audit sink
(CAEP push, cluster bus publish) produces orphan spans invisible to the OTel
trace tree.

**Debt 3: CI lacks benchmark gating** — The four existing benchmark files
(`bind_bench_test.go`, `issuer_bench_test.go`, `ratelimit_bench_test.go`,
`jwks_verify_bench_test.go`) are human-invokable only. No CI step enforces P99
latency or allocation budgets. Given that `make config-validate-all` already
demonstrates CI can run Go tools (it launches the server with `--validate-only`),
the infrastructure pattern exists — only the benchmark gate is missing.

## 2. Extension Directions

### Direction A: CSP & Security Header Governance Framework

**Why needed (business value):** Three SPA surfaces (`consent`, `login`, `oidc`)
are currently served without any Content-Security-Policy. A single XSS on any of
them can exfiltrate auth codes, tokens, or session cookies. Additionally,
`form_post.html` (OIDC form_post response mode) uses inline JavaScript that CSP
would block by default, creating a direct conflict between security and functionality.

**Core challenges:**

| Challenge | Detail |
|-----------|--------|
| `form_post.html` inline script | Must inject per-request nonce into template — Go's `html/template` supports this but requires `template.Src` with nonce attribute |
| Three SPA entry points | Different CSP needs per SPA (login vs consent vs oidc) — requires per-route policy or at least per-SPA whitelist |
| Report-Only transition | 2-week data collection period needed before enforcement; operator must understand the observation window |
| SPA inline styles | Modern SPAs often use inline styles for dynamic theming; need `'unsafe-inline'` for style-src or switch to CSS-in-JS with nonce |

**Expected architecture changes:**

```
Current:
  Go handler → serve static HTML files (no CSP headers)

Target:
  middleware/securityheaders.go (new)
    ├── Content-Security-Policy        (per-SPA, with nonce for form_post)
    ├── Permissions-Policy             (deny all unused features)
    ├── Referrer-Policy                (same-origin for auth endpoints)
    ├── X-Content-Type-Options         (nosniff — already partially done)
    └── Clear-Site-Data               (on logout endpoint)

  Phase 1.5 specific:
    interfaces/sso/templates/form_post.html
      ├── {{ .CSPNonce }} → <script nonce="{{ .CSPNonce }}">
      └── When rendering: sso.renderFormPost(ctx, nonce) generates + injects nonce
```

**Impact on existing system:**

| Concern | Impact | Mitigation |
|---------|--------|------------|
| Static file serving | Must switch from `http.FileServer` to handler wrapper (or `embed` + header middleware) | Minimal — Echo middleware pattern exists |
| OTel trace propagation | None — CSP is response header only, no request-path interaction | N/A |
| Audit events | None added | N/A |
| CI time | Increase ~0 (header injection is zero-allocation) | N/A |

### Direction B: Declarative Config Schema & GitOps Validation

**Why needed (technical value):** Current `make config-validate-all` performs
runtime validation (load config, start server, error out). This requires a Go
build step and cannot provide operator-side feedback in IDEs or CI linting.
A JSON Schema enables: (a) IDE autocompletion in YAML files, (b) `kubeval`-style
pre-deployment validation in GitOps pipelines, (c) schema-as-documentation that
stays in sync with code.

**Core challenges:**

| Challenge | Detail |
|-----------|--------|
| JSON Schema cannot express all Go constraints | Field mutual exclusion (webauthn + password), merge-order semantics (env override after YAML), migration paths — require a Go validator chain as complement |
| Schema generation must be automated | Manual schema drifts; need `go-jsonschema` or similar codegen from Go structs |
| `--validate-only` already exists | Must extend, not replace — add `--schema-only` flag that skips DB connection and audit init |
| Config key renaming/migration | Schema describes current shape; migration from v0.5 to v1.0 requires separate `migrate.Config()` logic |

**Expected architecture changes:**

```
Current:
  config.Load() → parse YAML + env + flags → runtime validate → start server

Target (three-layer validation):

  Layer 1: JSON Schema (sso-config.schema.json)
    ├── Auto-generated from config.Config struct tags
    ├── Checks: required fields, types, enums, patterns
    ├── Used by: IDE, CI linting, GitOps pre-deploy
    └── Tool: go generate ./config/ → schema_gen.go → sso-config.schema.json

  Layer 2: Go Validator Chain (config/validator.go)
    ├── type ConfigValidator func(*Config) []error
    ├── Built-in: field mutual exclusion, logical consistency, algorithm subset
    └── Called after schema passes, inside Load() + --validate-only

  Layer 3: Migration Logic (config/migrate.go)
    ├── Handles: field rename, type change, default shift
    └── Called before validation, on every Load()

  CLI:
    sso --validate-only             # current: full startup validation
    sso --validate-only --schema    # new: YAML + JSON Schema + validator chain only
```

**Impact on existing system:**

| Concern | Impact | Mitigation |
|---------|--------|------------|
| `config.Load()` | New `AfterSchemaValidate` hook in load pipeline | Add to existing `load.go`, not a new file |
| CI | `make config-validate-all` gets `--schema` flag | Single-flag add to existing target |
| Config YAML files | Schema reference line added (`# yaml-language-server: $schema=...`) | Non-breaking |
| Build | `go generate ./config/` added to `generate` target | ~2s added to build |

**Dependency:** Direction D (Benchmark CI) should precede this — the same CI
infrastructure (stable runner, artifact storage) is used for schema validation.

### Direction C: Async Trace Span Integrity

**Why needed (technical value):** The audit system and OTel currently share
TraceID (via W3C `traceparent` header) but produce independent span trees.
This means async operations (audit sink writes, CAEP push to affected clients,
cluster bus event publish) create orphan spans. When these operations fail —
CAEP push failure, cluster event loss — the failure is invisible in OTel trace
views, making diagnosis disproportionately expensive.

**Core challenges:**

| Challenge | Detail |
|-----------|--------|
| Async goroutine span lifecycle | If HTTP handler root span closes before audit goroutine completes, child span becomes orphan. Must choose: (A) `otel.WithNewRoot()` creating independent traces, or (B) delayed root span teardown |
| Audit sink interface | `audit.Sink.Write()` is synchronous in interface but async in impl; span context must be propagated through `context.Context` |
| No context propagation in existing sinks | Memory sink ignores ctx; SQLite sink uses `context.Background()` internally |
| Cluster bus publish | Async publish creates goroutine inside `cluster/memory.go` — no span at all |

**Expected architecture changes:**

```
Current:
  HTTP handler (root span) → audit.Send() → goroutine (no span)

Target (Path B: delayed root span):
  HTTP handler (root span)
    ├── audit.Send(ctx, event)
    │   └── audit goroutine (child span, ctx propagated)
    │       └── WaitGroup for root span teardown
    └── defer rootSpan.End()
        └── wg.Wait() with 100ms timeout (fail-open: orphan permitted after timeout)

  Specific sink changes:
    infrastructure/defaultimpl/memory_audit.go
      - Now respects ctx: otel.SpanFromContext(ctx) → span.AddEvent()

    infrastructure/defaultimpl/sqlite/audit.go
      - context.Background() → ctx from parameter

    platform/cluster/memory.go
      - Publish() creates child span on received ctx
      - Subscribe handler receives context with span
```

**Impact on existing system:**

| Concern | Impact | Mitigation |
|---------|--------|------------|
| `audit.Sink` interface | No signature change — context already flows through `context.Context` | Interface stable |
| `memory_audit.go` | Must add `context.Context` parameter to internal methods | Internal only; public SPI unchanged |
| Root span latency | Worst-case +100ms if audit goroutine slow | Timeout + fail-open; operator configurable |
| All tests using audit | Must propagate `context.Background()` or `t.Context()` | One-line change per call site |

### Direction D: Benchmark Budget & CI Integration

**Why needed (engineering value):** Four benchmark files exist but none are wired
to CI. Any code change (e.g., adding an allocation to the token issuance hot path,
increasing bcrypt cost, adding a database query to the ratelimit check) can silently
degrade P99 latency or increase GC pressure. Without budget gates, performance
regressions are only discovered in production.

**Core challenges:**

| Challenge | Detail |
|-----------|--------|
| GitHub Actions runner CPU variance | Shared `ubuntu-latest` vCPU — requires `-count=10` for statistical significance |
| CI time budget | 4 benchmarks × 4 backend combos × 10 reps = 160 runs, ~8-10min | Must tier: critical (every PR) vs extended (daily schedule) |
| Budget format | Need comparison mechanism: `benchstat` or custom comparator | Must handle "no previous baseline" on first run |
| File size for benchmark results | Storing baseline in repo (`testdata/benchmarks/`) grows repo | Use CI artifact, not committed file |
| Allocation budgets | More stable than latency on shared runners | Should be primary regression signal |

**Expected architecture changes:**

```
Current:
  [repo]/  *.go
  [repo]/  *_bench_test.go    # 4 files, human-only

Target:
  .benchmarks.yaml (new)
    ├── tiers: { critical, extended }
    ├── budgets: { p99_ms, ns_op, allocations }
    └── backends: { memory, sqlite }

  .github/workflows/benchmark.yml (new)
    ├── on: [pull_request, schedule(weekly)]
    ├── critical: runs on each PR (~2min)
    │   └── gates: block PR if p99 > budget or allocations > budget
    ├── extended: runs on schedule (~10min)
    │   └── report only: post to GH Pages
    └── tools: benchstat comparison against base branch

  benchmarks/compare.go (new, tools/ level)
    ├── Reads .benchmarks.yaml
    ├── Parses `go test -bench=. -benchmem` output
    ├── Compares against baseline (CI artifact or committed baseline)
    └── Exits non-zero on budget violation (for CI gate)
```

**Impact on existing system:**

| Concern | Impact | Mitigation |
|---------|--------|------------|
| CI pipeline | New workflow file; no changes to existing CI | Parallel workflow, non-blocking initial 30 days |
| Source code | Zero changes to .go files | All changes in `.github/` + `benchmarks/compare.go` |
| Build time | ~2min added to PR CI for critical tier | Acceptable; extended tier is off-PR |

### Direction E: FIPS 140-3 Compliance Build Mode

**Why needed (market value):** FedRAMP Moderate/High and FISMA compliance require
FIPS 140-3 validated cryptography. Snaplink currently uses Ed25519 (not FIPS
certified in most implementations) and bcrypt (NIST-recommended replacement is
PBKDF2). Without a FIPS build mode, the entire FedRAMP market is inaccessible.
This is the highest-value market expansion direction.

**Core challenges:**

| Challenge | Detail |
|-----------|--------|
| Ed25519 FIPS status | FIPS 186-5 includes Ed25519 (2023), but Go FIPS module lag means conservative default = P-256. Configurable `fips.allowed_curves` needed |
| bcrypt → PBKDF2 migration | bcrypt not FIPS-certified. PBKDF2-HMAC-SHA256 is FIPS 198-1, but Go's `x/crypto/pbkdf2` must use FIPS module's HMAC+SHA256 — only in `GOEXPERIMENT=systemcrypto` builds |
| FIPS base image | `golang:1.24-fips-alpine` or RedHat UBI — not standard Docker Hub images. CI must build from FIPS-enabled base |
| Build matrix duplication | Two Dockerfiles (`Dockerfile` + `Dockerfile.fips`), two CI jobs, dual test suites |
| HSM integration | FIPS mode with hardware-backed keys requires KMS bridge: PKCS#11, AWS KMS FIPS, Azure Key Vault |

**Expected architecture changes:**

```
Current:
  go build ./...           # single build, any algorithm
  go test ./...            # single test run

Target:
  go build -tags fips ./...    # FIPS-tagged build
  go test -tags fips ./...     # FIPS-only tests

  Dockerfile.fips (new)
    FROM golang:1.24-fips-alpine AS builder
    GOEXPERIMENT=systemcrypto go build -tags fips ./...

  security/fips.go (new, build tag: fips)
    ├── fips.Enabled() bool          // runtime check
    ├── fips.AllowedAlgorithms() []string  // returns configured set
    └── fips.PasswordHash(password)  // uses PBKDF2-HMAC-SHA256 instead of bcrypt

  config/fips.go (new)
    ├── FIPSConfig {
    │     Mode: "disabled" | "enabled" | "permissive"
    │     AllowedCurves: []string{"P-256", "P-384", "Ed25519"}
    │     AllowedAlgs: []string{"RS256", "PS256", "ES256", "EdDSA"}
    │   }
    └── fips.allowed_curves default: P-256 only (conservative)

  defaultimpl/fips_issuer.go (new)
    ├── FIPS-compliant JWT issuer wrapping crypto/ecdsa + crypto/rsa
    └── Rejects creation with non-FIPS alg
```

**Impact on existing system:**

| Concern | Impact | Mitigation |
|---------|--------|------------|
| Issue/verify entry points | Must check `fips.Enabled()` before using non-FIPS algorithms | Add to existing issuer factory, not to hot path |
| Password hashing | `defaultimpl/password.go` needs conditional bcrypt/PBKDF2 | Add build-tag guarded `password_hash.go` |
| CI | Two build matrices (regular + FIPS) | Shared test base; FIPS is additional job |
| Config | New `fips` section in YAML | Backward compatible: default disabled |
| Dependency | FIPS Go base image | Must be in registry accessible to CI |

## 3. Interface Design Proposals

### 3.1 Security Headers Middleware Interface

The CSP middleware should follow the **existing middleware pattern** in `interfaces/middleware/`.
No new abstraction layer needed.

```go
// Design sketch (not code — architecture only):
//
// middleware.SecurityHeadersConfig:
//   Policy map[string]string   // per-route CSP directives
//   ReportOnly bool           // Phase 1: report-only
//   Nonce func() string       // per-request nonce generator
//   ExcludePaths []string     // paths that should not get CSP headers
//
// Registration pattern (in sso.go):
//   s.Use(middleware.SecurityHeaders(middleware.SecurityHeadersConfig{
//       Policy: map[string]string{
//           "/ui/consent":  "default-src 'self'; script-src 'self'",
//           "/ui/login":    "default-src 'self'; script-src 'self'",
//           "/ui/oidc":     "default-src 'self'; script-src 'self' 'nonce-{CSPNonce}'",
//       },
//       ReportOnly: true,
//   }))
```

**Design decision: per-route vs global policy**

| Option | Pros | Cons |
|--------|------|------|
| Global CSP (same policy on all paths) | Simpler implementation, one config entry | SPA-specific CSP needs force most restrictive common denominator |
| Per-route CSP (config per path) | Tailored to each SPA's needs, tighter security | More config surface, potential for admin mistakes |
| **Recommended: per-SPA group** (login, consent, oidc each get own policy; all other paths get a global baseline) | Balance of security and simplicity | Requires 4 config entries (login, consent, oidc, + default) |

**Recommended: Per-SPA group** — Three explicit policies + one global baseline. The
`form_post.html` nonce applies only to the OIDC SPA group. This matches the
three `index.html` files already existing under `interfaces/web/*/`.

### 3.2 Config Validation Interface

**Recommendation: Three-layer validation with a single entry point.**

```
Current:    config.Load() → validate (inline)
Target:
  config.Load() →
    1. config.migrate()         // upgrade legacy keys (Phase 3)
    2. config.validateSchema()  // JSON Schema (Phase 1)
    3. config.validateLogic()   // Go validator chain (Phase 1.5)
    4. runtime checks           // DB connection, audit init (existing)
```

The JSON Schema is **auto-generated** at `go generate ./...` time. The Go
validator chain is the **safety net** for constraints JSON Schema cannot express
(field mutual exclusion, merge-order correctness).

**New SPI (lives in `config/` package, not a new layer):**

```go
// Design: Validator interface for pluggable config checks
type Validator interface {
    Validate(*Config) []error
    Name() string          // for error attribution
}
```

This keeps the existing `--validate-only` flag as the single entry point. The
`--schema-only` subflag controls how deep validation goes:

| Flag | Schema | Validator Chain | Runtime |
|------|--------|-----------------|---------|
| `--validate-only` | ✅ | ✅ | ✅ (current behavior) |
| `--validate-only --schema` | ✅ | ✅ | ❌ (new, fast path) |

### 3.3 Async Span Propagation

**No interface change to `audit.Sink`.** The existing `context.Context` parameter
carries the span implicitly. The change is inside implementations:

- `memory_audit.go`: Extract span from ctx and add event
- `sqlite/audit.go`: Replace `context.Background()` with provided ctx
- `cluster/memory.go`: Propagate ctx through `Publish()` so subscriber handers
  receive the parent span

**Design decision: Path A (new root) vs Path B (delayed teardown)**

| Option | Pros | Cons |
|--------|------|------|
| **Path A:** `otel.WithNewRoot()` for async goroutines | Parent handler can exit immediately; no latency added | Trace is fragmented — cannot see the full request lifecycle in one waterfall view |
| **Path B:** Defer root span teardown until async ops complete | Full trace waterfall; complete visibility | +100ms max latency (configurable timeout); risk of root span leak if goroutine hangs |
| **Recommended: Hybrid** — Audit sinks use Path B (they are bounded, fast); cluster bus publish uses Path A (long-lived subscribers) | Best of both | Two patterns to document; minimal complexity |

**Recommended: Hybrid.** Audit sinks (millisecond-latency writes) use Path B.
Cluster bus publish (potentially long-lived) uses Path A.

## 4. Technical Selection

### 4.1 CSP Implementation: Go middleware vs Reverse Proxy

| Criterion | Go middleware (Echo) | OpenResty / nginx |
|-----------|---------------------|-------------------|
| Per-route policy | ✅ Native | ✅ via `location` blocks |
| Nonce injection | ✅ In-template | ❌ Requires Lua scripting |
| CI compatibility | ✅ Same process | ❌ Separate deployment |
| Existing pattern | ✅ Middleware stack exists | ❌ Must add reverse proxy for SPAs |
| Latency | ✅ Zero-allocation path | ✅ Negligible |
| **Recommendation** | ✅ **Go middleware** | ❌ |

**Decision:** Go middleware in `interfaces/middleware/`. The nonce requirement for
`form_post.html` alone rules out nginx-only — Go must pass the nonce into the HTML
template.

### 4.2 JSON Schema Generator

| Tool | Go struct support | CI-friendly | Maintenance |
|------|------------------|-------------|-------------|
| `go-jsonschema` (by omissis) | ✅ Tags + types | ✅ CLI | Community maintained |
| `jsonschema-gen` (by atombender) | ✅ Deep structs | ✅ Codegen | Active |
| Manual YAML | ❌ Drift guaranteed | ❌ | ❌ |
| **Recommendation** | ✅ `go-jsonschema` with codegen comment annotations | ✅ go:generate | — |

**Decision:** `go generate` using `go-jsonschema`, configured via struct field tags.
The schema output is committed to repo (`config/sso-config.schema.json`) for IDE
consumption.

### 4.3 Benchmark Tooling

| Tool | Purpose | Recommendation |
|------|---------|---------------|
| `go test -bench=. -benchmem` | Raw benchmark execution | ✅ Already in use |
| `benchstat` (golang.org/x/perf) | Statistical comparison of benchmark results | ✅ **Standard**. Handles CI variance |
| `github.com/google/gops` | Profile collection for regression analysis | ❌ Overkill for CI gating |
| Custom `compare.go` | Budget enforcement against .benchmarks.yaml | ✅ **Must build** (120 lines) |

**Decision:** `benchstat` for comparison, custom budget reader for `.benchmarks.yaml`,
Go standard `testing.B` for execution. No new framework.

### 4.4 FIPS Build Base Image

| Base Image | FIPS Validation | Go Version | Availability |
|------------|-----------------|------------|-------------|
| `golang:1.24-fips-alpine` | Go FIPS module (in-progress NIST validation) | 1.24 | Docker Hub (official) |
| `registry.access.redhat.com/ubi9/go-toolset` | RHEL FIPS validated | 1.22 | RedHat registry, requires login |
| `golang:1.24` + `GOEXPERIMENT=systemcrypto` | Relies on host OS FIPS | 1.24 | Docker Hub (no FIPS guarantee) |
| **Recommendation** | ✅ `golang:1.24-fips-alpine` for CI, document UBI for production | | |

**Decision:** Dual strategy — CI uses `golang:1.24-fips-alpine` (fast, public);
production documentation recommends RedHat UBI for validated FIPS deployments.

### 4.5 PBKDF2 vs bcrypt

| Criteria | bcrypt (current) | PBKDF2-HMAC-SHA256 | Argon2id |
|----------|-----------------|-------------------|----------|
| FIPS 140-3 | ❌ Not certified | ✅ FIPS 198-1 | ❌ Not certified |
| Go standard library | ✅ `x/crypto/bcrypt` | ⚠️ `x/crypto/pbkdf2` + `crypto/sha256` (FIPS in systemcrypto mode) | ✅ `x/crypto/argon2` |
| Configurable cost | ✅ | ✅ | ✅ |
| Memory-hard | ❌ | ❌ | ✅ |
| **Recommendation** | Keep for non-FIPS | ✅ **Use for FIPS builds** | Consider for future non-FIPS |

**Decision:** Conditional at build time — bcrypt in non-FIPS builds, PBKDF2 in
FIPS builds. Argon2id is noted as a future upgrade path for non-FIPS builds but
is not recommended for FIPS until it achieves certification.
