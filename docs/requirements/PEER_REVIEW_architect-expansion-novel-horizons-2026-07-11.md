## 逐方向审查

### 方向一：身份编排 —— ✅ 结构合理，但 Consent 是隐藏前置依赖

**经过代码核验：** 正确。`handler.go:14` → `handleLogin` → `finishLogin` 链目前是**硬编码的**。`server_finish_login.go`（472 行）和 `server_login.go`（194 行）包含连续的 `if/switch` 块，没有任何可插入的 seam。可以通过一个中间件风格的钩子注册表将这些函数包装起来。

**⚠️ 关键发现——分析忽略了：** ROADMAP v5.0 方向①(a) 正确地识别出**Consent 记录存储根本不存在**（`ErrConsentRequired` 是已声明但未使用的死代码，`core/consts.go:383`，零调用方）。没有 ConsentStore，管线钩子用例的一半（“首次登录需要额外范围同意”、“撤销已授权应用”）是空谈。分析将方向一呈现为“零协议层侵入”，但它确实需要先构建 ConsentStore（这是一个**后端优先**的依赖项）。

**建议修正：**
1. 将**ConsentStore SPI** 从 ROADMAP 方向①(a) 的依赖项拉到方向一（A）的前置条件中——并明确注明这一点
2. 管线钩子（A）可以在没有 Consent 的情况下启动（900 行代码就可以运行），但声明式流程（B）在 Consent 基础设施构建之前不应启动

**工作量重新评估：** (A) ~400 行是合理的，但加上 (B) + ConsentStore，方向一的总工作量是 L→XL，而不是 L

---

### 方向二：API 安全产品化 —— ✅ 方向正确，但**低估了现有资产**

**经过代码核验：** 对能力的描述基本准确——本项目的确拥有 introspection、ext_authz、permissions 和 tokenusage 作为原始材料，用于构建 API 管理面。

**⚠️ 关键发现——开发者门户已存在：** 分析说“已有原料：`interfaces/web/developer/app.js`（DCR 注册）可扩展”——但实际代码库**进一步**：

```go
// interfaces/sso/sso_selfservice.go:414
func WithDeveloperPortalFS(developerFS fs.FS) Option
```

这个开发者门户 SPA 已通过 `pathDeveloperPortalPrefix = "/developer/"` 挂载，并可经由 `WithDeveloperPortalFS` 嵌入。近期提交`4c79fb82` 添加了“自助 DCR 注册 + 管理 SPA”。这意味着：

- **(B) API 密钥自助门户**：不是 500 行的工作量。而是**扩展**一个**已挂载的 SPA**，添加 API 密钥管理标签页。大约 150-200 行新前端代码 + 重用 DCR admin API。
- **(D) 范围市场**：可以通过开发者门户 UI 范围选择器的扩展而不是全新构建来实现。

**工作量重新评估：** 从 L（~1200 行总计）降至 M（~700 行），因为 ~40% 的底座组件已经存在。

**建议修正：** 重写范围 (B) 和 (D) 以利用现有的开发者门户 SPA。

---

### 方向三：AI 原生 IAM 运营 —— ✅ 存在有效，但为时过早

**经过代码核验：** 分析正确引用了所有组件：`audit/facets.go` 支持多维度聚合，`anomaly/` 具有可插拔检测器，`conditionalaccess/evaluate.go` 用于影响分析，`threataction/registry.go` 用于动作注册。

**⚠️ 战略问题——分析没有面对：** “为时过早”建议低估了一个挑战：**没有 LLM 可以可靠地将自然语言审计查询翻译成 `audit.Query` 而不会造成危险的误报**。审计查询空间的半结构化性质意味着模板匹配（分析中提到的贬义选项）在 90% 的用例中实际上更安全、更实用。分析应该反转优先级：先构建（D）身份图，因为**即使没有 AI，它也具有独立的运维价值**。

**建议修正：**
1. 将（D）身份图提升为主要交付物——它为管理员提供了**立即价值**（“谁可以访问什么，为什么？”）
2. 将（A）自然语言查询降级为“先构建接口，LLM 适配器稍后到来”——使用 `audit.Query` 的结构化查询构建器 UI 作为第一步，可选的自然语言层位于其上
3. 添加“无 LLM 降级”作为设计约束，允许代码路径**永远不要在生产中接触 OpenAI API**

**一个错过的机会：** 该分析没有提到 LLM 在代码生成循环中的使用——不是用于查询，而是用于**配置迁移**（例如，“这是一个 Okta 导出的 YAML——将其映射到 SSO 的配置格式”）。这更安全（人工审查 > 差异），并且是客户入职流程中的实际问题。

---

### 方向四：委托管理与治理 —— ✅ 最佳 ROI 候选，分析失误最少

**经过代码核验：** 这里的 claims 非常准确。当前的 admin 范围模型确实是二元的——“admin:read”和“admin:write”——没有租户级别的角色绑定（`interfaces/admin/middleware.go:29` → admin:read / admin:write 扩展是前一层的中介）。`Permissions` 通配符匹配器确实可以表达 `admin:read.tenant:{tid}/user:*`，但没有预定义的角色种子。

**⚠️ 次要发现：** 提及的“helpdesk”角色已经以**注释形式**存在于代码库中（`interfaces/admin/deps.go:66`, `interfaces/admin/users.go:16-193`）——helpdesk 用户的模式*部分实现*（密码重置、MFA 恢复、强制状态更改），但未绑定到正式的角色模型。这意味着 (A) 的一部分工作已经做了 40%。

**建议修正：** 将 (A) 的范围从“预定义角色种子”扩展到包括**审计现有 helpdesk 处理程序**以检查它们是否遵守 `admin:read.tenant:{tid}/user:password_reset` 而不是当前的无限制 `admin:write`。这是防止回归的增量审计。

---

### 方向五：多集群联邦 —— ❌ 结构合理但严重低估了现有基础设施

**经过代码核验：** 存在 `cluster/etcd`、`signingkeys/etcd`、`registry/etcd`、`sse/` 和 `caep/`。这些都是跨副本协作的原语。

**⚠️ 关键发现——SSOConfigDrift CRD + controller 已有：** 近期提交 `a635191d` 添加了“用于跨集群漂移的 SSOConfigDrift CRD + controller”。这意味着跨集群配置漂移检测**已经存在**——这与 (C) "全局条件访问策略冲突检测" 直接相关。

**⚠️ 关键发现——集群间通信层已有原语：** 分析说“`cluster/` 设计为单个 etcd 集群”——这是正确的，但未能注意到：
- MQTT 已经是一个嵌套模块（`mqtt/`）
- gRPC 已经是一个嵌套模块（`extauthz/` 使用 gRPC）
- 项目已经有 `sse/`（Server-Sent Events）用于跨副本事件流

这意味着**集群间通信层**不必从头开始构建；它可以使用 SSE 或 MQTT 进行多区域事件中继，重用现有模式。

**建议修正：**
1. 将 SSOConfigDrift CRD 添加到 (C) 的现有资产列表中
2. 将 (C) 从“全局条件访问策略”重新聚焦为“跨集群策略同步 + 漂移校正”（重用 CRD），使工作量从 500 行降至 ~200 行
3. 添加 MQTT/SSE 作为集群间通信的候选传输，而不是要求新的通信层

**隐私注意事项：** (A)“全局 subject 映射”中的分析“全局登录名”示例应更明确地提及**隐私法规**——GDPR 第 44 条有关数据传输的内容，以及 PIPL 在国内跨集群场景中的评估要求。如果隐私影响未提前纳入模型，这可能会成为合规障碍。

| ROADMAP v5.0 条目 | 与本文的关系 | 如果忽略 |
|---|---|---|
| ①(a) **ConsentStore SPI**（L，合规所需） | 方向一的前置依赖项 | 管线钩子在缺少 Consent 的情况下构建——范围扩展流程无法工作 |

## 架构警示：两个分析都遗漏了什么

除了这五个方向之外，从多个分析的交叉点中还浮现出一个架构级别的缺口：

### 出口连接器框架（Egress Connector Framework）

ROADMAP 和本文都假设外部服务集成（上游 IdP、CAEP webhook、通知通道、SMS、KMS）将作为未协调的适配器存在。缺少的是：

> 统一出口连接器框架，用于管理所有外部依赖的生命周期：健康检查、速率限制、熔断、重试策略、密钥轮换、配置热重载。

当前：`emailsmtp` 有自己的连接池，`oidc_federation` 有自己的 HTTP 客户端，`caep/` 推送 webhook 使用裸 `http.Post`。

应有的：一个 `connector` 抽象（由 `WithEgressConnector(name, opts)` 配置），位于所有外部出站调用之下，提供：
- 统一的健康检查（`GET /readyz?connector=okta-prod`）
- 统一的速率限制（每个连接器的令牌桶）
- 统一的密钥轮换（所有连接器共享的 mTLS 证书轮换）
- 统一的熔断（出站故障不会阻塞认证路径）

**为什么重要：** 本项目的 5 个方向中的 3 个（编排 → SSO 连接器调用，通知 → SMPT/SMS，CAEP → webhook 出口）增加出站连接器——如果没有框架，每个方向都独立解决速率限制、证书轮换和健康检查。这会造成技术债务并降低运营可见性。

**这不是一个独立方向**——而是一个**横切面架构最佳实践**，在实现任何出口密集型方向之前应该先建立。

## 关于范围定义的最终建议

| 教训 | 编码方式 |
|---|---|
| 始终与 ROADMAP 最新状态核对 | 一些 ROADMAP 项目（TrustedProxies）在编码时已实现 |
| 在声明“不存在”之前先 grep | 开发者门户、helpdesk 桩代码、SSOConfigDrift CRD 已存在 |
| 识别跨方向依赖关系 | ConsentStore 是编排的前置依赖项 |
| 避免假设“前端 = 从头开始构建” | 现有的 SPA（开发者门户、admin console）可以扩展而不是替换 |
| 在引入新的有状态依赖项之前先构建出口框架 | 否则方向一部署的每个部分都会重新发明连接器管理 |

---

**总结：** 这份分析是`snaplink/sso`扩展方向前十的周详分析。经过代码核验的三个修正建议最为关键：绘制 ConsentStore 前置依赖关系的映射、利用现有的开发者门户 SPA，以及在投入多集群联邦方向之前盘点现有的 CRD/MQTT 资产。方向建议保持不变，但 P3（多集群联邦）的工作量估计需要向上修正，P2（API 安全）需要向下修正。
