## 五个扩展方向

---

### 方向 1：身份验证与信任锚定（KYC/KYB/IAL）

**当前状态**: ⬜ 完全不存在

平台能够*认证*用户（验证密码、Passkey、SAML 断言等），但没有任何能力*验证用户的真实身份*。没有政府 ID 扫描、活体检测、地址验证、制裁筛查或身份保证等级（IAL）。

**为什么需要这个方向**:

1. **受监管市场的要求** — 金融科技、医疗保健、加密货币、合法赌博和零工经济平台需要 KYC/KYB 才能运营。目前，该平台可以为这些行业执行 SSO，但无法满足其基本的准入合规要求。
2. **身份保证等级（IAL）** — NIST SP 800-63 定义了 IAL1（自断言）、IAL2（远程验证）和 IAL3（当面验证）。拥有 IAL 框架可将平台从"登录工具"转变为"受信任的身份提供商"，能够承载更高的信任事务。
3. **直接收入增长** — KYC/KYB 验证通常按每次验证收费，代表着一个新的收入来源，而其核心授权基础设施几乎不需要更改。
4. **竞争对手差异化** — Auth0、Okta 和微软通过合作伙伴提供身份验证，但将该功能作为平台内的一等功能，可以创造出明显的竞争优势。

**高层面组件**:
- 文件验证引擎（护照、驾照等政府 ID 的处理 + OCR + 防伪检查）
- 活体检测集成（通过 SPI 实现供应商中立）
- 制裁 / PEP / 不利媒体筛选（API 驱动的检查）
- 地址验证（基于信用机构或公用事业数据）
- 身份保证等级（IAL）框架 — 等级评估 + 审计跟踪 + 令牌声明
- 验证工作流引擎 — 异步审查 + 升级 + 超时 + 重新验证
- 企业验证流程（KYB — 公司注册文件、实益所有人、UBO 声明）

### 方向 2：隐私同意管理平台（CMP）

**当前状态**: ⬜ 完全不存在

现有的"同意"基础设施是**OAuth 授权同意**（"Alice 允许 App X 代表她行事"），而非**隐私法规同意**（"Alice 同意出于目的 Y 处理她的个人数据"）。没有 IAB 透明与同意框架（TCF）、全球隐私平台（GPP）、CCPA 退出销售信号或按目的划分的同意管理。

**为什么需要这个方向**:

1. **隐私法规正在从合规负担转变为平台机会** — GDPR、CCPA/CPRA、LGPD 和新兴法规强制要求在共享个人数据之前获得同意。能够生成、存储和同步同意信号的平台对于广告技术、零售、Martech 和数据分析用例至关重要。
2. **同意是 SSO 的自然扩展** — 身份平台已经知道用户是谁、他们访问哪些应用程序以及处理哪些数据。添加同意管理层，可以让平台成为整个数据生态系统的"策略执行点"。
3. **IAB TCF 已成为广告技术标准** — 任何涉及程序化广告的客户都需要 TCF 同意字符串。没有此功能的 SSO 平台将他们推向补充解决方案。
4. **数据主体请求（DSR）自动化** — 虽然平台已有 GDPR 导出/擦除功能，但缺乏同意管理使 DSR 工作流不完整：用户行使"撤回同意"的权利应自动传播到所有下游处理器。

**高层面组件**:
- 同意信号生成器（TCF v2.2 字符串、GPP 字符串、US 州特定信号）
- 按目的划分的同意偏好存储（目的 1-10、特殊功能、供应商限制）
- CMP 小部件集成 API — 用于显示同意弹窗的标准端点
- 同意生命周期管理 — 注册、刷新、撤回、过期
- 同意审计跟踪 — 谁、何时、什么目的、什么供应商
- DSR 工作流集成 — 同意撤回 → 自动化下游通知
- 数据处理记录（GDPR 第 30 条） — 自动生成
- 同意信号同步 — 跨设备/浏览器同步一致信号

### 方向 3：身份治理与分析（IGA）

**当前状态**: ⚠️ 部分存在（威胁检测 + 响应），但完全缺少治理与分析层

现有能力：
- ✅ 异常检测（登录异常、不可能旅行、暴力破解检测）
- ✅ 令牌异常检测（地理速度、速率峰值）
- ✅ 威胁行动引擎（会话暂停、令牌族吊销）
- ✅ 审计管道（完整的事件溯源）

缺失能力：
- ❌ 访问认证/审查活动（谁拥有什么 + 他们应该拥有吗）
- ❌ 身份健康评分（按用户/组织汇总风险）
- ❌ 权限提升路径检测（服务账户过度权限、特权用户休眠）
- ❌ 跨账户行为关联（同一个用户在多个租户/应用中的行为）
- ❌ 僵尸/孤立账户检测（从未使用的账户、从未使用的凭证）
- ❌ 身份安全仪表盘（单一窗格俯瞰身份攻击面）

**为什么需要这个方向**:

1. **合规要求访问审查** — SOC2、SOX、PCI DSS 和 ISO 27001 要求定期认证"谁有权访问什么"。没有 IGA，平台无法证明合规性。
2. **身份安全正在成为增长最快的网络安全类别** — CrowdStrike、微软和 Okta 都在大力投资身份威胁检测与响应（ITDR）。平台已经拥有检测和响应能力；添加治理层可以完成"检测 → 分析 → 响应 → 证明"的循环。
3. **安全团队的基础设施需求** — 安全运营中心（SOC）需要一个集中的身份安全仪表盘。在没有 IGA 的情况下，他们将平台仅视为"登录工具"，并单独购买身份安全产品。
4. **货币化机会** — IGA 通常作为高级附加组件定价。身份分析仪表盘是面向 CIO/CISO 的销售演示中最引人注目的功能。

**高层面组件**:
- 访问认证活动引擎 — 创建活动、分配审阅者、聚合权利、跟踪响应
- 身份分析管道 — 访问聚合、使用基线、异常评分
- 安全仪表盘 — 身份攻击面评分、顶级风险实体、趋势、异常热图
- 权限提升路径检测 — 图分析：谁可以通过组合角色/组成员身份实现什么
- 服务账户治理 — 检测未使用的 API 客户端、过度权限、从不轮换的密钥
- 跨账户关联引擎 — 将同一用户在不同租户/应用中的行为关联起来
- 报告与导出 — 合规报告（访问审查结果、SoD 违规、权限漂移）

### 方向 4：企业组织生命周期自动化

**当前状态**: ⚠️ 部分存在（扁平组织成员），完全缺少层级结构

现有能力：
- ✅ 租户成员资格（成员/管理员/访客角色）
- ✅ 租户成员增删查改接口（TenantUserStore）
- ✅ 组织邀请（B2B 邀请令牌）
- ✅ 委托管理（组织管理员）

缺失能力：
- ❌ 组织层级树（父组织 → 子组织 → 部门 → 团队）
- ❌ 策略继承（父组织策略自动级联到子组织）
- ❌ 组织生命周期自动化（并购预配置、业务单元停用）
- ❌ 基于组织的合规聚合（子组织风险汇总到父组织）
- ❌ 委托管理扩展到每个层级（部门管理员、团队审计员）
- ❌ 组织范围的 SCIM 配置（跨所有子组织的自动配置）
- ❌ 基于组织的权利管理（许可证分配、功能标志继承）

**为什么需要这个方向**:

1. **大型组织的复杂性** — 拥有 50000+ 名员工的企业具有复杂的层级结构（控股公司 → 子公司 → 部门 → 团队）。扁平的租户模型对此无效。每个并购事件都需要跨多个组织的协调入职。
2. **策略继承是扩展的关键** — 手动将相同的安全策略配置到 50 个不同组织是不可行的。继承使管理员能够在根级别设置 MFA 要求或条件访问策略，并自动将其应用于每个子组织。
3. **合规聚合** — CISO 需要跨整个企业查看身份合规态势，而不仅仅是每个单独的组织。层级聚合使这成为可能，而无需自定义数据管道。
4. **并购工作流** — 组织生命周期中的最大痛点。自动化并购预配置（在关闭当天创建组织 + 配置身份提供者 + 设置 SCIM + 应用基线策略）对于企业销售交易至关重要。

**高层面组件**:
- 组织层级树模型 — 带有 ParentOrgID、路径、深度的有向无环图
- 策略继承引擎 — 策略在组织树中级联、合并和覆盖
- 组织生命周期状态机 — 预配置/活跃/冻结/归档/已删除，具有每个状态的自动化操作
- 并购工作流模块 — 批量用户迁移、身份提供者联合、合规基线应用
- 跨组织 SCIM 配置 — 单个 SCIM 基座 → 过滤到多个子组织
- 层级委托管理 — 在每个层级具有范围权限的角色（组织管理员、部门管理员、团队审计员）
- 合规聚合管道 — 每个组织身份健康的向上汇总之和

### 方向 5：开发者体验平台（完整 DX）

**当前状态**: ⚠️ 部分存在（基础 DCR 门户 + SDK 生成），但远非"就绪平台"

现有能力：
- ✅ 基本 DCR 管理 UI（9.9KB JS SPA）
- ✅ SDK 代码生成（Python + TypeScript，针对核心 OAuth 操作）
- ✅ API 文档查看器（嵌入式 OpenAPI 浏览器）
- ✅ MCP 服务器（AI 工具集成）

缺失能力：
- ❌ 交互式 API 资源管理器/游乐场（带有实时令牌的内置 Try-It）
- ❌ Webhook 事件模拟器 + 调试器（发送测试事件 + 查看交付日志 + 重试失败）
- ❌ 实时事件流查看器（基于 SSE 的审计事件调试器）
- ❌ API 密钥和凭据管理 UI（非 OAuth 客户端的长寿命 API 密钥）
- ❌ SDK 游乐场/代码示例（每种语言的浏览器内示例）
- ❌ 速率限制和使用分析仪表盘（每个客户端的调用量 + 限制命中）
- ❌ 应用程序健康/状态监控（已注册客户端的运行状况检查 + 最后活动时间）
- ❌ Webhook 端点测试 + 签名验证工具

**为什么需要这个方向**:

1. **开发者采用是关键增长杠杆** — 开发者选择 SSO 提供商的方式是尝试 API。交互式游乐场将集成时间从数天缩短到数分钟。Auth0 和 Clerk 的强大开发者体验是其增长的核心。
2. **Webhook 可观察性是企业要求** — 在 2026 年，没有 webhook 调试器的 SSO 平台是不完整的。开发者在集成期间花费最多时间调试 webhook 问题（错误负载、丢失事件、签名错误）。
3. **从 SSO 转变为"开发者身份平台"** — 通过添加 API 密钥管理、使用分析和应用程序监控，该平台从"登录 SDK 提供商"发展成为"开发者身份平台"——与应用基础设施的粘性要高得多。
4. **支持 AI 原生集成** — MCP 服务器是第一步。完整的开发者平台可以提供 AI 代理身份管理、AI  API 网关策略和 AI 使用监控，这与 AI 开发现场产生共鸣。
5. **减少支持负担** — webhook 调试器、API 游乐场和 SDK 游乐场直接减少了"集成为何失败？"类别的支持工单。

**高层面组件**:
- API 游乐场 — 基于浏览器的 OAuth 流程执行器，带有实时令牌检查器、请求/响应查看器、CURL/代码片段的复制
- Webhook 调试控制台 — 事件模拟器（选择事件类型 + 发送测试负载）、交付日志（每次尝试 + 响应代码 + 延迟）、失败重试、签名验证助手
- 实时事件流查看器 — 通过 SSE 连接到审计管道，显示实时事件，按类型/租户/用户过滤
- API 密钥管理 — 生成/轮换/撤销长寿命 API 密钥，用于非 OAuth 服务器到服务器集成
- SDK 游乐场 — 每种支持语言的浏览器内代码编辑器 + 针对沙盒服务器的执行
- 使用分析仪表盘 — 每个客户端/端点的速率限制命中计数、令牌使用趋势、错误率
- 应用程序健康中心 — 已注册客户端的运行状况检查状态、证书过期警告、最后活动时间戳
- 集成教程 + 模板 — 预构建的集成流程（React/Next.js + Django + Express + iOS + Android），带有可复制代码

## 与技术战略的关系

所有五个方向都坚持项目的核心架构原则：

- **分层架构**: 每个新功能将按照 `protocols/`（编排） → `domains/`（业务逻辑） → `shared/`（核心接口） → `infrastructure/`（实现）进行分层。
- **标准驱动**: 在所有适用情况下，新功能应遵循已建立的 RFC/IETF/NIST 标准（IAL 的 NIST 800-63，同意的 IAB TCF v2.2/GPP）。
- **SPI + 默认实现**: 每个新抽象 = 接口 + 内存实现 + 可选 SQLite/Postgres/Redis 实现。
- **Oracle-Leak 安全**: 验证端点必须遵循项目的反枚举模式（统一 404、恒定时间比较、虚拟哈希成本）。
- **故障模式**: 记录为故障开放（审计失败、风险评分器）或故障关闭（签名验证、信任链）以匹配项目的已建立策略。
- **无 emoji、无 TODO、无而我还在这里**: 遵循已建立的编码实践。
