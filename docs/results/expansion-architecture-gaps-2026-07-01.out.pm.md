## 2. 用户故事

### 2.1 方向一：多步 TOCTOU 防护

#### US-1: 停用用户无法完成多步认证

> **作为** 安全管理员，
> **我希望** 在管理员通过 SCIM 或管理 API 停用或删除用户后，该用户任何进行中的多步认证会话立即失效，
> **以便** 确保访问撤销在数秒（而非数分钟）内生效，通过 SOC 2 / ISO 27001 合规审计。

**验收标准：**

- Given 用户已完成登录步骤但处于 MFA 步骤，且管理员在此时停用该用户
- When 用户完成 MFA 挑战并提交
- Then 系统拒绝请求，返回通用的 `mfa_invalid`（不透露是账户被停用），并记录安全审计事件

- Given 用户已完成 MFA 但处于 Consent 步骤，且管理员在此时撤销了用户的关键 scope 权限
- When 用户提交 Consent
- Then 系统拒绝请求，要求用户重新开始授权流程

- Given 用户已获得 Authorization Code 但尚未交换 Token，且管理员在此时停用了该用户
- When 用户提交 Authorization Code 到 `/token`
- Then 系统拒绝请求，返回 `invalid_grant`（不透露具体原因）

#### US-2: 密码重置后旧会话不可用

> **作为** 最终用户，
> **我希望** 如果我重置了密码，任何在该密码重置前开始的登录流程（使用旧密码认证的）都应自动中止，
> **以便** 确保旧密码不会被利用来获取新令牌。

**验收标准：**

- Given 用户使用旧密码完成了登录步骤，但尚未完成 MFA
- When 用户在另一个设备上重置了密码
- Then 原登录流程在 MFA 提交时失败，提示需要重新登录

---

### 2.2 方向二：跨协议身份关联

#### US-3: 同一用户的不同登录方式自动关联

> **作为** 最终用户，
> **我希望** 我使用不同方式（Google OIDC、密码+邮箱、Passkey）登录时，系统能识别我是同一人，
> **以便** 我不需要记住"我用哪个 IdP 注册的"，且我的权限、数据、历史在所有登录方式下保持一致。

**验收标准：**

- Given 用户已有一个密码+邮箱注册的账户（邮箱 alice@example.com）
- When 用户首次使用 Google OIDC 登录（同样使用 alice@example.com 邮箱）
- Then 系统自动关联两个身份到同一用户账户（如果配置为自动模式）
- Or 系统提示用户"检测到已有账户，是否关联？"（如果配置为手动模式）

- Given 用户关联了两个身份
- When 用户使用任一身份登录成功
- Then 系统返回统一的用户 ID 和一致的权限/数据

- Given 用户仅有一个活跃的登录方式
- When 用户尝试删除这唯一的登录方式
- Then 系统拒绝操作，提示"至少保留一个登录方式"

#### US-4: 管理员管理用户身份关联

> **作为** B2B 联邦管理员，
> **我希望** 在管理 API 和管理界面中查看和合并重复用户账户，
> **以便** 在 SCIM 供给与自注册产生冲突时，我可以手动合并重复账户，而非要求用户重新注册。

**验收标准：**

- Given 两个用户记录 `user:alice`（密码，邮箱 alice@acme.com）和 `user:alice-saml`（SAML，邮箱 alice@acme.com）
- When 管理员在 Admin UI 中查询两个用户的关联并执行合并
- Then 合并后两个身份的认证均指向同一用户 ID
- Then 两个账户的权限/角色合并为并集
- Then 审计日志记录合并操作的时间、操作人、参与合并的用户

---

### 2.3 方向三：多维全局限流

#### US-5: Tenant 级公平资源分配

> **作为** SRE / 平台运维，
> **我希望** 为每个 Tenant 独立配置令牌签发速率配额，
> **以便** 一个 Tenant 的突发流量不会影响其他所有 Tenant 的合法用户。

**验收标准：**

- Given 部署上有 Tenant A（高流量移动 APP）和 Tenant B（低流量企业应用）
- When Tenant A 的某个 Client 发送大量请求触发其 Tenant 级配额上限
- Then 仅 Tenant A 的请求受限（返回 429），Tenant B 的请求不受影响
- Then 限流事件记录到审计日志，包含 tenant_id 和触发原因

- Given 运维配置了 `admin:*` scope 的签发配额为 100/小时
- When 某 Client 在 1 小时内签发了超过 100 个包含 `admin:*` 的令牌
- Then 额外请求被限流，返回 429

### 2.4 方向四：Admin Console 产品化

#### US-6: 安全管理员通过 UI 创建和管理 OAuth Client

> **作为** 运维工程师，
> **我希望** 在 Admin Console 中能够创建、编辑、删除 OAuth 2.0 Client，以及轮换 Client Secret，
> **以便** 我无需使用 `curl` 或 CLI 工具完成日常管理操作，降低操作门槛和误操作风险。

**验收标准：**

- Given 运维登录到 Admin Console（通过 OAuth 2.0 Authorization Code + PKCE）
- When 运维导航到 Clients 管理页面
- Then 展示 Client 列表（名称、ID、类型、创建日期、状态、操作按钮）
- Given 运维点击"创建 Client"
- When 填写 Client 信息（名称、类型、Redirect URIs、Grant Types）
- Then 提交后系统创建 Client 并展示 Client Secret（一次性展示）
- Then 审计日志记录创建事件

- Given 运维查看某 Client 详情
- When 点击"轮换 Secret"
- Then 系统生成新 Secret 并展示（旧 Secret 在配置的宽限期内仍有效或立即作废）
- Then 审计日志记录 Secret 轮换事件

#### US-7: 安全管理员通过 UI 管理 Tenant

> **作为** 安全管理员，
> **我希望** 在 Admin Console 中能够创建和挂起 Tenant，
> **以便** 在新客户上线时快速创建隔离环境，在客户欠费或被攻击时及时暂停服务。

**验收标准：**

- Given 安全管理员在 Admin Console 的 Tenant 管理页面
- When 创建一个新 Tenant（填写名称、域名、管理员邮箱）
- Then 系统创建 Tenant 并返回 Tenant ID
- Then 新 Tenant 默认处于活跃状态
- Then 审计日志记录创建事件

- Given 一个活跃的 Tenant
- When 管理员将 Tenant 状态设为"挂起"
- Then 该 Tenant 下所有活跃 session 立即失效
- Then 新登录请求返回 403 `tenant_suspended`
- Then 审计日志记录挂起事件及影响用户数
- When 管理员将 Tenant 恢复为"活跃"
- Then 该 Tenant 恢复正常服务

#### US-8: Admin Console 的"Dogfood"认证

> **作为** 企业采购评估者（POC），
> **我希望** Admin Console 通过标准的 OAuth 2.0 流程进行认证，而不是手动粘贴 Bearer Token，
> **以便** 我能够直观体验产品的完整安全模型，而不是感觉在使用一个"技术原型"。

**验收标准：**

- Given POC 评估者首次访问 Admin Console
- When 点击"登录"按钮
- Then 跳转到 SSO 的内置登录页面进行身份认证（支持密码 / OIDC IdP）
- Then 认证通过后通过 Authorization Code + PKCE 流程获取 `admin:read` 和 `admin:write` scope
- Then 管理会话在 session 中维护，无需再次输入 token
- Then session 过期后自动跳转到登录页

- Given 评估者关闭浏览器标签页后重新打开
- When 回到 Admin Console
- Then 如果 session 有效，自动恢复（无需重新登录）
- Then 如果 session 过期，重定向到登录页

### 2.5 方向五：SDK 嵌入体验

#### US-9: 嵌入开发者快速上手生产级集成

> **作为** 平台开发者，
> **我希望** 有一个完整的 "15 分钟起步" 嵌入示例，包含 SQLite 存储、健康端点、优雅关闭和信号处理，
> **以便** 我可以在一个下午内完成从"读文档"到"生产环境运行"的集成，而不是花一周时间拼凑各个组件。

**验收标准：**

- Given 开发者阅读 `docs/embedding-guide.md`
- When 按指南操作，复制示例代码并运行
- Then `go run main.go` 启动一个可用的 SSO 服务
- Then 服务包含 `/livez`、`/readyz` 健康端点
- Then 服务在 `SIGTERM` 信号下在 30 秒内优雅关闭
- Then 数据持久化到 SQLite 文件
- Then 整个过程耗时不超过 15 分钟（按指南步骤）

#### US-10: 嵌入开发者仅需实现自己需要的 Deps 子集

> **作为** 嵌入开发者，
> **我希望** 我不需要实现 `Deps` 接口的全部 ~50 个方法，而只需要实现我需要的部分（如存储 + 令牌签发），
> **以便** 最小嵌入场景的代码量可以从 ~200 行的脚手架降低到 ~50 行。

**验收标准：**

- Given 开发者只需要自定义用户存储和令牌签发
- When 实现 `UserProviderDeps` 和 `TokenIssuerDeps`（而非完整的 `Deps`）
- Then `NewServer` 接受分段组合的接口
- Then 未提供的部分使用 SDK 提供的默认实现（内存存储 / 默认签发器）
- Then 编译通过，运行时无 panic 或 nil pointer dereference
- Then 与完整 `Deps` 实现的功能一致（在配置能力范围内）

## 3. 边界场景分析

### 3.1 方向一：TOCTOU 边界场景

| 边界场景 | 风险描述 | 防护策略 | 优先级 |
|----------|---------|---------|--------|
| **并发 TOCTOU** | 用户状态在 hash 计算和验证之间又发生了变化（极度竞争） | 使用原子比较+交换；hash 不一致时要求重认证（非阻塞） | 高 |
| **时间窗口精度** | UserStateHash 的更新频率——实时 vs 批量 | hash 在每次用户状态变更时立即更新（不异步批处理）；同步操作推迟到 hash 更新完成 | 高 |
| **Session 跨设备撤销** | 用户在设备 A 上登录中，在设备 B 上撤销了会话 | 多步流程中每一步检查当前 session 是否仍有效 | 高 |
| **批量 SCIM 导入冲突** | SCIM 批量导入 10,000 用户，同时多个用户在进行 MFA | 每个 MFA 完成时重新验证用户状态（非批量操作） | 中 |
| **租户级状态变化** | 整个租户被挂起时，租户内进行中的认证步骤全部需要失效 | 在租户级别加入 hash，resumeState 携带 tenantVersionHash | 高 |
| **灰度部署期间** | 如果 TOCTOU 防护分阶段部署，旧代码不验证 hash，新代码验证 | 功能开关控制；部署期间新代码检测到 hash 不存在时视为"第一次版本化"而非失败 | 中 |

### 3.2 方向二：身份关联边界场景

| 边界场景 | 风险描述 | 防护策略 | 优先级 |
|----------|---------|---------|--------|
| **邮箱地址变更** | 用户邮箱变更后，自动关联策略会错误地将旧邮箱与新账户关联 | 关联策略应基于 Provider + ExternalID 的组合（不依赖邮箱）或双向确认 | 高 |
| **合并后的权限冲突** | 两个账户有不同的角色/权限，合并后产生预期外的权限集合 | 合并策略使用并集（Union），并有操作回滚机制 | 高 |
| **合并后解关联** | 用户关联后希望解除其中一个登录方式的关联 | 保留解除关联后每个身份的基本权限，但重新计算用户权限集；解关联前至少保留一个登录方式 | 高 |
| **OIDC 子账户变更** | Google 或 Microsoft 可能因隐私策略变化更换用户的 sub 声明值 | IdentityLink 应关联 provider + sub 的组合，并支持管理员手动修复 | 中 |
| **合并在撤销窗口** | 管理员将用户 A 合并到用户 B，然后有人使用用户 A 的旧凭证登录 | 合并后用户 A 的旧凭证应失效或重新指向用户 B | 高 |
| **并发合并** | 两个管理员同时对同一个用户的不同副本执行合并 | 使用乐观锁版本号；冲突时后者失败，提示重新加载 | 中 |

### 3.3 方向三：多维限流边界场景

| 边界场景 | 风险描述 | 防护策略 | 优先级 |
|----------|---------|---------|--------|
| **分布式限流一致性** | 多副本部署下，每个副本的本地 token bucket 状态不一致导致限流波动 | 推荐近似限流（每个副本独立的 token bucket，burst 允许超出双倍）；精确限流使用 etcd 或 Redis | 中 |
| **限流键选取顺序** | 多个维度同时触发（IP + Client + Tenant），内部优先级决定先拒绝哪个 | 固定优先级链：User > Client > Tenant > IP（先在最佳粒度拒绝，减少误杀） | 高 |
| **限流与 quota 的区别** | 短期限流（每秒）vs 长期配额（每天 Token 签发上限）混为一谈 | 清晰区分两类：令牌桶（短时限流）和配额计数器（配额重置周期） | 高 |
| **限流绕过风险** | 攻击者通过修改 client_id 请求头或使用多个 IP 绕过 per-client 和 per-IP 限流 | Per-User 维度作为兜底（认证用户谁在频繁操作）；匿名操作走单独的匿名限流池 | 高 |
| **配额接近上限的通知** | 用户接近配额基数时无预警直接返回 429 | 在配额达到 80% / 90% / 100% 时发出告警（日志+可配置的 Webhook） | 中 |
| **动态降级 vs 关闭服务** | 过载时优先拒绝低价值操作而非一刀切 | 限流系统区分操作优先级；高级别 scope（admin:*）的配额优先于低级别（openid） | 低 |

### 3.4 方向四：Admin Console 边界场景

| 边界场景 | 风险描述 | 防护策略 | 优先级 |
|----------|---------|---------|--------|
| **Admin Console 的 XSS 防护** | 使用 sessionStorage 存储 bearer token → 若 Admin Console 有 XSS 漏洞，攻击者可窃取高权限 token | 使用 HttpOnly Cookie + 后端 session（非 Bearer Token 前端存储） | 高 |
| **Admin Console 的权限控制** | 不同管理员需要不同的管理 scope（如只读审计员 vs 全权操作员） | 在 OAuth 2.0 流程中协商 scope 级别：`admin:read`（只读）vs `admin:write`（读写） | 高 |
| **Client Secret 轮换的宽限期** | 轮换 Secret 后，旧 Secret 在短时间内可能被缓存 | 轮换时支持并行窗口（旧 Secret 在 5 分钟内仍可用，或在轮换时立即作废） | 高 |
| **删除 Client 的连锁效应** | 删除一个 Client 会导致所有使用此 Client 的应用立即无法工作 | 删除前提示影响范围（活跃 Token 数、关联的 Tenant）；支持先停用 (Deactivate)→ 观察 → 再删除 | 高 |
| **Admin Console 的多语言** | 企业采购后可能需要 Admin Console 支持多语言（日文、德文等） | 建议架构支持 i18n 动态加载；MVP 阶段仅英文 | 低 |
| **Admin Console 的 Accessibility** | 企业采购要求符合 WCAG 2.1 AA 标准 | 在重构时使用语义化 HTML + ARIA 标签；MVP 阶段仅关注基本键盘导航 | 中 |

### 3.5 方向五：SDK 嵌入边界场景

| 边界场景 | 风险描述 | 防护策略 | 优先级 |
|----------|---------|---------|--------|
| **Deps 分段组合的 nil 检查** | 嵌入者实现部分 Deps 但漏了某些微妙的子接口 → 运行时 nil pointer dereference | `NewServer` 在构造时做完整检查：所有必需的依赖在构造阶段必须提供；可选的提供默认实现 | 高 |
| **版本兼容性声明** | 嵌入者使用 v1.x SDK 开发，升级到 v2.x 后发现 Deps 接口签名变化 | 使用 Go 的接口兼容性模式；Breaking changes 在 major version 升级时明确标注；提供 codemod 工具或迁移指南 | 高 |
| **默认实现的安全影响** | 嵌入者未提供自定义 JWT 签名密钥，使用内存默认 Ed25519 密钥
→ 重启后密钥丢失，已签发的 ID Token 无法验证 | 构造时 Warning："Warning: using ephemeral Ed25519 key. Tokens will be invalid after restart."
嵌入指南中突出说明"第一步：配置持久化密钥" | 中 |
| **嵌入 VS 独立部署的文档桥接** | 嵌入者先使用独立部署（sso-ctl）测试，然后切换为 Go SDK 嵌入 | 提供部署模式对比表和迁移路径：独立部署 → 远程 ssoclient → 本地 ssoclient → 完全嵌入 | 中 |
| **大规模嵌入下的资源使用** | 嵌入者将 SSO 嵌入到一个高吞吐量应用（如 API 网关服务）中，内存存储造成 GC 压力 | 在 embedding guide 中注明内存存储的适用场景和限制（原型/低流量/非持久化），生产场景推荐 SQLite | 中 |

### 6.2 MVP 范围定义（v2.1 - 第一个可交付版本）

**MVP 目标**：消除安全红线和产品印象短板，建立面向未来扩展的基础架构。

**包含：**
1. ✅ TOCTOU 多步状态防护（全部 3 个 ResumeState + authCodeValidate 完整覆盖）

- ❌ 身份关联自动关联 hook（Sprint B）

### 6.5 回滚策略
