# 产品经理分析报告：SSO 服务器数据后端能力建设

## 1. 需求梳理

### 1.1 核心用户群体

| 用户角色 | 代表画像 | 核心诉求 |
|---------|---------|---------|
| **平台运维工程师** | 管理 3-5 个生产集群，负责日常运维和故障恢复 | 数据不丢、可恢复、运维命令可审计、后端统一 |
| **后端开发工程师** | 负责业务系统对接 SSO，涉及租户管理和权限模型 | 清晰的 API 契约、一致的错误语义、易于本地调试 |
| **安全合规团队** | 负责 SOC2 / ISO 27001 / GDPR 合规审计 | 撤销持久化、审计日志链、数据擦除可验证 |
| **系统架构师** | 做技术选型，决策基础设施栈 | 部署模型灵活（单 DB / Redis HA / 多 Region） |
| **SaaS 平台负责人** | 多租户场景，需要隔离和数据独立 | 租户级操作、批量能力、数据不串 |

### 1.2 使用场景矩阵

| 场景 | 用户 | 频率 | 影响面 |
|------|------|-----|-------|
| 用户登录/授权码交换 | 终端用户（日均百万级） | 高 | 入口体验 |
| Token 刷新/续期 | 移动端/SPA 客户端 | 高 | 用户体验连续性 |
| Token 撤销（用户注销） | 终端用户/运维 | 中 | 安全关键 |
| 客户端注册/管理 | 开发者/运维 | 低 | 功能完整 |
| 租户配置/数据清理 | 运维/合规 | 低 | 合规关键 |
| 集群节点故障恢复 | 运维 | 低 | 可用性关键 |
| 安全事件响应（批量撤销） | 安全团队 | 极低 | 安全关键 |
| 跨区域数据隔离 | 多 Region 部署 | 低 | 合规关键 |

### 1.3 关键功能需求提炼

**Must-have（从产品角度）：**

1. **Token 撤销持久化** — 用户主动注销或安全事件触发撤销后，即使服务重启，撤销状态不可丢失
2. **Session 管理** — 用户可以在多设备上登录/登出，查看活跃会话，管理员可批量清退租户会话
3. **刷新令牌轮换** — 每次刷新后旧令牌失效，令牌被重用（reuse）时整族失效（安全红线）
4. **PKCE 强制** — 授权码流程必须验证 Code Challenge
5. **时钟安全** — Token 过期判断不依赖单机墙钟（避免 NTP 回拨导致安全问题）
6. **Token 内省自省** — 资源服务器可查询 token 活跃状态

**Should-have：**

7. **集群一致性** — 多副本部署时撤销、密钥轮换、客户端变更同步到所有节点
8. **Postgres 统一后端** — 降低运维复杂度，避免同时维护 Redis + SQLite 两种技术栈
9. **审计日志链** — 操作可追溯、不可篡改
10. **CAEP/SSF 安全事件推送** — 实时通知下游系统 token 已失效

**Could-have：**

11. **Device Code 流** — 命令行/无浏览器设备的 OAuth 登录
12. **CIBA（后端发起认证）** — 无需用户交互的设备端场景
13. **SCIM 用户同步** — 企业目录自动同步
14. **FAPI 安全加固** — 金融级安全要求

## 2. 用户故事

### 2.1 Token 撤销持久化

**用户故事 A — 安全响应**

> **作为** 安全运维工程师，
> **我希望** 当收到安全事件的 token 撤销请求后，服务重启不影响撤销状态，
> **以便** 确保泄露的 token 在架构故障后仍然失效。

**验收标准：**
- Given 集群中任意 token 已被撤销（已落盘持久化）
- When 集群所有节点全部重启
- Then 该 token 的 `/introspect` 返回 `{"active": false}`
- And 该 token 的授权码再次用于 `/token` 返回 `invalid_grant`

**用户故事 B — 用户注销**

> **作为** 终端用户，
> **我希望** 在任何设备上注销登录后，所有使用该 token 的请求立即失效，
> **以便** 确保我的账号安全，即使密码尚未修改。

**验收标准：**
- Given 用户已在 3 台设备上登录
- When 用户在设备 A 上点击"注销"
- Then 设备 A 的 token 立即失效
- And 设备 B、C 的 token 仍有效（单设备注销不波及）

### 2.2 Session 管理

**用户故事 C — 管理员批量清退**

> **作为** 租户管理员，
> **我希望** 当检测到某租户被入侵后，能一键清退该租户下的所有活跃会话，
> **以便** 在密码强制重置之前阻止攻击者继续使用已有会话。

**验收标准：**
- Given 租户 T 下有 200 个活跃用户，共 500 个会话
- When 管理员调用 `DELETE /admin/tenants/{id}/sessions`
- Then 返回 200 OK（异步执行）
- And 5 秒内租户 T 下所有会话的 token 在内省时返回 `active: false`
- And 其他租户不受影响

**用户故事 D — 用户查看会话**

> **作为** 普通用户，
> **我希望** 能查看自己的所有活跃会话（设备、登录时间、IP），并能远程下线特定设备，
> **以便** 在手机丢失或怀疑异常登录时可以主动控制。

**验收标准：**
- Given 用户在手机、家里电脑、公司电脑共 3 个会话
- When 用户访问"安全设置 → 管理设备"
- Then 显示 3 个会话及其信息（设备类型、最近活动时间、IP 归属地）
- When 用户选择"下线公司电脑"
- Then 该设备会话立即失效
- And 手机和家里电脑会话不受影响

### 2.3 刷新令牌轮换安全

**用户故事 E — Token 盗窃检测**

> **作为** 安全架构师，
> **我希望** 一旦刷新令牌被泄露并同时被攻击者和合法用户使用，整族 token 都失效，
> **以便** 限制被盗 token 的破坏窗口，迫使双方重新认证。

**验收标准：**
- Given 用户 Alice 的刷新令牌被攻击者窃取
- When Alice 的客户端正常执行刷新
- And 攻击者在相同 refresh family 上也执行刷新（重用）
- Then 整族 refresh token 被标记为已撤销
- And Alice 和攻击者的下次刷新都返回 `invalid_grant`
- And Alice 被要求重新登录（非静默刷新）

### 2.4 时钟安全

**用户故事 F — NTP 事故防御**

> **作为** 运维工程师，
> **我希望** 即使 NTP 服务故障导致某节点时钟回拨 1 小时，
> **以便** 已签发的 token 不会突然拥有"额外 1 小时有效期"，已过期的 token 不会突然变"有效"。

**验收标准：**
- Given 集群节点 A 的墙钟因 NTP 事故回拨 60 分钟
- When 一个原本已过期 30 分钟的刷新令牌在该节点上尝试刷新
- Then 节点 A 拒绝该请求（返回 `invalid_grant`）
- And 节点 A 签发的新的 token 使用单调时钟计算过期

### 2.5 集群一致性（跨副本撤销同步）

**用户故事 G — 多节点一致性**

> **作为** 平台架构师，
> **我希望** 在 3 副本部署下，任意一个副本收到 token 撤销请求后，其他 2 个副本也能感知，
> **以便** 无需配置 sticky session 或集中式 token 校验代理，架构更简洁。

**验收标准：**
- Given 集群有 3 个节点（N1, N2, N3），前端负载均衡轮询
- When N1 收到 token T 的撤销请求（`/revoke`）
- Then N2 和 N3 在等 2 秒后对 T 的内省返回 `active: false`
- And N1 返回 200 OK 给客户端（同步返回，不等待其它副本确认）
- And 网络分区修复后，分区期间发生的撤销在分区修复后 10 秒内同步

## 3. 边界场景分析

### 3.1 异常输入与错误处理

| 场景 | 当前行为 | 产品期望 | 风险等级 |
|------|---------|---------|---------|
| 重复撤销同一 token | 返回 200（幂等） | ✅ 正确 — 不应泄露 token 是否存在 | 低 |
| 撤销不存在的 token | 返回 200 | ✅ 正确（Oracle-leak 防护） | 低 |
| 刷新已失效的 refresh token | 返回 `invalid_grant` | ✅ 正确 | 低 |
| 并发刷新同一 refresh token（正常双提交） | 第一次成功，第二次返回 `invalid_grant` | ✅ 正确，但需引导客户端正确处理 | 中 |
| 管理员误操作批量清退 | 无撤销确认机制 | ❌ 需增加"二次确认"或"撤销窗口" | **高** |
| 部分节点写入撤销后崩溃，数据未持久化 | 尚未持久化 → 重启后恢复 | ❌ 需保证写入 quorum 后才返回（或至少落盘） | **高** |
| 撤销请求中 token 格式无效 | 返回 400/401 | 需统一为 `invalid_token` | 低 |

### 3.2 并发与竞态条件

| 场景 | 可能影响 | 当前策略 | 产品评估 |
|------|---------|---------|---------|
| 同一 refresh family 在多线程并发刷新 | 两请求都成功，family 未轮换 | SQLite: `DELETE RETURNING` 原子操作 ✅ | 安全 |
| 撤销请求与 token 使用同时到达 | 可能短暂有效 | 最终一致性（集群模式下） | 可接受，≤ 窗口期 |
| 密钥轮换与 token 签发同时进行 | 可能用旧密钥签发 | Leaderless 聚合 + overlap window ✅ | 安全 |
| 租户批量清退与用户新建会话同时 | 新建会话可能被误清退 | 需确认时序 | 需明确边界 |
| 集群分裂（split-brain）期间撤销 | 分区恢复后需 merge | etcd 自愈机制 ✅ | 安全 |

### 3.3 性能瓶颈场景

| 场景 | 预期负载 | 当前瓶颈预判 | 建议 |
|------|---------|------------|------|
| /token 端点（授权码交换） | 1000+ TPS | AuthCode 存储读写 | Postgres 索引优化/Redis 热路径 |
| /introspect 端点 | 5000+ TPS | 撤销集合查询 | 引入本地缓存 + 集群失效广播 |
| 刷新令牌轮换 | 2000+ TPS | RefreshToken 原子删除+写入 | SQLite WAL 模式/Redis pipeline |
| 批量租户清退 | 低频（月/季度） | 会话表全扫描 | 需要 TenantID 索引 |
| 同时大量设备注销（下班高峰） | 500 TPS 撤销 | 撤销写入为主 | 批量异步写入 + 读取实时 |

### 3.4 安全与权限边界

| 场景 | 风险描述 | 当前防护 | 改进建议 |
|------|---------|---------|---------|
| 跨租户内省 | 租户 A 的 token 可能被租户 B 的资源服务器验证 | 按租户隔离待确认 | 内省端点需检查调用方租户 scope |
| 批量清退 API 未授权 | 攻击者清退所有会话 | admin:write scope + 401 Bearer | 需增加操作审计 + 通知 |
| 撤销回调泄露 token 存在性 | 攻击者可枚举 token 是否有效 | 统一的 `invalid_token` ✅ | 保持此策略不变 |
| 集群内事件总线未认证 | 恶意节点注入撤销事件 | etcd 内置认证 | 需在生产环境启用 mTLS |

### 3.5 配置与部署场景

| 场景 | 当前支持 | 缺口 |
|------|---------|------|
| 单节点内存部署（测试/开发） | ✅ memory provider | 无 |
| 单节点 SQLite 部署（小团队） | ✅ SQLite | 无 |
| 多节点 Redis 部署（标准 HA） | ✅ Redis（6/6 hot stores） | 无 |
| 全 Postgres 部署（统一技术栈） | ❌ 仅 Session 完成 | 缺少 6 个 hot store 实现 |
| 混合部署（Postgres + Redis） | 需手动配置 | 缺少文档和最佳实践 |
| 多 Region 部署 | ✅ Session 按 tenant 隔离 | 其他 hot store 未验证多 Region |

## 4. 功能优先级（MoSCoW）

### Must Have（缺了就不能上线）

| 功能 | 依赖 | 优先级原因 |
|------|------|-----------|
| Token 撤销持久化 | `RevocationStore` 接口 + SQLite | 用户注销后服务重启不可恢复 → 安全红线 |
| Session 管理（完整） | Postgres Session 已完成 | 多设备管理、租户清退、用户自助下线 |
| 刷新令牌轮换安全 | RefreshTokenStore 原子操作 | 阻止 token 泄露后的横向移动 |
| PKCE + 单调时钟 | `time.Now()` 替换为单调时钟 | 防止 NTP 回拨导致 authz 绕过 |
| `invalid_grant` 统一错误 | Oracle-leak 防护 | 攻击者无法枚举有效 token |

### Should Have（重要，可稍晚上线）

| 功能 | 现状 | 价值 |
|------|------|------|
| 集群撤销同步（etcd） | 已实现 | HA 部署架构的必要条件 |
| Postgres 统一后端（6 hot stores） | **缺口**（见 §6） | 降低运维复杂度，单一技术栈 |
| 审计日志链 | 已有框架 | 合规审计必备 |
| 租户级隔离 + 数据残留 | 已有 SPI | GDPR/CCPA 合规 |

### Could Have（锦上添花）

| 功能 | 实现成本 | 用户价值 |
|------|---------|---------|
| Device Code 流 | 中（需 Postgres 后端） | CLI/IoT 设备登录，增量用户场景 |
| CIBA 后端认证 | 中 | 智能电视/自助终端，利基场景 |
| 用户自助查看活跃会话 | 低（前端工作） | 提升用户安全感，减少客服工单 |
| CAEP/SSF 事件推送 | 高（需 receiver 端支持） | 企业级安全事件实时联动 |

### Won't Have（本期不实现）

| 功能 | 原因 |
|------|------|
| SCIM 用户同步 | 需企业目录对接，超出当前 MVP |
| FAPI 2.0 加固 | 金融级需求，可后续独立发布 |
| WebAuthn / Passwordless | 新的认证流程，需单独 feature |
| 国际化（i18n） | 不影响功能正确性，可后续追加 |

## 6. 发布策略

### 6.1 MVP 范围定义

**Phase 0 — 最小安全加固（已有，建议 1 周内加固文档后发布）**

```
范围：
  ✅ Token 撤销持久化（RevocationStore + SQLite）
  ✅ 单调时钟保护
  ✅ Session 管理（含 Postgres 后端）
  ✅ 集群撤销同步（etcd）

交付物：
  - 升级 Migration 脚本
  - SQLite 自动迁移
  - 文档更新（撤销语义说明）
```

**Phase 1 — Postgres 统一后端（建议 4-6 周）**

```
范围：
  - AuthCodeStore Postgres 实现
  - RefreshTokenStore Postgres 实现
  - PARStore Postgres 实现
  - DeviceCodeStore Postgres 实现
  - CIBAStore Postgres 实现
  - JTIReplayStore Postgres 实现

依赖：Session Postgres 的参考实现模式
交付物：
  - 6 个实现 + 每个 ≥ 6 个测试用例
  - Postgres 迁移文件（CREATE TABLE + 索引）
  - 配置指南（单一 PostgreSQL 连接字符串即可运行）
```

**Phase 2 — 会话自助管理（建议 7-8 周）**

```
范围：
  - 用户查看活跃会话 API
  - 下线指定设备 API
  - 管理员租户清退 API（已有，补充确认）
  - 审计日志链公开接口

依赖：Phase 1 Postgres 后端
交付物：
  - Frontend 组件（可选，或仅提供 API）
  - 管理后台 UI 对接文档
```

### 6.2 灰度发布计划

| 阶段 | 受众 | 验证点 | 回滚条件 |
|------|------|-------|---------|
| Stage 0: 内部测试 | 开发团队 + QA | 所有测试通过、压力测试 ≥ 2000 TPS | 任何 P0 缺陷 |
| Stage 1: 尝鲜用户 | 2-3 个低流量租户 | 3 天无撤销丢失、性能基线达标 | P1 以上缺陷或性能退化 |
| Stage 2: 扩展 | 20% 租户 | 1 周稳定运行 | 撤销持久化验证失败 |
| Stage 3: 全量 | 100% 租户 | 2 周稳定 | — |

**关键风险控制点：**
- **Stage 0 → 1**：需人工模拟集群重启，验证撤销持久化
- **Stage 1 → 2**：需验证 Postgres 和 Redis 混合部署不冲突
- **Stage 2 → 3**：需完成向后兼容性回归（不升级的旧 client 不受影响）

### 6.3 回滚策略

**场景一：性能退化（如 /token P99 > 200ms）**

```
回滚步骤：
  1. 灰度分阶段切回旧版本（逆序）
  2. Postgres hot store 切回 Redis（配置开关）
  3. 旧版本在 Quorum 启动后接管流量
  4. 数据一致性检查：回滚期间产生的新撤销、新 token 不会丢失
```

**场景二：数据迁移问题（如建表失败）**

```
回滚步骤：
  1. 使用最后已知完好的备份恢复
  2. 迁移脚本设计为向前兼容（不删除旧表/旧字段）
  3. 新版本发现迁移失败 → 自动回退到旧版 schema
  4. 运维收到告警消息，可人工决定重试
```

**场景三：安全性问题（如 Oracle-leak 回归）**

```
回滚步骤：
  1. 立即停止部署（保留现场用于取证）
  2.回滚代码 commit（git revert）
  3. 非必要不修复 hotfix → 走正常发布流程
  4. 安全委员会事后 review
```

### 6.4 Feature Flag 设计

| Feature Flag | 默认值 | 适用阶段 | 说明 |
|-------------|--------|---------|------|
| `postgres_hot_stores.enabled` | `false` | Phase 0→1 | 启用 Postgres 作为 hot store 后端，false 用 Redis |
| `audit_log_chain.enabled` | `false` | Phase 2 | 启用审计日志链完整性校验（哈希链） |
| `bulk_session_delete.confirm` | `true` | Phase 1 | 租户批量清退需管理员二次确认 |
| `user_session_list.enabled` | `false` | Phase 2 | 用户自助查看活跃会话功能 |
| `session_meta_collection` | `true` | 始终 | 是否收集会话设备信息用于展示（不影响安全） |

**设计原则：**
- 所有 Flag 默认关闭，按需开启
- 每个 Flag 可按租户粒度控制（`config.PerTenant`）
- 运行时变更后不需要重启（热加载）
- Flag 的默认值在下次 Major release 更新为 true，然后废弃旧 Flag
