# 产品经理分析：SSO 平台五大扩展方向

> 分析基准：`docs/senior-architect-expansion-2026-07-02.md` + 核验评估 `docs/senior-architect-expansion-2026-07-02.out.md`
>
> 视角：从用户需求、商业价值、产品体验出发

---

## 1. 需求梳理

### 1.1 核心用户群体与使用场景

| 用户角色 | 描述 | 痛点 | 涉及方向 |
|---------|------|------|---------|
| **平台运维者 (Platform Ops)** | 管理 SSO 集群的 SRE/运维团队 | Admin API 缺乏治理，多集群配置靠人工同步，无操作审计，变更即风险 | 方向三、方向五 |
| **租户管理员 (Tenant Admin)** | 各组织的系统管理员 | 无法与外部协作方安全共享资源，认证流固化无法定制，缺乏运维透明度 | 方向一、方向二 |
| **资源服务所有者 (RS Owner)** | 后端服务/API 开发者 | 不知道自己的 token 生态什么样——多少活跃用户、哪些 scope、有无异常 | 方向四 |
| **最终用户 (End User)** | 登录应用的普通员工 | 认证流程可能过于繁琐（全局 MFA 一刀切）或过弱 | 方向二（间接） |
| **业务决策者 (Biz Decision Maker)** | 采购 RFP 决策人 / 合规负责人 | SOC2 合规要求、B2B 协作能力是 RFP 必问项、运维审计缺失 | 方向一、方向三 |

### 1.2 核心功能需求（按方向）

#### 方向三：Admin 治理框架（P0）
```
痛点故事：运维人员发现 admin API 没有操作确认——"昨天有人误删了一个生产环境的 client，我们现在才意识到。"

核心需求：
├── R3.1 敏感操作二次确认（DELETE / 关键 PUT 需要 reason + confirm）
├── R3.2 写操作配额（每个租户每 N 分钟最多创建 X 个 client）
├── R3.3 并发编辑冲突检测（两人同时编辑同一 client）
├── R3.4 操作原因审计日志（所有写操作记录 who/what/why/when）
├── R3.5 管理 IP 白名单 / 地理锁定
└── R3.6 变更审批工作流（创建→待审批→激活）
```

#### 方向四：RS Token 智能平台（P0.5）
```
痛点故事：后端服务开发者想知道"我的服务今天有多少活跃用户？最近 token 使用量异常增长？"

核心需求：
├── R4.1 Token 聚合统计（活跃用户数、token 分布、scope 排行）
├── R4.2 过期预警（未来 N 小时内过期的 token 数量）
├── R4.3 异常活动检测（同一 token 多 IP 使用、高频刷新）
├── R4.4 使用趋势（日/周/月签发量、验证量、撤销量）
└── R4.5 Token 事件订阅（实时推送状态变化）
```

#### 方向五：多集群 GitOps 配置治理（P1）
```
痛点故事：平台运维者管理 prod-us / prod-eu / staging 三套集群，配置经常不同步，
不小心修了 prod-us 忘了 prod-eu。

核心需求：
├── R5.1 声明式配置定义（K8s CRD / YAML）
├── R5.2 跨集群配置一致性检测与漂移自动修复
├── R5.3 GitOps 流程（git push → 集群自动同步）
├── R5.4 灰度配置发布（蓝绿 / 金丝雀）
├── R5.5 配置变更可视化与影响分析
└── R5.6 一键配置回滚
```

#### 方向一：跨租户 B2B 协作（P2）
```
痛点故事：Org A 需要与供应商 Org B 共享一个内部应用，但 SSO 是竖井式的——每个公司员工需另注册账号。

核心需求：
├── R1.1 外部用户（Guest User）生命周期管理（邀请→激活→过期→撤销）
├── R1.2 跨租户 Token 交换（Org A token → Org B 资源）
├── R1.3 租户间信任关系管理（连接配置）
├── R1.4 Guest 角色权限模型（默认只读，可自定义）
├── R1.5 跨租户审计线索关联
└── R1.6 外部用户自助门户（查看自己跨租户访问情况）
```

#### 方向二：条件认证策略引擎（P2）
```
痛点故事：安全团队需要"管理员登录敏感应用时必须 WebAuthn，普通员工登录内部 wiki 跳过 MFA"，
但现有认证流是线性固定的，无法按条件分支。

核心需求：
├── R2.1 认证流 DSL（YAML 定义条件分支认证流程）
├── R2.2 条件表达式引擎（基于风险评分、设备信誉、地理位置等）
├── R2.3 认证节点库（现有认证器包装为可组合节点）
├── R2.4 Webhook 集成（外部系统回调）
└── R2.5 Fallback 策略（条件不匹配时的默认路径）
```

### 1.3 Must-have vs Nice-to-have

| 方向 | Must-have（MVP） | Nice-to-have（V2） |
|------|-----------------|-------------------|
| 方向三 | R3.1 敏感操作确认 + R3.2 写配额 + R3.4 操作审计 | R3.3 冲突检测 + R3.5 IP 白名单 + R3.6 审批工作流 |
| 方向四 | R4.1 Token 聚合统计 + R4.3 异常检测 | R4.2 过期预警 + R4.4 趋势 + R4.5 事件订阅 |
| 方向五 | R5.1 声明式配置 + R5.2 一致性检测 + R5.6 回滚 | R5.3 GitOps + R5.4 灰度发布 + R5.5 影响分析 |
| 方向一 | R1.1 Guest 邀请 + R1.3 信任关系 + R1.4 角色模型 | R1.2 Token 交换 + R1.5 审计关联 + R1.6 自助门户 |
| 方向二 | R2.1 DSL 解析 + R2.3 节点库 + R2.5 Fallback | R2.2 高级表达式 + R2.4 Webhook |

## 2. 用户故事

### 方向三：Admin 治理框架

**用户故事 3.1——敏感操作确认**

- **作为** 平台运维管理员，**我希望** 执行 DELETE client 等危险操作时需二次确认，**以便** 避免误操作导致生产事故。

- **验收标准**：
  - Given 管理员在 admin 控制台点击"删除 client X"
  - When 系统弹出确认对话框，要求填写操作原因
  - Then 管理员必须输入 `reason` 和输入确认字符串（如 client ID）方可执行删除
  - And 操作记录包含操作原因、操作时间、操作人 IP

**用户故事 3.2——写操作配额**

- **作为** 平台运维管理员，**我希望** 对每个租户设置写操作配额，**以便** 防止恶意/误配置批量创建 client 耗尽资源。

- **验收标准**：
  - Given 租户 A 在 1 小时内已创建 10 个 client（配额阈值）
  - When 租户 A 管理员再次尝试创建 client
  - Then 系统返回 `429 Too Many Requests` 并提示配额重置时间
  - And 审计日志记录此次被拦截的尝试

**用户故事 3.3——操作审计日志**

- **作为** 合规负责人，**我希望** 所有 admin API 的写操作都有完整的审计日志（who/what/why/when/old/new），**以便** 通过 SOC2 审计。

- **验收标准**：
  - Given 管理员修改了 client X 的 redirect_uris
  - When 合规负责人查看审计日志
  - Then 审计记录包含：操作人、操作时间、旧值、新值、填写的原因
  - And 审计日志不可篡改（hash chain）

### 方向四：RS Token 智能平台

**用户故事 4.1——Token 聚合统计**

- **作为** 后端服务 Owner，**我希望** 查看我的服务有多少活跃用户和活跃 token，**以便** 了解我的服务的使用规模和健康度。

- **验收标准**：
  - Given 后端服务使用 client_id `my-service` 进行认证
  - When 服务 Owner 调用 `TokenStats("my-service")`
  - Then 返回：active_user_count、active_token_count、top_5_scopes、avg_token_ttl
  - And 响应时间 < 200ms

**用户故事 4.2——异常活动检测**

- **作为** 安全运维人员，**我希望** 收到同一 token 在多个 IP 地址使用的告警，**以便** 及时识别 token 泄露事件。

- **验收标准**：
  - Given 用户 A 的 token 在正常 IP 使用
  - When 同一 token 在 10 分钟内从 3 个不同地理区域被使用
  - Then 系统触发异常告警并在 Token 控制台标记
  - And 告警推送到配置的 Webhook

**用户故事 4.3——Token 事件订阅**

- **作为** 后端服务 Owner，**我希望** 实时订阅 token 进出活性状态的事件，**以便** 在我的服务内实现精细的访问控制。

- **验收标准**：
  - Given 后端服务已注册 token 事件订阅
  - When 某个用户的 token 过期/被撤销/刷新
  - Then 系统实时推送事件到服务的注册端点
  - And 事件包含 token_id、event_type、timestamp

### 方向五：多集群 GitOps 配置治理

**用户故事 5.1——跨集群配置一致性**

- **作为** 平台 SRE，**我希望** 自动检测 prod-us 和 prod-eu 集群的配置差异，**以便** 避免因配置漂移导致的用户行为不一致。

- **验收标准**：
  - Given prod-us 和 prod-eu 配置原一致
  - When prod-us 的某个 tenant 配置被直接修改（非 GitOps）
  - Then 系统在 5 分钟内检测到漂移并发出告警
  - And 自动尝试回滚到 Git 声明状态（可配置）

**用户故事 5.2——GitOps 配置同步**

- **作为** 平台 SRE，**我希望** 通过 git push 更新集群配置，**以便** 所有配置变更可审计、可回滚、可代码审查。

- **验收标准**：
  - Given 开发者修改了 `config/prod-us.yaml` 并 push 到 main 分支
  - When CI/CD 流程完成 schema 验证
  - Then Config Controller 检测到 CRD 变更并将配置同步到 prod-us 集群
  - And 配置变更记录在审计日志中

### 方向一：跨租户 B2B 协作

**用户故事 1.1——Guest 用户邀请**

- **作为** Org A 的租户管理员，**我希望** 邀请 Org B 的员工作为 guest 用户访问我的内部应用，**以便** 与供应商协作不需要对方另注册账号。

- **验收标准**：
  - Given Org A 管理员在控制台选择"邀请外部用户"
  - When 输入 partner@org-b.com 并选择角色 "project-viewer"
  - Then 系统生成一次性邀请链接（48h TTL）发送至 partner@org-b.com
  - And Org B 用户通过链接确认后，使用自己公司 SSO 即可访问 Org A 的应用
  - And 访问权限仅限 scope: `read:project`，不可越权

**用户故事 1.2——Guest 访问撤销**

- **作为** Org A 的租户管理员，**我希望** 立即撤销某个 guest 用户的访问权限，**以便** 当协作关系结束时确保数据安全。

- **验收标准**：
  - Given Org A 有一个活跃的 guest 用户来自 Org B
  - When 管理员在控制台撤销该 guest 的访问
  - Then 该 guest 在 60 秒内无法再访问 Org A 的任何资源
  - And 所有该 guest 的活跃 token 被立即撤销
  - And 审计日志记录撤销操作及原因

### 方向二：条件认证策略引擎

**用户故事 2.1——条件 MFA**

- **作为** 安全管理员，**我希望** 配置"管理员从新设备登录敏感应用时需要 WebAuthn MFA"，**以便** 在生产力和安全性之间取得平衡。

- **验收标准**：
  - Given 安全管理员定义了一条策略：`role=admin AND app=sensitive_app AND device=new → require webauthn`
  - When 管理员 Alice 从新设备登录 sensitive_app
  - Then 认证流程走密码校验 → 设备检测 → WebAuthn 挑战
  - And 同样的 Alice 从已知设备登录内部 wiki 则跳过 MFA
  - And 策略可在不重启服务的情况下动态生效

**用户故事 2.2——Fallback 策略**

- **作为** 最终用户，**我希望** 当我的首选认证方式不可用时（如 TOTP 应用不可用）有备用方法，**以便** 不因单点故障而无法登录。

- **验收标准**：
  - Given 用户配置了 TOTP 作为 MFA 方法
  - When TOTP 连续 3 次验证失败
  - Then 系统提示可用的备用认证方法（如短信验证码或恢复码）
  - And 备用验证成功后标记此事件为"降级认证"记录审计

## 3. 边界场景分析

### 3.1 方向三：Admin 治理

| 边界场景 | 风险等级 | 产品处理策略 |
|---------|---------|------------|
| 管理员误操作后要求撤销 | 🔴 高 | 方向三 MVP 不提供操作回滚（V2 特性），但敏感操作确认 + 操作审计已足够：误删可追责可恢复（通过备份或 `bootstrap` snapshot）。需在 UI 引导"删除前确认影响范围" |
| 多个管理员同时编辑同一 client | 🟡 中 | MVP 使用 optimistic locking（版本号），冲突时"后提交者看到冲突提示并手动合并"。不引入分布式锁（过度工程） |
| 管理员权限提升自保（root admin 不可被配额限制） | 🟡 中 | 超级管理员（break-glass 角色）可绕过配额和 IP 白名单，但所有突破操作记录为 `elevated_action` 审计事件 |
| 写配额阈值与合法 burst 冲突 | 🟢 低 | 配额使用 token bucket 算法，允许短时 burst。默认值通过运营数据校准（观察现有租户创建频率 P99） |

### 3.2 方向四：RS Token 智能

| 边界场景 | 风险等级 | 产品处理策略 |
|---------|---------|------------|
| RS 错误解读异常检测告警（误报导致过度反应） | 🟡 中 | 异常检测输出**建议性**标签（`suspicious`/`normal`/`review_recommended`），不自动执行任何安全动作。RS Owner 自主决策 |
| Token 统计延迟（最终一致性） | 🟢 低 | 聚合数据为近实时（~1 分钟延迟），标注 `last_updated_at` 时间戳。Token 事件订阅保证实时性 |
| 大量 RS 同时拉取统计导致 IdP 性能下降 | 🟡 中 | TokenStats API 引入缓存（TTL: 30s）。极端情况可通过方向三的速率限制保护 |
| RS 注册的 client_id 被恶意遍历 | 🟡 中 | TokenStats API 需要 API Key 或 mTLS 认证——不能仅凭 client_id 公开访问 |

### 3.3 方向五：多集群 GitOps

| 边界场景 | 风险等级 | 产品处理策略 |
|---------|---------|------------|
| Git 仓库被恶意篡改 → 配置被污染 | 🔴 高 | GitOps 流程中包含多签（GPG signed commits）和 schema 验证门禁。**错误配置不传播到集群**——验证失败即阻断 CI |
| 集群断开 Git 连接后手动修改配置（漂移） | 🟡 中 | 可配置漂移模式：`warn-only`（仅告警）、`auto-revert`（自动回滚）、`manual`（人工裁决）。默认 `warn-only` 避免自动回滚造成二次事故 |
| canary 发布中发现问题需要回滚 | 🟡 中 | canary 比例从 5%→10%→...→100%，每阶段观察 5 分钟。任何阶段可 "abort" → 自动回滚到上一个健康版本 |
| 多个团队同时修改同一配置 | 🟡 中 | CRD 级别的乐观锁 + Git merge conflict 是天然冲突检测机制——利用 Git 的优势而非重新发明轮子 |

### 3.4 方向一：B2B 协作

| 边界场景 | 风险等级 | 产品处理策略 |
|---------|---------|------------|
| 未收到邀请链接的用户声称被邀请（社会工程） | 🔴 高 | 所有邀请操作需管理员身份验证。邀请链接 payload 含 HMAC 签名，服务器验证签名后才接受，不可伪造 |
| Guest 用户的源身份变更（离职/改名） | 🟡 中 | 复用现有 CAEP 发射器——Org B 的 IdP 发出身份变更事件，Org A 接收后同步更新 guest 影子记录 |
| 邀请链接大量生成（DoS 攻击） | 🟡 中 | 每个租户有未消费邀请上限（默认 100），超出则 429。邀请 TTL 48h，减少无效记录的堆积 |
| Guest 用户在多个租户有身份（身份聚合） | 🟢 低 | MVP 不处理跨租户身份聚合——每个 guest 在宿主租户有独立影子记录。V2 引入全局身份 |
| 两个组织间信任关系破裂 | 🟡 中 | 信任关系可随时撤销（单方面）。撤销后该合作连接的所有 guest 自动失效 |

### 3.5 方向二：条件认证

| 边界场景 | 风险等级 | 产品处理策略 |
|---------|---------|------------|
| DSL 配置错误导致所有用户无法登录（lock-out） | 🔴 高 | 引擎编译阶段做**静态可达性分析**——验证所有路径最终导向 success 或 deny，没有死锁路径。配置加载失败回退到默认认证流 |
| 条件表达式无限递归或死循环 | 🔴 高 | DAG 执行引擎有最大节点数限制（默认 20 步）和超时（默认 10s），超出即降级为 deny |
| 外部 Webhook 超时 → 认证流程 hang | 🟡 中 | Webhook 节点有 timeout（默认 5s），超时后的降级行为可配置（`deny`/`allow`/`fallback_to_risk`） |
| 条件因子（风险评分/设备信誉）不可用 | 🟡 中 | 缺失的条件因子按"不满足条件"处理（安全优先）。策略可配置 `on_missing: "allow" | "deny"` |

## 4. 功能优先级（MoSCoW）

### 整体 MoSCoW 矩阵

| 分类 | 方向-功能 | 理由 |
|------|---------|------|
| **Must have** | 方向三：敏感操作确认 + 写配额 + 操作审计 | 安全底线，SOC2 合规必问项，快速见效 |
| **Must have** | 方向四 Phase 1：TokenStats 只读聚合 API | ~300 行投入，依赖全量在位，极高 ROI |
| **Must have** | 方向五：声明式配置 + 一致性检测 + 回滚 | 运维一致性基础，涨配置漂移是生产事故根源 |
| **Should have** | 方向三：并发冲突检测 + IP 白名单 | 重要但可延迟 1 sprint |
| **Should have** | 方向五：GitOps 原生集成 | 体验升级（PR review → auto sync），但 CI 流程已有基础 |
| **Should have** | 方向一：Guest 邀请 + 角色模型 | 产品 RFP 必问项，但 XL 工作量需专项立项 |
| **Could have** | 方向四：过期预警 + 事件订阅 | 增强体验但非核心需求 |

## 6. 发布策略

### 6.1 MVP 范围（Sprint 1-2 交付物）

| 交付物 | 形态 | 面向用户 | 依赖 |
|-------|------|---------|------|
| `DestructiveActionGuard` | API 中间件（自动生效） | 平台运维 | 无（纯新中间件） |
| `AdminWriteQuota` | API 中间件 + 配置项 | 平台运维 | `TenantQuotaStore`（已有） |
| `AdminAuditRecorder` | Audit Sink 扩展 | 合规 + 运维 | `audit.Recorder`（已有） |
| `TokenStats` API | gRPC + REST 读接口 | RS Owner | `TokenLister.ListActive`（已有） |
| `SuspiciousTokenActivity` API | gRPC + REST 读接口 | RS Owner + 安全 | `anomaly.Detector`（已有） |

**MVP 原则**：
- 所有 MVP 功能默认**向后兼容**——不需要现有用户更改任何配置
- 管理操作确认默认关闭（opt-in），避免破坏现有管理流程
- TokenStats API 新增独立 gRPC 服务，不影响现有认证路径

### 6.2 Feature Flag 设计

| Flag | 作用域 | 默认值 | 控制方式 | 对应功能 |
|------|-------|-------|---------|---------|
| `admin.destructive_action_guard` | 集群 | `false` | 配置/环境变量 | 敏感操作确认 |
| `admin.write_quota` | 集群 | `false` | 配置/环境变量 | 写操作配额 |
| `admin.audit_operation_reason` | 集群 | `true` | 配置/环境变量 | 操作原因审计 |
| `rs.token_stats` | 集群 | `true` | 配置/环境变量 | Token 统计 API |
| `rs.suspicious_activity` | 集群 | `false` | 配置/环境变量 | 异常活动检测 |
| `config.drift_detection` | 集群 | `false` | 配置/环境变量 | 配置一致性检测 |
| `b2b.guest_invitation` | 租户 | `false` | 租户配置 | Guest 邀请 |
| `b2b.cross_tenant_token_exchange` | 租户 | `false` | 租户配置 | 跨租户 Token 交换 |

**Feature Flag 发布流程**：
```
内测 (canary, 5% 集群, all flags off → manual on)
  → 公测 (beta, 20% 集群, opt-in enabled per request)
    → GA (100% 集群, default-on for non-breaking flags)
      → 移除 flag 代码（下一 major 版本）
```

### 6.3 灰度发布计划

| 阶段 | 范围 | 时间 | 监控指标 |
|------|------|------|---------|
| Alpha | 内部开发环境 + CI | Sprint 1 结束时 | 功能正确性、无回归 |
| Beta | 2-3 个友好客户 staging 环境 | Sprint 2 第 1 周 | API 响应时间、错误率、功能使用数据 |
| Canary | 5% 生产集群（非关键区域） | Sprint 2 第 2 周 | error budget、延迟变化、无 P0 事件 |
| Gradual Rollout | 25% → 50% → 75% → 100% | Sprint 2 第 3-4 周 | 关键指标（见 5.2）稳定 |
| GA | 100%，公告发布 | Sprint 3 发布日 | 功能采纳率追踪 |

### 6.4 回滚策略

| 层 | 回滚机制 | RTO | RPO |
|----|---------|-----|-----|
| **功能层** | Feature Flag 关闭 → 功能立即失效 | < 1min | 无 |
| **代码层** | 回退到上一个发布版本 | < 10min | 5min（配置变更） |
| **配置层** | Config Rollback 控制器恢复上一个健康配置 | < 5min | 3min（最后一次健康配置） |
| **数据层** | 审计日志不可回滚（append-only），但 Token 统计无状态可重建 | 无 | 无 |

**回滚决策树**：
```
发现生产问题
  → 是否与新增功能强相关？
    → Yes → 关闭 Feature Flag（最快恢复）
    → No / 不确定 → 回退二进制版本
  → 恢复后：
    → 问题可复现 → 修复后重新 canary
    → 问题不可复现 → 假设环境差异，增加监控后继续
```

### 6.5 各方向独立发布可行性

| 方向 | 可独立发布？ | 发布策略 | 影响范围 |
|------|------------|---------|---------|
| 方向三 | ✅ 可独立 | Feature Flag 粒度的渐进发布 | 仅 admin API 层 |
| 方向四 | ✅ 可独立 | 新增 gRPC 服务，无侵入 | 新增服务，不影响现有路径 |
| 方向五 | ⚠️ 需注意 | CRD 定义依赖 K8s 环境 | 无 K8s 的环境仅使用文件配置 |
| 方向一 | ⚠️ 需依赖 | 需要方向三的治理框架保护 admin API | Tenant + Auth 存储变更 |
| 方向二 | ❌ 不可独立 | 嵌入认证路径，需全面测试 | 核心认证流程，回滚最复杂 |
