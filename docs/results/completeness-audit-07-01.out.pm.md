## 2. 用户故事

### 2.1 RBAC 职责分离（F05）

**作为** 企业安全合规官，  
**我希望** 系统管理员和审计员角色不可分配给同一个用户，  
**以便** 通过 SOC 2 合规审计中的职责分离检查，避免一个人同时拥有"执行"和"审核"权限。

**验收标准**：

- **Given** 我有 `admin:write` 角色（排除 `auditor`）和 `auditor` 角色（排除 `admin:write`），已配置互斥规则
- **When** 我试图将用户 A 同时赋予 `admin:write` 和 `auditor` 角色
- **Then** 系统拒绝此分配，返回明确错误信息："角色 admin:write 与 auditor 互斥"

- **Given** 用户 A 只持有 `admin:write` 角色
- **When** 我试图将 `auditor` 角色附加给用户 A
- **Then** 系统拒绝，提示角色冲突

- **Given** 用户 A 持有 `admin:write` 且系统中不存在任何 `auditor` 角色分配
- **When** 管理员尝试将 `auditor` 角色配置为与 `admin:write` 互斥
- **Then** 配置成功，但已经持有这两个角色的用户 B 需要被提醒——要么解除其一，要么拒绝此配置变更

### 2.2 刷新令牌绝对过期上限（F03）

**作为** 企业安全官，  
**我希望** 刷新令牌有一个硬性绝对过期时间（例如 90 天），即使用户持续使用也无法超过此期限，  
**以便** 确保用户需要定期重新认证，满足合规审查对"长期会话"的风险管控要求。

**验收标准**：

- **Given** 系统配置 `refresh_token_max_lifetime: 90d`
- **When** 用户在第 1 天登录，签发 refresh token，之后每 15 天刷新一次
- **Then** 第 90 天之后的下一次刷新请求被拒绝，用户必须重新登录

- **Given** 系统未配置 `refresh_token_max_lifetime`
- **When** 管理员查看安全配置面板
- **Then** 面板显示警告："建议设置刷新令牌绝对过期时间以避免长期会话风险"

- **Given** 系统配置绝对上限 90 天，滑动窗口 30 天
- **When** 用户在第 85 天刷新令牌
- **Then** 新签发的 refresh token 的绝对过期时间仍为第 90 天（不延长），滑动窗口重置

### 2.3 授权码多账号切换（F01）

**作为** 企业应用开发者，  
**我希望** 在用户使用 SSO 登录时支持 `select_account` 提示，  
**以便** 使用多账号的企业用户（如客服同时操作个人账号和替班账号）能灵活选择登录身份，无需清除浏览器缓存或重新打开无痕窗口。

**验收标准**：

- **Given** 用户 A 在浏览器中已登录两个账号（user1@example.com, user2@example.com）
- **When** RP 请求认证且 `prompt=select_account`
- **Then** OP 展示账号选择页面，列出已登录的账号供选择

- **Given** 系统不支持 `select_account`
- **When** RP 请求认证且 `prompt=select_account`
- **Then** 系统按规范降级为 `prompt=login`（而非返回错误）

### 2.4 自省缓存惊群防护（F07）

**作为** SRE 运维工程师，  
**我希望** 令牌自省端点在高并发时使用 stale-while-revalidate 缓存策略，  
**以便** 在微服务网格中 1000 个并发请求同时到达时，不会因为自省缓存同时过期而形成"惊群效应"压垮数据库。

**验收标准**：

- **Given** 自省缓存 TTL=60s，stale-while-revalidate=30s
- **When** 第 61 秒收到 200 个并发自省请求
- **Then** 其中 199 个立即返回缓存中的过期值（仍合法），仅 1 个请求回源刷新缓存
- **And** 后续请求在缓存刷新后都返回新值

- **Given** 自省缓存超过 TTL+stale 窗口（如第 100 秒）
- **When** 收到自省请求
- **Then** 请求必须回源，不可返回陈旧数据

### 2.5 OIDC Discovery 声明一致性（F02）

**作为** 集成工程师，  
**我希望** Snaplink 的 `.well-known/openid-configuration` 文档中声明的能力与实际行为完全一致，  
**以便** 在技术选型和采购评审中，不会因为声明了 `claims_parameter_supported: true` 但实际不支持 `essential`/`value`/`values` 而被扣上"产品成熟度不足"的帽子。

**验收标准**：

- **Given** Discovery 文档声明 `claims_parameter_supported: true`
- **When** 客户端发送 `claims={"id_token":{"email":{"essential":true}}}`
- **Then** 如果 email 不可用，OP 返回认证失败（而非忽略 essential 标记）

- **Given** Discovery 文档因实际未实现而改为 `claims_parameter_supported: false`
- **When** 客户端读取文档
- **Then** 客户端知道该功能不可用，不会使用 claims 参数请求

### 2.6 按维度批量回收 Refresh Token（F04）

**作为** 平台运维/管理员，  
**我希望** 在员工离职、租户关闭或客户端密钥泄露时，能按用户/租户/客户端维度批量回收所有刷新令牌，  
**以便** 在安全事件发生时快速止损，无需逐条手动操作或等待自然过期。

**验收标准**：

- **Given** 员工张三已离职
- **When** 管理员在管理控制台选择"回收用户所有刷新令牌"
- **Then** 张三名下所有活跃的 refresh token 被立即撤销
- **And** 张三下一个刷新请求返回 `invalid_grant`

- **Given** 租户 AcmeCorp 已关闭
- **When** 触发租户关闭流程
- **Then** 系统自动回收该租户下所有用户和应用的刷新令牌

- **Given** 客户端 ID `myapp-backend` 的凭据疑似泄露
- **When** 管理员回收该客户端的刷新令牌
- **Then** 仅该客户端签发的 refresh token 被撤销，其他客户端不受影响

## 3. 边界场景分析

### 3.1 异常输入和错误处理

| 场景 | 功能入口 | 风险描述 | 当前处理 | 建议改进 |
|------|---------|---------|----------|---------|
| 使用过期 refresh token 刷新 | 刷新令牌轮换 | 应返回 `invalid_grant` | ✅ 返回 `invalid_grant` | 添加过期 token 的审计事件，区分"主动撤销"和"过期" |
| 刷新时 scope 缩减到原范围之外 | 刷新令牌轮换 | 不应扩展 scope | ✅ `ScopesSubsumed` 校验 | — |
| 自省时传入 DPoP token | 令牌自省 | 应返回 `token_type: DPoP` | ❌ 返回 `Bearer` | 修正为 `DPoP` |
| 自省过期且撤销的 token | 令牌自省 | 两种状态应区分 | ⚠️ 不确定先验签还是先查 store | 明确优先级策略，审计日志中增加状态标识 |
| Discovery 请求携带意外 accept 头 | OIDC Discovery | 应返回 JSON | ✅ 通常正确 | — |
| `select_account` 但只有一个账号 | 授权码流程 | 应直接重定向而非展示页面 | ❌ 未实现 | 单账号时自动重定向，零账号时降级为 `login` |
| 互斥角色配置循环依赖 | RBAC SSD | 如 A 排斥 B，B 排斥 A | ❌ 未实现（功能缺失） | 实现 DAG 检测，拒绝循环依赖 |

### 3.2 并发和竞态条件

| 场景 | 功能入口 | 风险描述 | 当前处理 | 建议改进 |
|------|---------|---------|----------|---------|
| 自省缓存惊群（TTL 过期瞬间 1000 并发） | 令牌自省 | DB 连接池被打满，请求超时 | ❌ 无防护 | 实现 stale-while-revalidate |
| 刷新令牌并发提交（窗口内 2 次） | 刷新令牌轮换 | 正常双提交应幂等 | ✅ `refresh_grace.go` | 已实现 |
| 刷新令牌并发提交（窗口外） | 刷新令牌轮换 | 应检测到家族重用并销毁 | ✅ `DeleteFamily` | — |
| 同时修改互斥角色配置和用户分配 | RBAC SSD | 读写冲突导致脏数据 | ❌ 功能缺失 | 使用 DB 事务，按角色 ID 加写锁 |
| 批量回收刷新令牌时新签发冲突 | 刷新令牌轮换 | 用户正在刷新时管理员回收 | ⚠️ 未明确 | 回收前验证，newer-than-revocation 的 token 保留 |

### 3.3 性能瓶颈场景

| 场景 | 功能入口 | 风险 | 当前防护 | 建议 |
|------|---------|------|---------|------|
| 自省端点高并发（Mesh 场景，每秒 10k 请求） | 令牌自省 | 频繁验签 + DB 查询 | 可选缓存 | 实现 stale-while-revalidate + 缓存分层（本地+L2） |
| Discovery 文档频繁获取 | OIDC Discovery | CDN 或客户端频繁拉取 | 响应小、可缓存 | 添加 `Cache-Control: public, max-age=3600` |
| 刷新令牌存储无限累积 | 刷新令牌轮换 | 过期 token 不清理，存储膨胀 | ❌ 无清理 | 定时任务清理过期 token + 分区删除 |
| 同时回收大量 token（全租户回收） | 刷新令牌轮换 | 百万级 DELETE 操作 | ❌ 无限制 | 分批/异步回收，添加进度反馈 |
| 角色分配频繁变更 | RBAC | 缓存一致性问题 | ❌ 需确认 | 事件驱动缓存失效 |

### 3.4 安全和权限边界

| 场景 | 功能入口 | 风险 | 当前处理 | 建议 |
|------|---------|------|---------|------|
| 攻击者试图利用自省端点枚举有效 token | 令牌自省 | 暴力枚举 | ✅ 不存在的 token 统一返回 `active:false` | — |
| 攻击者盗取授权码但无 PKCE verifier | 授权码流程 | 兑换失败 | ✅ `DELETE RETURNING` 防重放 | 可考虑添加 DPoP 双绑定 |
| 同时持有互斥角色的用户利用组合权限越权 | RBAC SSD | 组合权限跳过安全控制 | ❌ 无防护 | 实现 SSD + DSD |
| refresh token 在客户端泄露后无限使用 | 刷新令牌轮换 | 不受时限无限使用 | ❌ 无绝对过期上限 | 添加 `max_lifetime` |
| Discovery 文档泄露内部端点信息 | OIDC Discovery | 安全隐患最小，公开信息 | ✅ 应安全 | — |

### 3.5 配置和部署场景

| 场景 | 涉及功能 | 描述 | 建议 |
|------|---------|------|------|
| 新部署时默认策略 | RBAC SSD | 初始安装无互斥角色配置，后续启用 | 默认关闭，配置开启后不可回退为宽松模式（防止合规失效） |
| 从无绝对上限迁移到有绝对上限 | 刷新令牌轮换 | 已存在的 token 怎么处理？ | 迁移策略：① 绝对上限从迁移日起算 ② 对存量 token 统一设置 max_created_at |
| 灰度发布自省缓存改进 | 令牌自省 | 验证新旧行为一致 | 添加 `X-Introspection-Cache: hit/stale/miss` 响应头 |
| 多区域部署下 Discovery 文档 | OIDC Discovery | 不同区域 issuer 不同 | 确保每个部署实例的 discovery 正确反映本地端点 |
| 企业采购中声明能力与实际能力不符 | OIDC Discovery + 全部 | "过度承诺"风险 | 建立"声明-实现"自动化测试，每次发版自动验证 |

### 6.3 回滚策略

| 功能 | 回滚难度 | 回滚方式 | 注意事项 |
|------|---------|---------|---------|
| F05: SSD | **高** | 关闭 feature flag，但已建立的互斥角色配置保留在 DB 中不删除 | 如果回滚后有人利用窗口期绕过约束，合规风险已存在。建议 SSD 一旦启用就不可降级 |
| F03: 绝对过期上限 | **中** | 关闭配置，但已因达到上限而失效的 token 不可恢复 | 绝对过期是"不可逆"操作——用户需要重新登录。回滚后受影响用户不会自动恢复，需要重新认证 |
| F01: select_account | **低** | 关闭功能，降级为 `login` 行为 | 对 RP 透明，RFC 规范允许降级 |
| F08: DPoP token_type | **低** | 切回旧逻辑 | 恢复旧行为后依赖此字段的 RS 仍会用旧逻辑 |
| F02: Discovery 对齐 | **低** | 恢复旧声明 | 可能再次出现声明不一致，但无运行时破坏 |

**关键回滚原则**：
1. **F05 + F03 一旦开启不建议回滚**——这是合规功能的本质：你不可能"假装没有启用过职责分离"
2. 所有回滚前必须有灰度期验证数据支持
3. 回滚后需要主动通知受影响客户，并提供迁移指南

### 6.4 功能开关（Feature Flag）设计

```yaml
# config/feature_flags.yaml
features:
  rbac_ssd:
    enabled: false            # 默认关闭，企业客户按需开启
    description: "静态职责分离 - 互斥角色约束"
    type: "permanent"         # 稳定功能，最终默认开启
    depends_on: []            # 无依赖

  refresh_token_max_lifetime:
    enabled: false            # 默认关闭，开启后强制此配置
    description: "刷新令牌绝对过期上限"
    type: "permanent"
    depends_on: []

  prompt_select_account:
    enabled: true             # 立即开启
    description: "支持 select_account prompt 参数"
    type: "permanent"

  dpop_token_type_fix:
    enabled: true             # 立即开启
    description: "自省端点 DPoP token 返回正确 token_type"
    type: "bugfix"            # 修复类，观察两轮后移除 flag

  discovery_alignment:
    enabled: true             # 立即开启
    description: "Discovery 声明与实际行为对齐"
    type: "bugfix"
```

**Flag 生命周期策略**：
- `bugfix` 类 flag：灰度 2 周后删除代码中的 flag 条件，仅保留正向路径
- `permanent` 类 flag：初始默认关闭 → 观察 1 月 → 默认开启 → 保留 flag 供客户按需关闭（但建议最终废弃关闭选项）
