# 产品经理分析报告：五个扩展方向的优先级与产品化评估

> **分析日期**：2026-07-01
> **输入来源**：`docs/expansion-identity-beyond-protocols.md` + 资深架构师的技术核验与优先级微调建议
> **分析视角**：产品经理（Product Manager）
> **核心问题**：架构师建议的优先级调整是否经得起产品视角的推敲？哪些方向有用户价值落地的最短路径？

## 一、需求梳理

### 1.1 核心用户群体与使用场景

| 用户角色 | 身份画像 | 适用方向 | 核心诉求 | 使用频率 |
|---------|---------|---------|---------|---------|
| **SRE / 运维工程师** | 管理 SSO 生产集群的运营者 | **方向二**（生产韧性） | 减少 on-call、提前感知容量问题、避免误报 | 持续（自动化） |
| **企业安全主管（CISO）** | 买 SSO 产品的决策者 | **方向五**（治理仪表盘） | 向管理层和审计师证明控制有效 | 月/季（审计周期） |
| **普通终端用户** | 日常登录企业应用的员工 | **方向一**（安全态势） | 了解自己的安全状态、主动改善 | 每月 1-2 次 |
| **合规审计师** | 外部/内部审计人员 | **方向五**（合规报告） | 一键导出 SOC2/FedRAMP 证据包 | 按审计周期 |
| **开发工程师** | 嵌入 SSO SDK 的开发者 | **方向三**（滥用防护） | 集成安全能力的清晰 SPI | 一次性集成 |
| **企业采购评估者（POC）** | 产品选型决策链成员 | **方向二+五** | 评估平台的产品成熟度和生产就绪度 | 评估期密集 |

### 1.2 关键发现解读

**`FacetQuerier.Facets` 有界基数限制**是一个重要的**产品约束信号**：

> `FacetQuerier` 只聚合 Outcome（success/failure，2 个值）、Type（固定词汇表）、ClientID、Provider——这些是"有界基数维度"。**ActorID（用户）被显式排除**，因为它是高基数的。

这意味着方向五中需要按用户聚合的查询（MFA 覆盖率、弱密码用户清单、休眠账户）**不能复用现有 `FacetQuerier`**。需要新建专门的聚合查询层。

**产品理解**：这不全是坏消息。

| 影响 | 解读 |
|------|------|
| ❌ 方向五不能"零侵入"复用 audit 查询 | 实现成本从"复用 ~50 行"变成"新建 ~300 行" |
| ✅ 方向一的安全评分同样面临此约束 | 方向一"用户级聚合"也需要新查询层——两者有共享基建的机会 |
| ✅ 方向二的 readyz/健康检查完全不受影响 | 确认零侵入判断 |
| ✅ `FacetQuerier` 的设计本身是正确的 | Operator 级仪表盘（方向五的"成功率趋势/各 Client 失败率"）依然是低基数、可直接复用 |

**产品建议**：如果方向一（安全评分 MVP）和方向五（MFA 覆盖率/休眠账户）的底层数据源相同（`MFAEnrollmentStore` + audit 事件），考虑做一个**共享的聚合查询 SPI**——一次投入同时服务两个方向。避免各自造轮子。

## 二、用户故事

### 2.1 方向二 L1：生产韧性基础——容量感知 readyz + 级联健康 + 启动检查

**Story 2.1 — SRE 提前感知容量压力**

> **作为** 值班 SRE，
> **我希望** `/readyz` 在队列积压达到 80% 容量时自动返回 503，
> **以便** K8s 自动摘除即将过载的 Pod，防止级联超时导致整个集群雪崩。

**验收标准**：
- **Given** SSO 集群正在正常服务，某一 Pod 的认证请求队列深度超过阈值的 80%
- **When** K8s liveness/readiness probe 探测该 Pod
- **Then** `/readyz` 返回 HTTP 503，K8s 自动将该 Pod 从 Service Endpoints 中摘除
- **Then** 摘除事件记录在 Prometheus + 审计日志中
- **Then** 当队列深度恢复到阈值以下后 30 秒，`/readyz` 返回 200，Pod 自动重新加入负载均衡

**Story 2.2 — SRE 排查依赖故障根因**

> **作为** 值班 SRE，
> **我希望** `/readyz` 返回每个后端依赖（SQLite 连接池、KMS 可达性、audit sink）的独立健康状态，
> **以便** 在告警触发时能立即判断是"全局宕机"还是"某个非关键依赖降级"，从而决定是否起床处理。

**验收标准**：
- **Given** SSO 服务但 audit sink 的 Redis 连接失败
- **When** SRE 查询 `/readyz?verbose=true`
- **Then** 返回 `{"status":"degraded","checks":{"audit_sink":"red","session_store":"green","jwks_cache":"green"}}`
- **Then** 服务继续处理认证请求（审计降级为 drop-on-overflow），不触发 PagerDuty

**Story 2.3 — SRE 确认部署成功**

> **作为** 发布工程师，
> **我希望** SSO 在启动时自动检查所有关键依赖（磁盘空间、端口可用性、存储后端可达性）后再加入负载均衡，
> **以便** 避免因配置错误导致的"启动成功但服务异常"陷阱，减少部署回滚次数。

**验收标准**：
- **Given** 新版 SSO 部署到 K8s，但 SQLite 数据目录磁盘空间不足
- **When** 新 Pod 启动
- **Then** PreFlight checker 检测到 `disk.space < 500MB`，阻止 Pod 进入 Ready 状态
- **Then** K8s 不将流量路由到该 Pod，Deployment 保持旧版本继续服务
- **Then** CI/CD pipeline 收到明确的失败原因："PreFlight check failed: disk space insufficient"

### 2.2 方向一子集：安全评分 MVP

**Story 2.4 — 普通用户了解自己的安全评分**

> **作为** 企业员工 Alice，
> **我希望** 在自助门户中看到一个 0-100 的安全评分，并附带"怎么做能提高评分"的明确建议，
> **以便** 我能在被安全团队强制要求之前主动开启 MFA、更换弱密码。

**验收标准**：
- **Given** Alice 当前未开启 MFA，密码强度为"中等"
- **When** Alice 登录 SSO 后访问 `/portal/security`
- **Then** 显示安全评分 52/100
- **Then** 显示 2 条建议："开启 MFA（+25分）"、"更换更强的密码（+15分）"
- **Then** 点击建议直接跳转到对应的设置页面（MFA 管理 / 密码修改）
- **Then** Alice 开启 MFA 后返回安全页面，评分更新为 77/100

**Story 2.5 — 安全主管推动安全改善**

> **作为** 安全主管张总，
> **我希望** 在 Admin 控制台上看到一个"组织安全健康度"总览图，显示 MFA 覆盖率、弱密码占比等关键指标，
> **以便** 我能量化安全改善进度，在季度安全会议上向管理层展示"我们在改善"。

**验收标准**：
- **Given** 张总登录 Admin Console
- **When** 他访问治理仪表盘
- **Then** 展示 MFA 覆盖率条形图（整体 78%、财务部 95%、工程部 62%）
- **Then** 展示弱密码用户数量（42 人），点击可查看清单
- **Then** 展示趋势线（过去 3 个月 MFA 覆盖率从 45% 提升至 78%）
- **Then** 支持导出为 PDF 或 PNG 用于会议材料

### 2.3 方向三 L2→L3 协同：RiskScorer + RateLimiter 上下文传递

**Story 2.6 — 安全团队防御分布式凭据填充**

> **作为** 安全分析师，
> **我希望** 速率限制器知道当前请求的风险评分——高风险请求的限流阈值自动降低 90%，
> **以便** 在分布式慢速凭据填充攻击中，攻击者即使每个 IP 只尝试一个账号，也会因为异常行为特征被精准限制。

**验收标准**：
- **Given** 攻击者使用 5000 个住宅代理 IP，每个 IP 测试一个不同的用户名-密码组合
- **When** 每个请求到达 `/token` 端点
- **Then** RiskScorer 评估每个请求：IP 为住宅代理（+0.3）、凭据为已知泄露密码（+0.5）、请求间隔均匀（+0.2）→ 总分 1.0
- **Then** 风险评分传递给 RateLimiter → 阈值从 10 req/min 自动降至 1 req/min
- **Then** 攻击者每秒只能完成 ~20 次猜测（而非 ~50000 次）
- **Then** 安全团队收到告警："检测到分布式凭据填充攻击（来源：5000+ 代理 IP，目标：high-value 账号）"

## 三、边界场景分析

### 3.1 方向二 L1（生产韧性）

| 场景 | 风险 | 产品要求 |
|------|------|---------|
| 突发流量峰值在 1 秒内将队列从 10% 涨到 95% | readyz 立即返回 503 → K8s 摘除 Pod → 但摘除后流量分配到其他 Pod → 其他 Pod 也被压垮（**雪崩**） | 支持**提前预警**：阈值为 60% 时发出 WARNING 而非直接 503；仅 90%+ 才返回 503 |
| 某 Pod 的 readyz 在 "green/red" 之间频繁抖动（flapping） | K8s 频繁摘除/加入 Pod → 导致 Service Mesh 的端点表不断更新 → 客户端连接重置 | 引入 **hysteresis**（滞后阈值）：从绿到红的触发阈值 ≠ 从红到绿的恢复阈值。默认恢复需要持续 30 秒低于阈值 |
| 非关键依赖（如审计 Sink）持续故障 | readyz 持续返回 "degraded" → 监控告警疲劳 → SRE 开始忽略 degraded 状态 | degraded 状态**不触发 PagerDuty**，仅在 dashboard 显示。仅 red 状态触发告警。产品上提供"静默模式"开关 |
| 启动检查超时（pre-flight 检查依赖 30 秒无响应） | 整个 Pod 启动失败 → 滚动更新被阻塞 | 启动检查应有**可配置的超时**（默认 30 秒），超时后应 Fail-Open（标记 WARNING 但允许继续启动）而非 Fail-Close（阻止启动） |
| 多副本同时冷启动预热，所有 Pod 同时请求后端 | 预热导致存储后端连接数爆满 → **预热雪崩** | 预热应支持 **jitter（随机延迟）**，每个副本在 `[0, maxJitter]` 之间随机偏移后再开始预热序列 |

### 3.2 方向一安全评分 MVP

| 场景 | 风险 | 产品要求 |
|------|------|---------|
| 用户没有 MFA 注册记录——是未注册 MFA 还是系统从未支持 MFA？ | 评分将缺失 MFA 部分的数据 → 错误地暗示"安全" | 三元状态：`enabled` / `not_enabled` / `unknown`。`unknown` 时评分不扣分但提示"无法评估 MFA 状态" |
| 用户在评分页看到一个低分但**没有任何可操作的改善建议** | 挫败感，用户放弃改善 | **每个扣分项必须对应至少一条可操作的建议**（带直接链接）。如果没有链接（如"你的账户有异常登录模式"），建议用中性表述不直接扣分 |
| 密码健康检查（HIBP）无法访问 | 密码健康维度无法计算 | Fail-Open：不扣分但显示"密码泄露检查暂时不可用"。不要因此降低总体评分或阻止用户查看页面 |
| 安全评分被用作**访问控制条件**（如评分<50 要求 MFA） | 这是高阶方向，但 MVP 如果 API 设计不预留可能导致断裂 | MVP 的评分返回应包含**影响因子明细**（`{"score":52,"factors":[{"name":"mfa","impact":25,"status":"missing"}]}`），为后续策略引擎预留 |
| 管理员角色 vs 普通用户——管理员的安全评分应包含额外维度 | 管理员可能有不同的安全要求（如强制 MFA、更短密码周期） | 评分模型应支持**角色感知**：管理员的评分基线不同，缺失管理员 MFA 的扣分更重 |

### 3.3 方向三 L2→L3 协同（RiskScorer + RateLimiter）

| 场景 | 风险 | 产品要求 |
|------|------|---------|
| RiskScorer 自身性能抖动（单次评估 > 50ms） | 同步请求路径被阻塞 → 正常用户登录也变慢 | RiskScorer 评估必须有 **p99 < 10ms** 的性能预算。超过预算的评估应 Fail-Open（返回最低风险分）而非阻塞请求 |
| RiskScorer 和 RateLimiter 的上下文传递丢失（网络抖动/反序列化失败） | 限流器没有风险信息 → 退化为基础全局限流 | 上下文传递应**Fail-Open**：接收方无法解析风险上下文时，使用最保守的限流阈值（即"高风险"模式） |
| 恶意用户操纵风险特征（伪造 User-Agent、使用无头浏览器） | 风险评分永远偏低 | 风险评分不应依赖单一信号。缺少设备指纹时自动上调风险基础分。产品上，需要在设计阶段就定义**信号衰减策略** |
| 同一用户的极高风险请求被限流，但该请求确实是合法操作（误杀） | 用户体验受损 | 限流导致的 429 必须包含明确的 `Retry-After` 头和**用户可读的错误信息**："检测到异常登录模式，请 30 秒后重试。如果您认为这是误杀，请[联系支持]。" |
| 协同策略在超大规模部署下（1000 万+日活）的计算开销 | 即使单个评估 < 5ms，每秒 5000 请求的评估开销可能占满 CPU | 需要**评估缓存**：同一用户的多次评估在 60 秒窗口内复用结果。但缓存导致 TOCTOU——需要权衡 |

### 3.4 方向五 MFA 覆盖率 + 休眠账户

| 场景 | 风险 | 产品要求 |
|------|------|---------|
| 新用户注册后立即查询 → 登录事件尚未写入 audit | 用户被标记为"休眠"→ 错误的休眠账户告警 | 休眠阈值必须是**注册后时间 ≥ 休眠阈值**，而非"audit 无记录"。新注册用户应在上线 90 天后再纳入休眠检测 |
| 用户开启 MFA 后又关闭 → 覆盖率统计口径 | "覆盖率下降"触发告警，但可能只是用户主动操作 | 覆盖率变化应区分"自然波动"（用户自助关闭）和"异常批量关闭"（可能为攻击）。提供 3 种口径：**注册率** / **启用率** / **活跃使用率** |
| 休眠账户中包含服务账号、系统机器人 | 服务账号的"长期不登录"是正常行为，不应告警 | 用户模型应支持**账户类型标签**（human / service / machine）。休眠检测默认排除服务账号。管理员可配置是否纳入 |
| MFA 覆盖率统计被大量僵尸账户稀释（从未使用的老账户） | 覆盖率看起来很低（分母太大），但活跃用户覆盖率可能很高 | 覆盖率应提供两种口径：**全体** / **活跃用户**（30 天内有登录行为）。产品上默认显示活跃用户覆盖率为准 |
| 多租户场景：每个租户的 MFA 覆盖率差异很大 | 聚合数据掩盖了低覆盖率的租户 | 覆盖率必须支持**按租户下钻**。Admin 仪表盘应展示"最低覆盖率 Top-5 租户"作为默认视图 |

## 四、功能优先级（MoSCoW 方法）

基于代码库分析 + 产品价值评估，我对架构师的优先级调整做**产品视角校验和补充**：

### Must Have（本期必须交付）

| 方向 | 模块 | 产品理由 | 工作量 |
|------|------|---------|--------|
| **方向二 L1** | 容量感知 readyz | SRE 第一需求："你的服务什么时候会死？"——没有容量感知的 readyz，K8s 调度器是盲人。这是生产部署的前提条件 | ~150 行 |
| **方向二 L1** | 级联健康 | SRE 第二需求："依赖故障时我应该起床吗？"——区分"核心降级" vs "非核心告警"直接影响 on-call 生活质量 | ~100 行 |
| **方向二 L1** | 启动前检查 | 发布工程师第一需求："部署失败的原因是什么？"——在 CI/CD 中阻止配置错误进入生产 | ~100 行 |
| **方向一子集** | 安全评分（MVP） | 产品差异化需求——竞争对手都有"安全健康分"（Google My Account、Microsoft My Sign-Ins），这是企业采购的加分项。60 分的 MVP 意味着 60% 的价值 | ~300 行 |
| **方向五子集** | MFA 覆盖率 | 合规需求——SOC2 CC6.7 要求组织级 MFA 覆盖率可见性。没有这个数据，审计师不会签字 | ~200 行 |

### Should Have（重要但可延迟 1-2 个 Sprint）

| 方向 | 模块 | 产品理由 | 工作量 |
|------|------|---------|--------|
| **方向三** | L2→L3 协同（RiskScorer + RateLimiter） | 安全纵深需求——当前最容易被分布式慢速攻击利用的空隙。但 MVP 需要 RiskScorer SPI 的定义已存在，集成风险较低 | ~400 行 |
| **方向五子集** | 休眠账户检测 | 合规需求——NIST AC-2 要求账户定期审查。但可以通过手动导出 + 脚本方式临时满足优先级可以略低 | ~200 行 |
| **方向一子集** | 登录地理可视化 | 用户可见价值高，但 MVP 阶段可以先用列表展示替代地图，降低前端复杂度 | ~300 行 |

### Could Have（锦上添花）

| 方向 | 模块 | 产品理由 | 工作量 |
|------|------|---------|--------|
| **方向一** | 设备管理 + 信任评级 | 依赖新建 DeviceStore SPI，且与方向三的设备指纹有耦合。建议两个方向统一定义后再实现 | ~400 行 |
| **方向五** | 合规报告自动生成（SOC2 证据包） | 极大节省合规团队时间，但不影响功能可用性。企业客户一般在采购后 3-6 个月才需要 | ~500 行 |
| **方向二 L2** | 特性门控（Feature Toggle） | 运维灵活性增强。但可以通过环境变量 + 重启实现等价功能（尽管体验差） | ~300 行 |
| **方向二 L3** | 启动/关闭顺序 DSL | 在 Level 1 稳定之前不需要。当前硬编码顺序对大多数场景已足够 | ~300 行 |

### Won't Have（本期不实现）

| 方向 | 模块 | 原因 |
|------|------|------|
| **方向四** | 跨协议 Session Hub & 迁移工具 | 依赖全协议后端稳定。当前 SAML/LDAP/Kerberos 的生产部署场景尚未规模化，迁移需求在客户达到 50+ 后才出现。**本期列为 P3，不投入任何开发资源** |
| **方向一** | ML 驱动安全评分 | 团队没有 ML 运维能力。当前规则引擎 + 静态评分的精度足够覆盖 80% 场景。ML 评分作为 V2 规划 |
| **方向三** | JA3 指纹收集 + 浏览器指纹 | 依赖额外的基础设施（代理层/JS SDK），超出了当前 SSO 的职责边界。应作为"平台集成能力"独立项目 |
| **方向三 L5** | 跨用户暴力破解模式检测 | 异步行为分析的复杂度较高，需要存储跨用户攻击模式。建议在基础风险评分稳定后由异常分析团队专项负责 |

### 优先级总览（MoSCoW 矩阵）

```
优先级    方向                Phase 估算    关键理由
─────────────────────────────────────────────────────
Must    方向二 L1 (readyz)     ~2-3天 (350行)   生产部署前提
Must    方向一 (安全评分MVP)    ~1周 (300行)     产品差异化 + 用户可见价值
Must    方向五 (MFA覆盖率)     ~1周 (200行)     合规需求 SOC2 CC6.7
Should  方向三 (L2→L3协同)     ~1.5周 (400行)   安全纵深缺口
Should  方向五 (休眠账户)      ~0.5周 (200行)    合规 NIST AC-2
Could   方向一 (地理可视化)     ~1周 (300行)     体验提升
Could   方向二 L2 (特性门控)    ~1周 (300行)     运维灵活性
Won't   方向四                 -                依赖条件未满足
```

## 五、成功指标

### 5.1 方向二 L1（生产韧性）

| 指标 | 当前基线 | 目标（Level 1 上线后 4 周） | 测量方式 |
|------|---------|---------------------------|---------|
| 因容量过载导致的 P0 告警次数 | 无法测量（当前无容量感知） | **减少 80%** | PagerDuty 月度统计 |
| 启动失败的部署回滚率 | 假设 ~5% | **降至 <1%** | CI/CD 管道统计 |
| SRE 故障定位 MTTR（平均修复时间） | 未知 | **缩短 30%**（健康度信息立即可用） | 值班日志 |
| 误报告警（SRE 起床后发现无需处理） | 未知 | **减少 50%**（依赖降级 vs 核心故障区分） | SRE 反馈 |

**产品化的关键**：这些指标需要**从上线第一天就能看到**。建议在方向二 L1 做完的同时，在 Prometheus 中增加对应的告警规则和 Grafana 仪表盘。没有仪表盘的健康检查等于没有。

### 5.2 方向一安全评分 MVP

| 指标 | 目标 | 测量方式 |
|------|------|---------|
| 用户访问率 | 上线后 4 周内，**>30%** 的活跃用户至少访问一次安全仪表盘 | `/portal/security` 的页面 PV |
| 建议行动率 | 看到建议后，**>15%** 的用户在 7 天内执行至少一项改善操作 | 建议点击 → 对应功能完成率 |
| MFA 自发启用率 | 安全仪表盘上线后，自助 MFA 启用率**提升 2 倍** | 对比上线前后 MFA 启用周趋势 |
| NPS 反馈 | 用户反馈中"安全检查"相关正向反馈占比 > 60% | 内嵌反馈收集（⭐ 评分） |

**产品化的关键**：不要用"评分"来羞辱用户。评分的目的是**赋能**（"我能做什么变好"），而非**评判**（"你的安全很差"）。文案、颜色、建议的措辞都需体现正向引导。

### 5.3 方向五 MFA 覆盖率

| 指标 | 目标 | 测量方式 |
|------|------|---------|
| 覆盖率数据的准确性 | **<1%** 的误差（与真实数据对比） | 随机抽样 100 个用户手动核对 |
| 查询响应时间 | 覆盖率聚合查询 **p99 < 200ms** | APM 监控（Datadog / Prometheus） |
| 审计师采纳率 | 合规审计中使用覆盖率数据**替代手动统计** | 季度反馈 |
| 每季度覆盖率提升 | 覆盖率 **季度环比增长率 > 5%** | 仪表盘趋势线 |

### 5.4 方向三 L2→L3 协同

| 指标 | 目标 | 测量方式 |
|------|------|---------|
| 协同限流的误杀率 | 被错误限流的合法请求 **< 0.01%** | A/B 测试：协同 vs 非协同策略对比 |
| 分布式攻击检测率 | 模拟分布式慢速攻击时检测率 **> 90%** | 红队演练 / 安全测试 |
| 风险评估延迟 | 风险评分注入 **不增加 p95 延迟 > 5ms** | 请求级追踪 |

### 6.4 Feature Flag 设计

所有新功能使用一致的 Feature Flag 命名模式：

```yaml
# config/features.yaml
features:
  # 方向二 L1
  resilience:
    capacity_aware_readyz: true        # 容量感知 readyz（默认开）
    cascading_health: true             # 级联健康探针（默认开）
    preflight_checks: true             # 启动前检查（默认开）
  
  # 方向一
  security_score:
    enabled: false                     # 安全评分（灰度，默认关）
    show_on_portal: true               # 在门户中展示
    factor_weights:                    # 各维度权重配置
      mfa: 0.4
      password_strength: 0.3
      session_health: 0.2
      login_activity: 0.1
  
  # 方向五
  governance:
    mfa_coverage: false                # MFA 覆盖率仪表盘（默认关）
    stale_identity_detection: false    # 休眠账户检测（默认关）
    auto_disable_stale: false          # 自动禁用休眠账户（默认关，不允许在 Phase 0 开启）
    stale_threshold_days: 90           # 休眠阈值
  
  # 方向三
  rate_limiter:
    risk_aware: false                  # 风险感知限流（默认关）
    risk_aware_shadow: true            # 影子模式——记录但不执行限流决策（灰度用）
  
  # 方向二 L2
  feature_toggle:
    runtime: false                     # 运行时特性门控（默认关）
```

**Feature Flag 原则**：

1. 所有灰度功能 == 默认关闭
2. 每个 Feature Flag 有 owner（谁可以修改）和 expiration（何时转变为默认行为）
3. 自注册——新功能自动出现在 `/admin/features` 端点
4. 变更记录——谁在何时 toggle 了哪个 feature 写入审计日志
5. 生命周期管理——超过 2 个版本未 promoted 到默认开的 feature 触发废弃警告

## 七、综合建议

### 7.1 对架构师优先级微调的回应

| 架构师建议 | 产品经理评估 | 结论 |
|-----------|-------------|------|
| **方向二 L1 → P0** | ✅ **完全同意**。零侵入、立即可用、每行代码都有运维价值。这是「地基」——没有它，上层功能在故障时不可见 | **确认 P0** |
| **方向一安全评分 → P0** | ✅ **同意，但增加前提**：MVP 版本（安全评分 + 2 条建议）确实是 ~300 行可实现的。但需注意**文案和 UX 的设计投入**——评分做得不好反而会引发用户不满或焦虑 | **确认 P0**，但要求增加 UX 设计 Sprint |
| **方向三 L2→L3 → P1** | ✅ **同意**。这是当前最容易被利用的安全空隙。但 Phase 0/1 的基础设施必须先建成（RiskScorer 稳定、RateLimiter 已部署），所以逻辑上排在 Phase 2 | **确认 P1** |
| **方向五 MFA+休眠 → P1** | ✅ **同意 P1，但建议拆分**：MFA 覆盖率提升到 Phase 1（合规 ROI 高，~200 行），休眠账户放在 Phase 2（复杂度和使用频率较低） | **MFA 覆盖率 → Phase 1 (P0)**，休眠账户 → Phase 2 (P1) |
| **方向一设备管理 → P2** | ✅ **同意**。设备指纹 SPI 是新建工作，且与方向三的设备指纹需求耦合——建议两项统一设计再实施 | **确认 P2** |
| **方向四 → P3** | ✅ **坚决同意 P3**。SessionHub 依赖全协议后端稳定，当前客户规模不足以产生迁移需求。**不建议在 2026 Q3 投入任何资源** | **确认 P3** |

### 7.2 核心产品决策

1. **共享聚合查询 SPI 是 Phase 0 的关键架构决策**：方向一（用户级安全评分）和方向五（MFA 覆盖率）都需要按用户聚合的数据。如果分别建两套，浪费；如果建一套共享的 `AggregationQueryer` SPI，一次投入双重收益。**建议在 Phase 0 的技术设计 Sprint 中优先定义这个 SPI**。

2. **安全评分的"不是扣分，是加分"原则**：用户看到 52/100 的第一反应是"我怎么这么差？"。建议从 0 分起步，"已采取安全措施 → 加分"，而不是从 100 分起步"缺少安全措施 → 扣分"。前者给用户正向激励（"我已经做了哪些"），后者产生焦虑（"我还差哪些"）。

3. **方向二 L1 的 SRE 仪表盘跟功能代码一样重要**：只有代码没有仪表盘 = 功能不存在。Phase 0 的交付物清单必须包含 Prometheus 告警规则 + Grafana 仪表盘 JSON 模板。

4. **方向五的合规报告 API 设计必须预留"可审计"接口**：审计师需要的是**不可篡改的导出证据**，而非"截图看起来很漂亮"。MFA 覆盖率 API 必须在返回数据的同时，附带**生成时间戳 + 数据源说明 + 覆盖范围的明确声明**（"统计时间：2026-07-01T00:00:00Z，覆盖 1,234 位活跃用户，数据源：MFAEnrollmentStore"）。

5. **不要把方向三（限流协同）做成全自动黑盒**：安全团队需要理解"为什么这个请求被限流了"。协同策略引擎必须有**决策可解释性**：每次限流决策记录 `{risk_score: 0.85, factors: {ip_reputation: 0.3, credential_leak: 0.5, geo_velocity: 0.05}, action: rate_limit_90pct}`。没有解释的攻击检测 → 没有人信任的告警。

### 7.3 一句话总结

> **方向二 L1 给 SRE 安全感（"不会半夜被假告警叫醒"），方向一的评分给用户掌控感（"我知道我的账户安全"），方向五的治理给审计师证据（"这是合规证明"）。三个方向回答三个完全不同的用户角色问题，共享同一底层数据——将它们绑定在一个连贯的产品发布计划中是最高 ROI 的选择。**
