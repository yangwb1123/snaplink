# 📋 产品经理分析报告：安全策略文档（SECURITY.md）

---

## 1. 需求梳理

### 1.1 核心用户群体与使用场景

| 用户角色 | 场景 | 接触文档 |
|---|---|---|
| **安全研究员/白帽子** | 发现漏洞后需要私密报告，获得明确流程指引和响应承诺 | `.github/SECURITY.md`（GitHub 自动发现） |
| **运维部署人员** | 上线前需要安全加固检查清单，确认生产环境符合最低安全标准 | `.github/SECURITY.md` |
| **项目贡献者/开发者** | 提交代码时需要遵守安全规范，确保不引入安全缺陷 | `docs/SECURITY.md`（开发者清单） |
| **企业安全合规团队** | 评估是否采用此产品，需要了解支持策略、响应 SLA 和漏洞处理流程 | 两个文档都需要 |
| **最终用户（非技术）** | 不直接接触，但其数据安全受此策略保护 | — |

### 1.2 关键功能需求提炼

**D security.md** 和 **github security.md** 本质上是**同一个能力（漏洞报告流程）的两种面向**。从产品角度看，这不是"两个功能"而是一个功能需要覆盖两个场景：

| 需求 ID | 需求描述 | 面向角色 | 当前状态 |
|---|---|---|---|
| R‑01 | 提供清晰的私密报告入口（无门槛，首选） | 安全研究员 | ✅ GitHub Security Advisories |
| R‑02 | 提供邮件备选报告通道 | 安全研究员 | ✅ email |
| R‑03 | 明确可接受的支持版本范围 | 运维/合规 | ✅ `.github` 有；`docs` 缺失 |
| R‑04 | 公布响应时效承诺（SLA），建立信任 | 安全研究员/合规 | ⚠️ 两处不一致（24h vs 3 工作日） |
| R‑05 | 明确报告范围（in/out of scope） | 安全研究员 | ✅ `.github` 有；`docs` 缺失 |
| R‑06 | 提供上线前安全加固清单 | 运维 | ✅ `.github` 有；`docs` 缺失 |
| R‑07 | 提供开发者侧安全编码检查清单 | 贡献者 | ✅ `docs` 有；`.github` 缺失 |
| R‑08 | 透明展示安全架构决策（fail-open/closed 模型） | 架构师/合规 | ✅ `docs` 有；`.github` 缺失 |
| R‑09 | 统一两处文档，消除歧义 | 所有用户 | ❌ 两处存在矛盾 |

### 1.3 Must-have vs Nice-to-have

| 优先级 | 需求 |
|---|---|
| **Must have** | R‑01 (报告入口), R‑02 (备选通道), R‑04 (SLA 承诺), R‑09 (统一文档) |
| **Should have** | R‑03 (支持版本), R‑05 (报告范围), R‑07 (开发者清单) |
| **Could have** | R‑06 (运维加固清单), R‑08 (安全架构说明) |
| **Won't have** | (无) — 所有需求均已部分存在，只是未统一 |

## 2. 用户故事

### 2.1 安全研究员提交漏洞

```
作为 安全研究员，
我希望 有一个明确且便捷的私密漏洞报告路径（首选 GitHub Advisories，备选邮件），
以便 在不暴露 0-day 细节的前提下，安全地将漏洞告知维护者并获得响应。

验收标准：
  Given 我发现了 snaplink/sso 的一个安全漏洞
  When 我访问仓库页面 → "Security" tab → "Report a vulnerability"
  Then 系统引导我填写标准化的报告表单
  And  我在 3 个工作日内收到人工确认回执

  Given 我无法使用 GitHub 界面
  When 我发送邮件至 security@snaplink.dev
  Then 系统在 24 小时内自动回复确认收悉
  And  邮件中包含安全 FAQ 或 PGP 公钥获取方式
```

### 2.2 运维人员安全加固

```
作为 运维工程师，
我希望 在部署前有一个可逐项打勾的安全加固检查清单，
以便 不会遗漏关键安全配置，确保生产环境达到最低安全标准。

验收标准：
  Given 我正在准备上线部署
  When 我参照安全策略文档中的 "Operator-Side" 清单逐项检查
  Then 我可以确保：
    - TLS 已启用
    - 非生产组件（ssoclient/dev）已禁用
    - Boootstrap 锁非 noop
    - JWT 签名密钥已有轮换计划
    - 审计日志已接入持久化存储
    - 时钟已配置为单调递增（chrony 而非 ntpdate）
```

### 2.3 贡献者安全编码

```
作为 项目贡献者，
我希望 在提交代码时有一份可自检的安全清单，
以便 在审查之前提前发现常见安全疏漏（缺少 no-store 头、边界校验等）。

验收标准：
  Given 我完成了代码修改、准备提交 PR
  When 我对照开发者安全清单逐项自检
  Then 我可以确认：
    - 所有凭据端点已设置 tokenNoStoreHeaders
    - 所有 401 已使用 setBearerChallenge
    - Oracle-leak 模式已统一
    - 枚举防护（bcrypt dummy hash）已实现
    - 审计日志已使用 SetMeta 而非直接操作 map
    - 错误代码和 API 文档已同步更新
```

### 2.4 安全合规评估

```
作为 企业安全合规负责人，
我希望 清楚了解该产品的漏洞响应 SLA、支持版本策略和 fail-open/closed 模型，
以便 评估该产品是否满足我所在企业的安全合规要求。

验收标准：
  Given 我在评估是否引入 snaplink/sso
  When 我阅读安全策略文档
  Then 我可以获得：
    - 明确的版本支持矩阵（pre-1.0 策略 + 1.0 后 SemVer 计划）
    - CVSS v3.1 严重性评级标准
    - 各阶段响应时效承诺（确认、分诊、修复、披露）
    - 协调披露时间线默认 90 天
    - 已标明的 in-scope/out-of-scope 组件
```

## 3. 边界场景分析

### 3.1 异常输入与错误处理

| 场景 | 当前状态 | 风险等级 | 建议 |
|---|---|---|---|
| 报告者通过邮件发送了不完整的信息（无复现步骤、无版本） | 两文档均建议包含，但未强制 | 🟡 中 | 自动回复模板提示报告者补充缺项 |
| 报告者将漏洞发到了公共 Issue 而非私密渠道 | 文档已预警"不要公开提交" | 🟡 中 | 考虑 Issue 模板中自动添加安全检查提醒 |
| PGP 密钥文件过期/404 | `docs` 引用 `.well-known/pgp-key.txt`，`.github` 未引用 | 🟠 高 | 需确认该密钥是否真实维护；若废弃则应删除引用或统一到 `.github/` |

### 3.2 文档不一致导致的边界风险

| 问题 | 影响 | 严重性 |
|---|---|---|
| SLA 不一致（24h vs 3 工作日） | 报告者期待 24h 响应，实际是 3 工作日→逾期感→信任受损 | 🔴 严重 |
| `docs` 有 PGP 引用但 `.github` 没有→报告者不知可用 | 加密通道利用率低 | 🟡 中等 |
| `docs` 无 in-scope/out-of-scope→报告者可能浪费时间报告 out-of-scope 项 | 研究者和维护者双输 | 🟡 中等 |
| `docs` 无运维清单→运维者可能遗漏关键安全配置 | 生产环境安全隐患 | 🔴 严重 |
| 两个文档在同一次发布中可能被分别更新→内容漂移加剧 | 长期维护成本上升 | 🟡 中等 |

### 3.3 并发与竞态条件（安全响应流程）

| 场景 | 问题 | 建议 |
|---|---|---|
| 多人同时报告同一漏洞 | GitHub Advisories 可以协作，但邮件通道可能重复 | 邮件自动回复中加入推荐优先使用 GitHub Advisories 的引导 |
| 漏洞在修复窗口期内被第三方公开披露 | 竞争性披露→无准备时间 | 策略中应包含应急加速时间线（Critical 公开披露→24h 热修复） |
| 维护者休假/失联导致 SLA 超期 | SLA 承诺无备份人员→超期损害信誉 | 策略中加入维护者后备联系人机制 |

### 3.4 性能瓶颈（非技术、流程层面）

| 瓶颈 | 当前设计 | 风险 |
|---|---|---|
| 仅单邮件地址（security@snaplink.dev） | 邮箱若无人值守，SLA 承诺形同虚设 | 高 |
| SLA 中 30 天修复期对于 Critical 偏长 | 行业最佳实践（如 GitHub Security Lab）是 14 天内出补丁 | 中等—建议收紧至 14 天 |
| 协调披露周期 90 天固定 | 部分漏洞可能无需 90 天就已公开 | 低—已有"与你协商"的灵活性 |

### 3.5 安全与权限边界

| 场景 | 注释 |
|---|---|
| 安全策略文件本身（`.github/SECURITY.md`）被篡改 | 需通过分支保护规则限制对该文件的修改权限 |
| `docs/SECURITY.md` 被视为"开发者内部文档"却包含了外部信令（邮件地址、PGP 引用） | 外部信令应只出现在 `.github/` 这一权威入口 |

### 3.6 配置与部署场景

同 2.2 运维清单。需要注意的是：当前两份文档都**没有**说明"如果你看到了不一致的版本，以哪份为准"的排错指引。

| 分类 | 项目 | 说明 |
|---|---|---|
| **Must have** | 统一两处 SLA 为标准版本 | 当前不一致是直接的信任风险 |

| **Should have** | 在 `docs/SECURITY.md` 中增加对 `.github/SECURITY.md` 的显式引用（"请优先查阅 GitHub 安全策略"） | 导航指引 |

| **Could have** | Issue/PR 模板中自动嵌入安全策略链接 | 自动化预防 |
| **Could have** | 邮件自动回复确认 + 补全信息模板 | 提升报告质量 |

| **Won't have** | 多语言版本 | 当前阶段不必要 |

## 5. 成功指标（OKR 框架）

### 5.1 客观可量化指标

| 指标 | 目标值 | 度量方式 |
|---|---|---|
| **SLA 符合率** | ≥ 95% 的报告在承诺时效内收到确认 | 追踪 GitHub Advisories + 邮件确认时间 |
| **安全报告平均响应时间** | 确认 < 48h；分诊 < 7 天 | 内部度量，季度回顾 |
| **开发者清单遵循率** | 提交前自检通过率（通过 CI 或人工审查） | 可在 CI 中加入清单自检步骤 |
| **运维清单完整性** | 上线前加固检查覆盖率 > 80% | 运营团队反馈 + 安全事件前置分析 |
| **两个文档内容一致性** | 歧义差异数 = 0 | 定期自动化 diff 检查 |
| **安全报告平均质量评分** | ≥ 4/5（含完整复现步骤、版本、影响评估） | 维护者主观评分，引导模板优化 |

### 5.2 定性指标

- 报告者满意度（可在确认邮件后附带 1-2 题问卷）
- 社区对安全响应透明度的公开评价（GitHub 讨论 / Twitter / HackerNews）
- 合规评估团队的采纳信心指数（可在评估交流中捕捉）

## 6. 发布策略

### 6.1 MVP（最小可行产品）范围

本次"产品"是一个**文档重构 + 流程改进**，而非新功能开发。

**MVP 交付物：**

1. **统一 SLA**：将 `docs/SECURITY.md` 的 "24h" 修改为 "3 business days"，与 `.github/` 一致（或反之，取决于团队实际运维能力）。
2. **文档角色明确**：
   - `.github/SECURITY.md` → 全量权威版本（包含所有章节）
   - `docs/SECURITY.md` → 精简版，专为开发者/贡献者设计，开头显式引用 `.github/SECURITY.md` 为完整版
3. **PGP 状态确认**：要么删除 `docs/` 中的 PGP 引用（若实际未维护），要么将 PGP 引用同步到 `.github/` 中。
4. **交叉引用**：`docs/SECURITY.md` 末尾增加 "Quick Reference" 表格，告知读者各部分内容的最佳阅读位置。

### 6.2 灰度发布计划

| 阶段 | 范围 | 验证目标 | 时长 |
|---|---|---|---|
| **Phase 0: 内部审查** | 维护团队 review 修改后文档 | 内容准确性、无技术错误 | 2-3 天 |
| **Phase 1: 无声上线** | 合并到 `main`，观察社区反馈 | 无负面反馈 | 1 周 |
| **Phase 2: 主动沟通** | 在 Release Notes / CHANGELOG 中提及安全策略更新 | 社区周知 | 1 次发布周期 |
| **Phase 3: 全线完成** | 在 Issue 模板 + CI 检查中引用新策略 | 流程内化为自动化 | 下个 milestone |

### 6.3 回滚策略

| 触发条件 | 操作 | 评估 |
|---|---|---|
| 社区反馈 SLA 从 24h 降至 3 工作日不可接受 | 恢复为 24h 但另立"目标型"和"承诺型"两层 SLA | 低概率 |
| 安全研究员反馈混淆（文档改后导航不清） | 撤销 `docs/` 的简化改动，恢复原状，另计划 | 中概率 |
| PGP 密钥维护状态确认冲突 | 从两个文档同时删除 PGP 引用，待密钥流程成熟再引入 | 低概率（但可预见） |

### 6.4 Feature Flag 设计（非功能性，但可用于文档释出）

虽然不是功能代码，但文档的"发布"可用类似机制：

| Flag | 用途 | 受众 |
|---|---|---|
| `docs.security.policy.consolidated` | 控制是否展示统一后的安全策略（可在内部 staging 先预览） | 维护者内部 |
| `docs.security.developer.redirect` | 控制 `docs/SECURITY.md` 顶部是否显示"请查阅 .github/ 权威版本"的横幅 | 所有读者 |

## ✅ 总结与产品建议

### 当前最大问题

> **两个版本的 SLA 承诺不一致（"24小时" vs "3个工作日"）是最高优先级需解决的问题。** 这不是文字编辑问题——它直接影响到安全社区对项目的信任。

### 产品建议

1. **立即行动（今日可做）**：统一 SLA 数字，确认实际运维能力后采用合理的那个值。
2. **短期（本周）**：明确 `.github/SECURITY.md` 为权威版本，重构 `docs/SECURITY.md` 为开发者子集文档，消除所有已知矛盾点。
3. **中期（本月）**：将运维安全清单纳入部署文档（如 `docs/deploy.md`）的必读章节，而非仅放在安全策略里。
4. **长期（季度）**：建立文档一致性自动化检查（GitHub Action diff 检查两个文件），防止内容漂移再次发生。

**一句话产品定位**："一份清晰、一致的漏洞报告策略，是对安全社区最基础的尊重。"
