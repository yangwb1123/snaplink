# Feature Spec: Active ITDR — Detection-to-Response Bridge

> Generated by: Architect Agent | For: Implement Agent | Verified by: Reviewer Agent

## 1. Goal

Build a **Threat Executor SPI + Policy Engine** that bridges the gap between the existing anomaly detection subsystem (which already detects impossible travel, velocity bursts, brute-force sprays, and token anomalies) and active security actions on the auth request path. Currently, `domains/anomaly.Runner` + `domains/tokenanomaly.Detector` produce signals that go to audit + webhook — they "smoke alarm" but never "call the fire department". This spec adds an off-request-path response executor that translates detection findings into policy actions (suspend session, revoke token family, step-up MFA on next login, notify tenant admin), and a lightweight policy engine that governs *which* threats trigger *which* actions, without requiring operator code changes.

This is NOT about rewriting the synchronous `spi.RiskScorer` path — the request-time risk decision stays millisecond-budget. The executor acts on signals **after** they're produced, affecting *subsequent* requests.

## 3. Architecture Analysis

### 3.1 Current State: Detection-Rich, Response-Poor

The system today has a clean three-tier anomaly architecture:

```
Login Path          Off-Path Detection              Response
──────────          ──────────────────              ────────
LoginEvent ─────►   anomaly.Runner ───► Detector     audit.Sink (EventAnomalyDetected)
  (hot path)         └─► Sink ───────► audit.Recorder
                     └─► webhook (operator notification)

TokenUsage ─────►   tokenanomaly.Detector ───► FindingStore
  (recorder drain)    └─► admin read API (GET /suspicious)
```

**What's missing:** The detection results have no path back into auth policy. An `impossible_travel` critical signal from `anomaly.Runner`:
- ✅ Generates an audit event
- ✅ Emits a metric
- ✅ Optionally fires a webhook
- ❌ **Cannot** trigger a session suspension, token revocation, or MFA step-up on next login

The only "active" response today is through `RefreshTokenRotationLimiter` (velocity cap kills families) and `conditionalaccess.Policy` (request-time evaluation of synchronous risk score) — neither is fed by the async anomaly detectors.

### 3.2 Why Not Just Inline the Response?

The current architecture deliberately separates **detection** (async, windowed, off-path) from **decision** (sync, millisecond-budget, on-path). Three reasons the response must stay off-path:

| Concern | Async Detection | Sync Decision |
|---|---|---|
| Budget | Seconds (windowed queries OK) | <10ms (single KV lookup) |
| State | Full login history, geo stats, per-IP counters | Current request only |
| Failure mode | Fail-open (log and continue) | Fail-closed (deny) |

A `ThreatExecutor` that acts on anomaly signals runs off-path, AFTER the request completes, and affects **subsequent** requests — same latency profile as detection, same fail-open contract.

### 3.3 Existing Interfaces That Already Point in This Direction

The codebase already has several primitives that suggest this extension was anticipated:

| Existing Interface | Role in new design |
|---|---|
| `anomaly.Detector` | Produces `anomaly.Signal` — unchanged |
| `anomaly.Sink` | Currently takes Signal → audit. New `ThreatExecutor` joins alongside Sink in the runner's per-signal fan-out |
| `tokenanomaly.FindingStore` | Persists token anomalies. New design: FindingStore + a sweep callback that feeds ThreatExecutor |
| `session.SessionStore` (via `SessionManager`) | `RevokeSession` / `SuspendSession` — the revocation endpoint for session-level response |
| `oauth.RefreshTokenStore` | `DeleteFamily` — the revocation endpoint for token-family response |
| `cluster.Bus` | `KindTokenRevoked` — cross-replica broadcast so a suspension on one replica propagates |
| `conditionalaccess.Policy` + `Evaluate` | Policy engine that already evaluates RiskScore + UserMemberOf + DeviceManaged. Could be extended with `ThreatType` conditions |
| `spi.RiskScorer` | Synchronous risk on auth path — NOT changed. New executor feeds the *state* (session suspension) that the RiskScorer can check |

## 4. Design: Threat Executor SPI + Policy Engine

### 4.1 New Package: `domains/threataction/`

### 4.2 Core SPI

```go
// Threat is one actionable signal — produced by either anomaly.Detector
// or tokenanomaly.Detector and consumed by a ThreatExecutor.
// It carries everything the executor needs to decide AND act.
type Threat struct {
    // Type matches anomaly.Signal.Type or tokenanomaly.Finding.Type.
    Type string // "impossible_travel", "velocity_burst", "rate_spike", etc.

    // Severity mirrors anomaly.Signal.Severity.
    Severity string // "info", "warn", "critical"

    // SubjectID is the affected user.
    SubjectID string

    // ClientID is the OAuth client, when scoped to one client.
    ClientID string

    // FamilyID is the refresh token family, when the threat is token-scoped.
    FamilyID string

    // TenantID scopes the action to a tenant.
    TenantID string

    // Evidence is structured detail from the detector (same as
    // anomaly.Signal.Evidence). Used by policy evaluation for
    // conditional matching (e.g. "only suspend when evidence.distance_km > 5000").
    Evidence map[string]string

    // TraceID for log correlation.
    TraceID string
}

// Action is one response action to execute. Multiple actions can
// result from one Threat (suspend session AND notify admin).
type Action string

const (
    ActionNoop       Action = "noop"        // log + metric only (current behavior)
    ActionSuspend    Action = "suspend"     // suspend user session(s)
    ActionRevoke     Action = "revoke"      // revoke refresh token family
    ActionStepUpMFA  Action = "step_up_mfa" // tag session for MFA on next login
    ActionNotify     Action = "notify"      // send admin notification (email/webhook)
    ActionChallenge  Action = "challenge"   // require additional verification next auth
)

// ThreatPolicy maps one threat class to an action. Evaluated by the
// executor BEFORE executing — if no policy matches, default is Noop.
type ThreatPolicy struct {
    Name       string
    Enabled    bool
    Type       string   // glob pattern? "impossible_travel", "impossible_travel/critical"
    Severity   string   // empty = any; "critical", "warn+critical"
    Action     Action
    // RateLimit caps how often this action fires per (subject, type) per window.
    // Prevents notification storms on a flapping detection.
    RateLimit  *RateLimitPolicy
    // Conditions is an optional expression over Threat.Evidence.
    Conditions ThreatConditions
}

type RateLimitPolicy struct {
    PerWindow time.Duration
    Max       int
}

type ThreatConditions struct {
    // KeySelector is an Evidence key; operator means "value must match".
    // Empty = unconditional.
    Key      string
    Operator string // "eq", "gt", "lt", "exists"
    Value    string
}

// ThreatPolicyStore persists policies. Admin API CRUD.
type ThreatPolicyStore interface {
    List(ctx context.Context) ([]ThreatPolicy, error)
    Get(ctx context.Context, name string) (*ThreatPolicy, error)
    Put(ctx context.Context, policy ThreatPolicy) error
    Delete(ctx context.Context, name string) error
}

// ThreatExecutor maps a single Threat into one-or-more Actions,
// consulting the policy store. Executed off the request path.
//
// FAIL-OPEN: a threat-executor error (store unavailable, action
// backend timeout) MUST NOT escalate — it is logged, metric'd,
// and the next threat proceeds. A single broken executor
// (e.g., SMTP server down) must not block session-revocation
// executors from acting on the SAME threat. To satisfy this,
// the Executor SHOULD return a partial-results error (one
// action succeeded, another failed) rather than failing
// all-or-nothing.
type ThreatExecutor interface {
    // Name identifies this executor in metrics + audit events.
    Name() string

    // Execute runs the applicable action(s) for the threat.
    // Returns the actions actually taken and any errors per action.
    Execute(ctx context.Context, threat Threat, policy ThreatPolicy) (ActionResult, error)
}

// ActionResult reports what was done.
type ActionResult struct {
    Action  Action
    OK      bool
    Detail  string // human-readable: "session s_abc123 suspended"
}

// ThreatExecutors is a composite executor that:
// 1. Looks up matching policy (first-match wins, ordered by name)
// 2. Rate-limits per (subject, type, action) tuple
// 3. Executes via the appropriate handler
// 4. Records an audit event for every non-Noop action
type ThreatExecutors struct {
    policies ThreatPolicyStore
    handlers map[Action]ThreatExecutor // one per action type
    // ...
}
```

### 4.3 Wiring into the Existing Runner

The key architectural question: **detection→response wiring at what level?**

**Option A: Callback in `anomaly.Runner`** (minimal change)
- Add `ThreatExecutor` field to `Runner`
- In `Runner.inspect()`, after the `Sink.Record` call, call `executor.Execute` for each `Signal`
- `tokenanomaly.Detector.Analyze()` similarly calls executor for each `Finding`
- **Pro:** Minimal new code. Zero new abstractions. ~50 lines changed in `runner.go`
- **Con:** Two separate call sites (`anomaly.Runner` + `tokenanomaly.Detector`). If a third detector type emerges, must remember to wire there too. Policy lookup duplicated.

**Option B: `DetectionPipeline` abstraction** (cleaner, more change)
- New `DetectionPipeline` wraps the `Runner` + `tokenanomaly.Detector` + any future detector. It owns:
  - The per-detector routing table (which threat types → which executor)
  - The shared `ThreatPolicyStore`
  - The rate-limiter
- Detectors emit `Threat` events (not just `Signal`/`Finding`) into a shared work queue
- Pipeline has its own worker pool that runs policy matching + executor dispatch
- **Pro:** Single routing point. Easy to add new detector types. Clean separation between "detection" and "response". Audit trail unified.
- **Con:** New abstraction layer. More code. Need to convert `anomaly.Signal` and `tokenanomaly.Finding` into a common `Threat` type.

**Recommendation: Option A for the first iteration, with an interface shape that allows Option B later.**

Rationale:
- The existing detectors are stable and finite (anomaly.Detector for login events + tokenanomaly.Detector for token usage). No third detector type is queued.
- Option A can be done in ~200 lines of Go across two files. Option B is ~600 lines.
- The `ThreatExecutor` SPI is the same in both designs. Migration path: Option A → if a third detector emerges, extract into a `DetectionPipeline` that wraps the original Runner + new detector + executor. No breaking change.

### 4.4 Concrete Action Implementations (first wave)

| Action | Implementation | Dependencies |
|---|---|---|
| `suspend` | Call `SessionManager.SuspendSession(ctx, subjectID)` | `session.SessionManager` |
| `revoke` | Call `RefreshTokenStore.DeleteFamily(ctx, familyID)` + cluster Bus broadcast | `oauth.RefreshTokenStore`, `cluster.Bus` |
| `step_up_mfa` | Set a `step_up_required` flag on the session metadata (read by the authenticator pipeline on next auth) | `session.SessionManager.SetMeta()` or a dedicated `StepUpStore` |
| `notify` | Emit a structured `audit.Event` + optional webhook POST | `audit.Recorder` (already exists), webhook dispatcher (existing) |
| `challenge` | Tag the session requiring re-auth with a specific method (FIDO2, TOTP) on next access | `session.SessionManager` |

### 4.5 Integration with `tokenanomaly.Detector`

The `tokenanomaly.Detector.Analyze()` method is a periodic sweep (called by a timer, not event-driven). For the Active ITDR bridge:

- `tokenanomaly.Detector` gains an optional `ThreatExecutor` field
- After emitting each `Finding` to the FindingStore, if executor is set, convert Finding → Threat and call executor
- The detector's existing `onFinding` metric hook pattern already shows this design pattern — the executor hook follows the same shape

```go
// In tokenanomaly/detector.go — new field:
type Detector struct {
    // ... existing fields ...
    executor threataction.ThreatExecutor // new
}

// In Analyze, after each finding:
if d.executor != nil {
    threat := threataction.Threat{
        Type:      f.Type,
        Severity:  string(f.Severity),
        SubjectID: f.SubjectID,
        // ...
    }
    // Best-effort, fail-open
    if _, err := d.executor.Execute(ctx, threat, policy); err != nil {
        d.logger.Error("threat executor failed", ...)
    }
}
```

### 4.6 Cluster-Wide Coordination

Threat actions that affect auth state (suspend, revoke, step-up) MUST propagate across replicas:

- `suspend` → `cluster.Bus.KindTokenRevoked` (reuse existing bus message kind; rename is out of scope)
- `revoke` → Same `KindTokenRevoked` (already exists)
- `step_up_mfa` → May need a new bus kind (`KindSessionPolicyChange`) or piggyback on existing session state

**Design decision:** For wave 1, only `suspend` and `revoke` are cluster-aware (existing bus kinds). `step_up_mfa` and `challenge` use a shared store (Redis) or are best-effort single-replica for now.

## 10. Implementation Roadmap

### Phase 1 (P0) — Core SPI + Memory Store + Runner Integration
- Define `Threat`, `Action`, `ThreatExecutor` SPI
- Implement `ThreatPolicy` + `ThreatPolicyStore` interface + `MemoryThreatPolicyStore`
- Implement `ThreatExecutors` composite with policy matching + rate-limit + audit recording
- Wire into `anomaly.Runner.inspect()` (Option A)
- Wire into `tokenanomaly.Detector.Analyze()`
- All tests pass, `make acceptance` green

**Risk:** Low. All new code, no existing path modified. The `anomaly.Runner` changes are additive (nil-check on optional executor).

### Phase 2 (P1) — Action Handlers (suspend + revoke)
- Implement `SuspendSessionExecutor` using `SessionManager.SuspendSession`
- Implement `RevokeFamilyExecutor` using `RefreshTokenStore.DeleteFamily`
- Cluster bus broadcast integration
- Integration tests: wire a real detector → executor → verify session revoked

**Risk:** Medium. `DeleteFamily` is fail-closed by design currently — executor calls it off-path, which is a different context. Must ensure the executor's closure semantics are correct (session suspended even if executer errors → logged, not retried).

### Phase 3 (P2) — Admin Policy API
- CRUD endpoints for `ThreatPolicyStore`
- Admin gating (`admin:write`)
- Default policy (sensible out-of-box: critical → suspend + notify; warn → notify; info → noop)
- OpenAPI documentation

### Phase 4 (P2) — Step-Up + Challenge Actions
- `StepUpMFAExecutor`: tags session metadata
- `ChallengeExecutor`: requires re-auth with specific method
- Cluster bus `KindSessionPolicyChange` for cross-replica propagation
- Conditional Access integration: add `ThreatType` condition to `conditionalaccess.Conditions`

### Deferred (not in scope)
- `notify` action handler (webhook/SMTP already exists via audit sink — executor records audit event, existing webhook pipeline picks it up)
- Machine-learning severity tuning
- SIEM-specific output formatting
