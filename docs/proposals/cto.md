## Decision: PROCEED WITH CONDITIONS

**1. Executive summary.** This is a maintainability refactor of the security-critical admission pipeline — real but internal value: compile-time order safety for a 12-slot chain, one construction site replacing seven hand-written functions, relief of genuine budget pressure (10-file ceiling, `server_routes.go` at 488/500). The design's structural verification is impeccable — I independently confirmed every budget, line count, signature, and ordering claim. But **all four adversarial reviewers independently found the same HIGH flaw (F1)**, and my own re-verification confirms it: the Tracing relocation breaks a deliberate anti-enumeration invariant documented at `router.go:244-253` ("stamp response headers a genuinely-unmatched request never gets") and hardened in 7+ committed tests in `feature_gate_hotreload_test.go` (including a `t.Fatalf` sanity check). The design misses it entirely and mischaracterizes the delta as "a fix" — the delta list is also wrong (omits 404s/400s; "panic responses remain header-less" is factually false in both states). As written, it ships a red suite.

**2. Resolution is cheap and lossless — Option A:** keep request-ID stamping on `Router.Use`; the chain's Tracing slot hosts OTel only. Every invariant, every committed test, and all spec §1 goals survive. The only thing lost is the rejection-path correlation-header side effect, which was never a requirement — if product wants it, that's a separate deliberate change, not a refactor sidecar. Also trim M3: the Tracing/Logger/Idempotency signature migrations exist only to satisfy a grep acceptance that fights the router's own design (`core.MiddlewareFunc` route-level middlewares are inherent; `shared/core` is untouched per spec). Idempotency migration should be deferred — zero call sites, and per security F3 it's a protocol re-wiring (handler-side commit), not a signature change.

**3. Contrary case considered.** No user-visible value; touches the highest-security surface; the dual-signature tax is largely architectural, so the "single signature" goal is partly chasing the wrong target. This argues for trimming scope (Option B — M1+M2 only — is the fallback), not stopping: budget pressure is real, order-safety value compounds, and the marginal cost after Option A is ~1 new file + a bounded, enumerable test rewrite (~1.3k lines across 4 test files).

**4. Conditions before M2:** F1 resolution recorded; spec §2 acceptance re-scoped; `FromCore` amended per F2 (pass `ctx.ResponseWriter()`/`ctx.Request()`, writer-identity regression test); test-(d) stub mechanism specified (`middleware.Auth` is deleted by the same change — architect finding 3); SDK break (`sso.AuthMiddleware`/`sso.CORS`, zero in-tree consumers — verified) explicitly product-approved or split to a later release; same-change docs per AGENTS.md §5.6 (`observability.md` stack diagram is *already* drifted — fix it here; stale `cors.go:5` comment). Exit criteria, non-goals, and a 6-decision owner table are in the doc.

**5. Top risks:** (1) suite-weakening drift on F1 — the feature-gate tests must stay green *unchanged*, with a negative control that fails on any divergence; (2) FromCore writer bypass silently degrading replay control — spec amendment + writer-identity test; (3) Idempotency re-wiring losing its oracle-safe position — defer; (4) budget regressions (`Wrap` cyclo ~13–14/15, `server_routes.go` realistic landing ~440–465) — documented growth path via fixed-order array; (5) test-churn inventory undershoot — enumerate all ~16 ctx call sites in `middleware_extra_test.go`, delete the now-unused `fakeContext` harness; (6) `WithProbes` ServeMux pattern-panic footgun — document only.

Advisory only — maintainers and business owners retain approval authority.
