Design doc written to `docs/auto/domains-tokenanomaly-direction3-design.md`. All evidence in the spec was verified against the code, and the doc makes **six decisions** under the requested headings (API surface, storage model, failure modes, breakage analysis):

## Decisions

- **Decision 1 — API surface**: `metering.Event.FamilyID` + the `RecordRefreshTokenIssued` seam gains `familyID string`. Verification found the spec's file list **incomplete**: the method is declared in *six* interfaces and called at *six* sites. `token_device.go` (decl :29, call :169), `token_exchange.go:67`, and the `token_ciba_test.go:70` fake all break `go build` if omitted. Audit event deliberately unchanged (family already flows via reuse/velocity audit events).
- **Decision 2 — production reachability (the critical gap)**: issuance events — the only ones the new seam feeds — carry **no thumbprint** (jti minted inside the issuer), so they can never enter the thumbprint-keyed observation table. Without an extra change, Improvement 2's family-scoped revoke stays a permanent no-op in production. The fix: one telemetry-only field at `protocols/oauth/handle_introspect.go:358`, where `info` is the full `RefreshToken` record (`info.FamilyID` in scope, verified via sqlite `Inspect` return type). `JTI` and `FamilyID` propagate together through rotation, making thumbprint↔family 1:1. The doc reconciles this with the spec's "do not modify protocols/oauth" line (wire-contract intent, not a blanket ban) and flags descope risk if refused.
- **Decision 3 — API surface**: `Finding.FamilyID` (omitempty), `dispatchThreat` fills `Threat.FamilyID`, `evidenceFor` gains `family_id`; `RevokeFamilyExecutor` untouched — only reachability changes. `DedupKey` stays valid because family is stable per thumbprint.
- **Decision 4 — storage model**: no `Bucket` dimension (Event field ignored by stores, no migration); detector-local capped `subjectMinuteRates` table in `detect.go` (155 lines today, per the spec's placement rule), fed from all subject-bearing `Record` events, `WithMaxTrackedSubjects` (default 4096), oldest-minute eviction + sweep-time window pruning to bound per-row memory.
- **Decision 5 — windowed spike**: prefix-baseline scan per minute (latest-minute behavior byte-identical), one finding per client per sweep across both dimensions — this resolves a **DedupKey collision** I found: subject-scoped findings would key identically to client-scoped ones (`rate_spike\x00<client>`), silently overwriting each other in the store.
- **Decision 6 — invariants**: zero-value byte-identity, fail-open, import direction.

## Key failure modes / breakage risks documented

Repeated threat dispatch while a burst minute stays in-window (idempotent, accepted), consecutive-burst baseline dampening, subject-spike revoke being subject-wide by correct construction, the spec's incomplete file list, `Detail` wording drift for rate_spike (the byte-identity claim doesn't cover it), `server_helpers.go` budget drift with the spec's own escape hatch, and the one-per-client rule being load-bearing.

No `.go` files changed, so no mandatory Go gates were triggered; the doc ends with the full verification plan from the spec.
