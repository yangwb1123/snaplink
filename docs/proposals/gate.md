# Gatekeeper cross-check: review findings vs. the design

## Resolved or correct in the design (reviewers agree)

- **grpcadmin fan-out relocation** → `grpcserver/sod_admin.go` (6→7/10) — all four reviewers verified the counts; the relocation is mandatory and wire-neutral.
- **`session_id = 6` reservation**, additive `SoDAdminService` under ADR-0008, `ConflictDetails`-as-details oracle-safety, non-retroactivity documentation, migration v2 append-only, `invalidateAuthzPolicy` on declarations (perf L1 notes the bundle contains no SoD content, so the bust is pointless-but-harmless — rationale error, not blocking).
- **DB F4** (postgres SERIALIZABLE vs FOR UPDATE): partially addressed — the design permits SERIALIZABLE and pins the conformance subtest as arbiter; reviewers verified the peer already uses `runTx(serializable)+40001`. Acceptable as an implementation instruction, though "verify" should become "pin".
- **Postgres env-gating (DB F1), redis hash-tag/`{user}` (DB F2), sqlite busy_timeout (DB F3), TTL/sweep anchor, memory retention, no-retry deny amplification, liveness coupling, cross-client admin binding, permanent DSoD lockout, bootstrap-fallback parity**: **unresolved** — the design either asserts an "existing maintenance cadence"/"OIDC session lifetime" that has no named source, or inherits the pre-existing property silently. Mediums, not individually blocking, but none are addressed.

## Blocking issues — not resolved in the design

1. **The enforcement consumer is unbuildable as specified (step 3's core).** The design's "Consume: the mesh gate passes `session_id` into `Check`" matches no call graph — `MeshAuthorize` performs no permission evaluation, and the design specifies no mechanism (which permission, what the verdict does in the ALLOW/DENY seam, store-down mapping). `X-Auth-Roles` stays the full assigned set, so DSoD stays inert in the exact topology the bundle targets. The claim "the only first-party caller that ever populates `session_id` … so the row is unreachable from shipped code" is false as written: the open `Authorizer` RPC and `ssoclient/remote/authz.go` call `Check` today, and `ssoclient.CheckRequest` has no `SessionID` field the design never mentions. The fail-open→fail-closed availability flip on the mesh path is unacknowledged. (Security F1, Protocol F-3, Distributed F1, QA F2, Perf H1.)
2. **Spec/design contradiction on post-`DeactivateSession` semantics, unflagged.** Spec §3 acceptance: session-scoped `Check` "falls back to the assigned set"; design pins DENY and claims it only "fills the row the spec left open" — it actually overrides an explicit acceptance sentence. A test written from the spec fails against the design. Must be reconciled in both docs. (Protocol F-1, QA F3.)
3. **The spec's headline acceptance test is unpassable as designed.** Spec acceptance drives the existing `PermissionAdminService.AssignRoles` → FailedPrecondition with offending codes; today it maps `ErrRoleConflict` → `codes.Internal`, and the design declares `admin_permissions.go` "untouched" while its error table covers only the new service. The existing RPC needs the same mapping (or the acceptance criterion must move). (Protocol F-2.)
4. **Activation hook is cited at the wrong code path.** `accessors_handlers.go:69` is inside `EnforceSilentRenewalPolicy`; interactive-login sessions (the primary flow, sid minted at `server_login.go:122`) never pass through it — every session-scoped check would deny until the first silent renewal, and wiring there would re-activate the full set over an operator's mid-session narrowing on every refresh. (Protocol F-4, Distributed F2.)
5. **Deactivation "everywhere the sid is already in hand" is false for two of three hooks.** `handle_end_session.go:193` calls `RecordLogout(ctx, "", ...)` (empty sid, though sid is in scope), and admin logout has no session field on the `AdminToken` record. The design's own cleanup wiring would deactivate nothing on those paths. (Protocol F-5.)
6. **Partial-revocation leaves stale grants in the ACTIVE set.** `stripActiveRole` is called only from `RemoveRole`; `UnassignRoles` and `RemoveRoleFromUser` never strip active roles, so an admin unassigning a role mid-session keeps it granting at session-scoped `Check`. The design's cascade covers catalog deletion only. (QA F1.)
7. **The concurrency guard targets an impossible interleave.** `AssignRoles` is a whole-set replace (memory + sqlite), so "two concurrent AssignRoles both pass the check and interleave" cannot happen and the named subtest would never fail; the real delta race is `AddRoleToUser` (load-append-store). The txn requirement mentions `AddRoleToUser`, but the rationale, subtest name, and postgres READ COMMITTED exposure must be re-specified around the delta path. (QA F4.)

## Doc-accuracy findings (Low, uncontested, should be corrected in the same change)

Subtest counts 5+6/11 vs actual 10 (5+5, with the GMW skip as a branch inside a subtest, not a separate one); "openapi.yaml regenerated with `buf generate`" (it is hand-maintained; docs-validate is not in `make ci`); `AdminActorFromContext` cited at `options_admin.go` (actually `aliases.go:73`); RPC-name drift vs. the sibling design (`ActivateSessionRoles`/`DeactivateSessionRoles` vs `ActivateRoles`/`DeactivateSession`); `memory.go` doc → nonexistent `memory_sod.go`; committed `memory.go.bak`; `migration_test.go` asserts version==1 twice (breaks at v2); no fifth (login-conflict) audit event named; `ErrUserNotFound` mapping on the session path unspecified; undecided openapi placement of a gRPC-only message; pre-existing `docs/` fan-out 17>16 gate failure (report at handoff; the design's budget section tracks Go only).

**Bottom line.** The design is sound where it is gate-aware (placement, proto additivity, oracle-safe errors, migration ordering), and several review findings are genuinely resolved by its own corrections. But the change's raison d'être — step 3, enforcement — is specified against code that does not do what the design says (blockers 1, 4, 5), two committed documents contradict each other on the core decision (blocker 2), the spec's first acceptance test cannot pass (blocker 3), and the revocation and concurrency stories each have a hole that makes a headline subtest vacuous or a stated guarantee false (blockers 6, 7). None of these are implementation-stage choices; they are design-level defects the reviews independently converged on. The design must be revised (and the spec amended) before implementation.
