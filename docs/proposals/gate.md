**Unresolved — blocking:**

1. **H1 — Multi-replica divergence unguarded, and the design's mitigation claim is factually wrong** (Proto F-1 High, DS F-2 High, Sec F2, SRE F1 High). Design Decision 4 states "the reactions revoke per-replica credentials — the gates inherit, not worsen, this", and risk 10 claims "the refresh gate narrows the blast radius (families die on every replica's next rotation attempt)". Reviewers verified the opposite: no-record = ACTIVE means replica B's *gate allows* indefinitely; only families already deleted from a *shared* store by A's reaction die. No `haCoherenceIssues` entry, no boot refusal, no single-replica/restart=un-suspension statement in `config-reference.md`. The design has not corrected its own wording.
2. **H2 — Sync reactions run on the admin request ctx** (DS F-1 High, Sec F3, SRE F3 High). Decision 3.2's headline "the admin response implies revocation completed" is false under client disconnect/gateway timeout: `Append` committed, revocation canceled mid-flight, retry is a `409 lifecycle_state_conflict` trap, recovery requires a spurious suspend→activate→suspend dance. No `context.WithoutCancel` (in-repo precedent) anywhere in the design.
3. **H3 — Token-exchange and device-secret chains bypass suspension, absent from the design's residual list** (Sec F1, Arch F3, SRE F7). `HandleTokenExchangeGrant` mints fresh-TTL tokens hop-by-hop with the chain cap default-off; `HandleDeviceSecretExchange` never checks liveness. Design risk 6 names only the auth-code gap; Decision 3.3's "ChainStore cut" is a different (reaction-leg) matter. No decision, no residual entry, no remediation.
4. **M1 — The D1 helper API cannot serve site 4** (Arch F1, Sec F7). `rejectLifecycleBlockedUser(ctx, req *login.Request, userID)` writes 403 `account_locked` with `req.State`; `finalizeCallbackSession` has no `req` and needs 401 `callback_failed` + `recordCallbackFailure`. The design's table records the shape difference but its API does not parameterize it, and a second helper blows the budget (486+30+15=531 > 500). Internal inconsistency — the implementer must improvise.
5. **M4 — Per-client revocation loop retained despite the SPI's revoke-across-every-client form** (Proto F-2, Perf F-1). Design 3.1 reuses the `clients.List()` + per-client `DeleteAllForSubject` loop: a `List()` error deletes zero tokens (violating "never less locked out"), de-registered clients' tokens survive, and 10k clients ≈ 10k+1 serialized RTTs on the admin path (≥10 s at 1 ms RTT, past gateway budgets). `DeleteAllForSubject(userID, "")` is strictly stronger, precedented (`interfaces/admin/users.go:399`), and the same code change fixes the performance finding.
6. **Owner decisions unratified** (principal §5; arch §5). Six binding unknowns — fail-closed posture, exchange parity, INVITED semantics, direction-3 commitment, restore-from-archive UX, 423-vs-403 intent — have no sign-off anywhere in the tree, and they change contract text. The principal review's precondition is explicit: "Do not start Milestone 0 before these are recorded."

**Partially resolved (documentation amendments, Medium):** M2 refresh burn-and-kill on *store-error* denials (design documents after-`Consume` + retry-kills-family and the login-side outage, but not the outage×retry interaction for healthy users); M5 `openapi.yaml` omitted from the design's contract-update list (error-codes.md 423→403 is covered); M6 crash-window at-most-once semantics undisclosed (failure-mode table implies contained failure when it is silent); M7 sweep-driven ARCHIVED clock-jump blast (design declares the behavior "an improvement" but never documents the clock assumption, `max_per_sweep` default-0, or a transition metric); M8 QA reactivation acceptance not E2E-constructible (needs the two-token fake unit choreography; three fixtures unnamed).

**Bottom line**: every review concurs the design's mechanics are sound and the findings are *amendments, not re-architectures* — but the design as written contains one factually wrong security-invariant claim (H1), two gaps in its own disclosure list (H2's cancellation caveat, H3's bypass paths), an internally inconsistent helper API (M1), a weaker-than-available revocation leg (M4), and six unratified owner decisions. The principal review's own verdict is "conditionally ready — it cannot ship as written", with P1–P7 as pre-implementation preconditions. None of these are absorbed in the design file (it predates every review; no revision exists). Implementation must not start until the design revision lands.
