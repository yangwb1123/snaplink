### Findings per claim

**1. Array indices — claim holds.** `diffValue` recurses only when *both* sides are `map[string]any` (`diff.go:72-77`); `[]any` values are whole-value `replace`d at their own path, never traversed. Fuzz reconstruction independently confirmed: every emitted path resolves through object-only intermediates in `before`, at any array nesting depth. Keys literally named `0`/`-` emit `/0`/`/-` — ordinary object keys per RFC 6901 §4 (the `-` array special case is defined only for arrays), correctly accepted by the map-only resolver.

**2. "Can never contain empty keys" — false as literally stated; the intended invariant holds.** The emitter *does* emit empty-key segments: key `""` at root → `"/"`; nested → `"//x"`, `"///z"`, and `add` → `"//"` (all reproduced by the real emitter in directed tests). The literal conjunction in the task is wrong on this limb; E5a/D-A already sharpened this, and the design resolves `"/"` by key lookup rather than path-length rejection — confirmed correct and false-reject-free (fuzz includes forced `""` keys at depths 1–3).

**3. False rejects by the map-only, object-only-intermediate validator — zero.** 200k pairs, zero `validatePatch(Diff(before, after), before)` failures. Key boundaries verified: replace at map/null/array-valued leaves (type-change emission, `diff.go:79`), `add` parent = root for single-segment paths, `remove`/`replace` leaf existence only, empty patch valid. Emit-side reconstruction also confirmed op/location semantics exactly (`remove` ⇔ in before only, `add` ⇔ in after only, `replace` ⇔ both).

**4. Split-before-unescape — RFC 6901 §4-correct.** The RFC's evaluation is split-on-`/` first, then per-token unescape (`~1`→`/`, `~0`→`~`); unescape-first would inject fake separators (the `/a~1b/c` trap — 2 tokens, not 3, verified). The strict left-to-right scanner is equivalent to the RFC's two-pass transform on every emittable form (`~01`→`~1`, `~10`→`/0` verified) and additionally rejects `~2`/trailing `~`, which the server's escape (injective: `~`-first-then-`/`, `diff.go:87-92`) can never produce — rejection is therefore exactly the unemittable set.

**5. `'/'` empty-key lookup and injectivity — sound.** `"/"` is a single empty token per RFC 6901; the root (`""`) is never an op target (ops only at `childPath`), so no `""`/`"/"` ambiguity exists. Location→path is injective: escape is injective, escaped segments contain no `'/'`, and `Split` recovers tokens deterministically — verified exhaustively over the alphabet and via round-trip rebuild of every emitted path (200k×). False-accept class is bounded by the documented over-approximation (D-B): resolvable-but-unemitted shapes, e.g. `add` at an existing key — benign since the controller only counts ops.

**6. Panic risks — none found, two implementation-order cautions.** The validator as specified uses ok-checked assertions, no index arithmetic, and is iterative (100k-segment paths, `~` floods, `\x00`/`\xff` bytes: 100k cases, zero panics). Cautions for the implementer: (a) rule 2 must check `op.Path == ""` *before* `op.Path[0]`; (b) the tilde scanner must bounds-check `seg[i+1]` before reading (trailing-`~` case). Both are trivially satisfied by the design's stated rule order but worth pinning in review.
