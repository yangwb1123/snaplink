## Verdict: sound direction, two material corrections, two additions

**1. Bounded cardinality — FAIL as worded.** `RejectUnregistered` (`reject.go:35-47`) rejects exactly when `!reg.Registered(s)`, so the rejected scope is *by construction* not in the registry — a "per-scope" label is request-borne attacker input (unbounded), and a label keyed by registered pattern can never fire. The contract's "no per-path/per-user labels" plus the `WithTenantMetricsAllowlist` precedent ("len(allowlist)+1, never the unbounded set") point to the correct shape: `sso_scope_registry_rejections_total{grant_type}` — the fixed grant vocabulary, matching the `sso_tokens_issued_total{strategy}` analog.

**2. Oracle / response-surface — PASS only with the refined labels.** `/metrics` is served by `buildProbeMux` on the **same listener as the API**, unauthenticated, outside rate limiting (`server_routes.go:479-481`). A requested-scope label would make it a registry-complement enumeration oracle. Grant-type labels leak nothing per-scope; responses stay byte-identical, no trace_id in body (A-8f), zero new `Err*`/audit events — the review's "no wire change" half holds.

**3. W3C trace correlation — compatible but thinner than claimed.** The counter increments synchronously in-request (no detached span). But the observability.md line "covered by the existing per-request logging" is materially weak: `middleware.RequestLogger` is DEBUG-level opt-in, has **no trace_id field**, and body logging is contraindicated on `/token` (bodies contain tokens). Server-side, a rejection has *no per-event record by default*. The counter makes R-2 *detectable* (spike) but not *identifiable* — "which scope is wrong" needs a bounded seam log line (`grant_type`/`scope`/`trace_id`; `core.TraceIDFromContext` is available at the seam).

**4. Mixed-version fleet — counter alone is NOT sufficient.** A flat-zero counter is indistinguishable across "old binary skips gate" / "gate off" / "no traffic", so fleet-sum rejection = 0 is not proof of drain. The missing piece is a boot-seeded `sso_scope_registry_enabled` gauge (the exact `sso_feature_gate_enabled` pattern, always registered by new binaries): per-target state = absent (old binary, R-3 detected) / 0 / 1. With it, flip/soak/rollback claims become computable per pod, and window-period sums are read only against each target's gauge state (OFF pods mint invisibly, so ON-pod rejections are a lower bound of the burn asymmetry). Bonus: the registry is frozen/build-once, so the gauge cannot go stale the way `sso_feature_gate_enabled` does on SIGHUP.

**5. Contract status — the review understated it.** `docs/observability.md` currently pins "no new audit event type and **no new metric**" for scope-registry rejections — written by this design's own docs rows. The counter is a deliberate public-contract amendment (metrics table rows + paragraph rewrite + fixing the "per-request logging" claim), not "contract-respecting, additive". Delta is small and layer-legal: all 9 call sites funnel through `RejectUnregistered` (one increment site), `RefreshGrantDeps` already carries a Metrics handle, protocols→platform is an allowed import.

Bottom line: adopt the counter **class-labeled + gauge + seam log line**, and amend observability.md in the same change — then drain/rollback verifiability across a mixed fleet is real; as literally recommended ("per scope", "additive"), it would violate the contract and add an oracle.
