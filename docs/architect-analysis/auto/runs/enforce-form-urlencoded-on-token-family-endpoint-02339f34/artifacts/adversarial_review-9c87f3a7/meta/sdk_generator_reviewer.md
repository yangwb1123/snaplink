Validation complete. All six design claims were checked against the generator templates, the committed clients, the bind implementation, and the OpenAPI consumers. Findings below, anchored to evidence.

## Per-item verdicts

**1. Repeated-key encoding parity with `net/url.ParseForm` — CONFIRMED, with one real gap (G1).**
Server semantics (`protocols/oauth/oauthwire/bind.go`): repeated keys land in `url.Values`; `setFormField` takes `raw[0]` for strings, the whole slice for `[]string` (`formStringSlice` also splits a single space/comma value). The `[]string` fields on all four endpoints are exactly `TokenRequest.resource/audience` (`token_request.go:25,32`), `PARRequest.resource`, `IntrospectRequest.tokens` — repeated-key encoding is the correct parity choice, and both `URLSearchParams.append`-style and `urlencode(doseq=True)` produce `+`-for-space which `ParseQuery` decodes back. Empty arrays → no keys → nil field, equivalent to today's `[]`. Order is irrelevant to the server.
**G1 (significant): PAR's `authorization_details` (RFC 9396) and `claims` (OIDC §5.5) are silently lost under form-only.** `parRequestForm.AuthorizationDetails/Claims` are `json.RawMessage` (`handle_par.go:100,105`); `setFormField` has no case for them, so the form path drops them — today JSON callers bind them, `validatePARRequestParams` runs the RFC 9396 gate (`handle_par.go:222-227`), and `issuePARRequest` stores them (`:241,251`). After migration every caller (including both SDKs, which today send JSON) loses them without any error: RAR constraints and claims requests vanish silently. The design's F1–F8 and compatibility list don't cover silent parameter loss. RFC 9396 §3.1/OIDC §5.5 prescribe a JSON-string value for these params in form contexts — the design needs a decision: (a) server-side RawMessage-from-JSON-string binding + clients `JSON.stringify` object-valued fields in form mode, or (b) explicit unsupported + openapi `PARRequest` schema/description adjustment. Either way, add a regression test; today's TS client exposes `authorization_details?: AuthorizationDetail[]` and `claims?: Record<string, unknown>` on `postPAR` (client.ts:1143-1145), Python likewise (client.py:927-928).

Non-string values confirmed mangled: list-of-dicts → `str(dict)` per element; a dict value iterates its **keys** (`claims={'id_token':…}` → `claims=id_token`) — same G1.

**5. emit-test negative-set coverage — ADEQUATE with one explicit gap.** `TestTSClientAuthenticationOperations` (emit_test.go) covers 4 positive + `postLogin`/`postLogout` negatives — both body-carrying JSON ops, good representatives. `TestGenerateTS_ConfidentialAuthAndStrictOptionalTransport` is at emit_test.go:207 with `{ body, clientAuth: true });` at :231 exactly as the design says — it **must** flip to `{ body, clientAuth: true, form: true })` or the suite goes red. **G4: there is no Python generation test at all** (`TestGeneratePython*` absent); M5's "extend TestTSClientAuthenticationOperations-style tables" must include a *new* Python emission test pinning `form=True` on the four ops and its absence on `postLogin`/`putRegistration`/device ops. `postRevokeAll` (no body) is a weak emission-negative; `postLogin` is the strong one.

(c) The generator reads the *embedded* spec (`docs.OpenAPISpec`, `go:embed openapi.yaml` in the `docs` package, main.go:60-62), so M6→M7 order is harmless (embed refreshes at `go run`; identical schemas anyway). `docs/docscheck/` has no content-type or servers assertions (grep-empty), confirming E7/C4's docscheck claim. ## New drift/gaps beyond the design's C1–C6

- **G1 (blocking-ish): PAR `authorization_details`/`claims` silent loss** — see item 1. Needs a decision and a test; currently both SDKs and the server's JSON path bind them, and form-only would silently break RFC 9396 RAR and claims requests.
- **G2: the "second committed client tree" is not committed.** `ops/deploy/openresty/fullstack/static/docs/sdks/` is **untracked** (`git status` → `??`, empty `git ls-files`/`git log`, not ignored either) — it's stale VitePress-style static-site build output (no `FetchLike`/`clientSecret`/`requestTimeoutMs`/`clientAuth`; pre-`9f0b74c3` generation), and nothing in the repo references or syncs it (no script, Makefile target, workflow, or nginx conf mention). M6's scope (docs/sdks only) is consistent with the repo; the design should state this explicitly so no one assumes a sync obligation or treats the stale copy as drift.
- **G3 (minor): None/undefined values.** Python `doseq=True` encodes `None` as literal `"None"` and TS `String(undefined)` similarly, vs JSON `null`/omission today. The form encoders should skip nullish values (the query paths already filter them in both clients).
