Every citation was re-verified against HEAD in this review (no code changed). Verdicts on the four points:

**1. Semantic asymmetry — BLOCKING (High).** The "documented" asymmetry is unobservable on the wire: with `omitempty`, empty-roles and roles-not-emitted are the same absence, and four internal states collapse into one shape (non-member / lookup failure / token-endpoint path — plus the fact that a member always has a role, `TenantRoleMember`). Worse, `mintAccessToken` is the direct-mint login branch only (single caller, `server_login_client.go:388`); the first refresh rotation re-mints via `refreshRotatedSubject` (`token_refresh.go:287`), which preserves AMR/ACR/AuthTime per the chain-preservation discipline but would silently drop roles — an RP re-evaluating per token sees roles vanish mid-session. And because **all ten** other mint seams already stamp `Subject.TenantID`, token-endpoint tokens will carry `tenant_id` but never `roles` (including client_credentials with no user). Oracle-safety itself is not violated (absence collapses identically); the harm is RP-side authorization drift. Required: thread roles through the chain, or pin the absence as a tested wire contract (code-exchange + refresh-rotation ACs), plus an explicit collapse table in the failure modes.

**2. Fail-open `subjectRoles` in `mintAccessToken` — BLOCKING (High).** The seam precedent (`server_oauth.go:202`) is distinguishable: there roles only feed a *deny* decision, so fail-open = "don't deny" and nothing leaves the server degraded. Here the degraded artifact *is the deliverable* — a valid, verifiable token with an authorization input silently omitted, and introspection can't echo it (`claimsFromPayload` drops it, verified). The fail-open list (geo/trust/audit/suspension-lookup) is advisory; roles is the same category as scope, which is fail-closed. The design must explicitly reconcile this, and add an audit event (details-only-in-audit discipline) since a log-only outage is forensically unrecoverable.

**3. Keying on `result.UserID` — PASS with a required pin (Medium).** Operationally it's the only correct choice (`TenantUserStore` is keyed `(TenantID, UserID)`; the pseudonym would fail open to empty — the exact failure `deriveMeshIdentity` guards against at `mesh_authz.go:322`). But `mintAccessToken` computes `issuedSub` *before* the Issue call, so nothing structural prevents a future refactor from passing the pseudonym. Required: helper signature `(ctx, tenantID, userID)` + an AC-6 using a pairwise client. Also document the within-tenant correlation property (identical roles vectors let colluding clients correlate pairwise subs).

**4. Unconditional `tenant_id` — CONDITIONAL, one blocking collision (High).** Consistent with `tenant_mismatch` (gate compares request-context vs client binding; the claim is truthful either way) and suspension (mint-time evidence like `serving_region`; no new oracle). Two contract gaps: (a) **blocking** — `tenant_id` already exists as a *user-attribute* claim name in `ext` (`Extra: subject.Claims` at `issue_payload.go:34`; consumed by `tenantHintFromClaims` at `governance.go:482`), so one token can carry two different `tenant_id` values; the design must state precedence or strip it from `ext`, with a collision AC; (b) the token-exchange path stamps the *exchanging* (guest) tenant, not the subject's home tenant — the claim contract must say "the OAuth client's tenant binding at mint time".

Verified sound (no change): ServingRegion discipline reuse, byte-compat for empty cases, JIT-before-mint ordering, budget placement (server_login.go 469→~492), and the R5 exclusion of introspection/openapi changes.
