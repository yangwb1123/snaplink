# Review: operator-facing surface of the revised deliverable

**Headline finding: the revision was never applied.** The deliverable at `docs/architect-analysis/cmd-sso-ctl-clientscmd-scope-matrix-conformance-requirements.md` is byte-identical to HEAD (`3223d12a`, design stage) — `git diff HEAD -- <file>` is empty, no later commit or branch carries a revision, and no revision artifact exists in the run directory (`add-a-scope-matrix-v2-conformance-view-to-client-b11bdc20` contains only requirements/design/adversarial-review outputs). All four requested verifications were checked against the only version that exists, and **all four fail**. Every underlying code fact I relied on was re-measured at HEAD.

## Ask 1 — Pre-enablement workflow on registry-disabled (default) deployments: FAIL

- **Absent.** The document contains zero occurrences of "pre-enable", "enabled-off", "not enabled", or any registry-enabled qualifier on the verdict contract. The FM table has no enabled-off row.
- **Actively dishonest as written.** §2's completion marker still claims unqualified runtime agreement: *"a scope the CLI rejects is exactly a scope `/token` would 400 for"*. On default-off deployments — confirmed default per `docs/config-reference.md`: *"Default-off: no block (or `enabled: false`) = byte-identical server"* — the server has **no** registry gate (`RejectUnregistered` no-ops on nil registry; `build_stores.go:295-314` wires it only inside the `Enabled` branch), so `validate` exit 1 for `billing:typo` coexists with `/token` minting it. §10.3's adoption guarantee ("cannot introduce a check that … fails while runtime mints 200") carries only the qualifier "for built-in-matrix deployments" — missing the enabled qualifier, which is the axis that actually matters. The scope_security_reviewer's finding #1 was not addressed.
- **Actionable in principle.** The predicate (`NewMemory(Matrix(), nil)`) is exactly the gate an enabled, unprovisioned, no-extras deployment enforces, and `config-reference.md` already documents the enablement order (land matrix with `enabled: false` → pre-flight → fleet-wide flip). The fix is a reframe ("static conformance to the built-in matrix; the pre-enablement target-state gate"), not a redesign — but that reframe is not in the document.

## Ask 2 — stderr distinguishes true drift from documented false-verdict classes: FAIL

- The single offender line (R1.6:154) — `` `sso-ctl clients: validate: scope "billing:typo" is not in the built-in scope matrix` `` — carries **no class qualifier**, and §7 pins only stdout/stderr routing ("offenders on stderr only; stdout carries only `validate: OK`"), not any distinguishing content. An operator cannot tell FM-5/FM-7/enabled-off/version-skew output from true drift; the doc doesn't even claim a discriminator exists.
- **FM-5 is half-labeled**: the Behavior column covers only additions ("may report false positives"); the removals direction (provisioned matrix ⊊ built-in → CLI exit 0 while `/token` 400s, masking drift with CI green) is unlabeled despite the row title mentioning "drops built-ins".
- **No enabled-off row** (the default deployment), **no version-skew row** (the matrix is compiled into both binaries; `config/scope_registry_test.go` shows the table is expected to grow — a mixed-version fleet gets both false directions). The four-quadrant boundary the scope_security_reviewer mapped remains one quadrant in the doc.

## Ask 3 — F1 env-var and F2 message-shape finalized in §7, pinned by U4/U5/E1a: FAIL (both)

- **F1 not corrected**: §3:83-84 ("`SSO_ADMIN_TOKEN`, `SSO_ADDR`") and §7:289 Credentials row ("`SSO_ADMIN_TOKEN` + `SSO_ADDR`") still name a nonexistent variable. Measured: `apiclient.go:27` `EnvAddr = "SSO_ADMIN_ADDR"`, `apiclient.go:30` `EnvToken = "SSO_ADMIN_TOKEN"`; no `SSO_ADDR` exists anywhere in the repo. Nor is any credential/env reference pinned by U4/U5/E1a — those rows assert scope names and exit codes only.
- **F2 not decided**: §7's Output row specifies routing only, not shape; R1.6:154 still uses the F2-flagged form (`sso-ctl clients: validate: scope "…"` — verb nested after the colon, at odds with the module idiom `progName: <verb> failed: …`), while FM-1 uses a *different* shape (`validate failed: <err>`). Two candidate shapes coexist, neither is selected in §7, and U4/U5/E1a pin only *which scopes are named*, not the line shape — so "pinned consistently" is unsatisfied under either choice.

## Ask 4 — "gate with `sso-ctl check`" guidance corrected: FAIL

All guidance survives, untouched: §3:99 ("operators must gate with `check` instead"), FM-5:327 ("gate with `config validate` + `sso-ctl check` T-8d"), FM-6:328 ("T-8d probes it live"), FM-7:329 ("covered by the T-8d probe at runtime"), §9:333 ("covered by `check` T-8d at deploy time"), and §10.3 ("alongside `config validate`"). Measured at HEAD:

- **`sso-ctl check` is unreachable from the binary.** `main.go`'s `subcommands` map has 16 entries — no `check`. `go test ./cmd/sso-ctl/ -run TestSubcommands -count=1` → `FAIL: TestSubcommands_CheckIsWired … subcommands["check"] is not registered — "sso-ctl check …" is unreachable`. (Pre-existing failure at HEAD, reported per AGENTS.md §2.)
- **`config validate` cannot cover admin-registry clients**: `validateScopeRegistry` (`config/config_oauth2.go:30`, invoked from `config_load.go:220`) checks `client.allowed_scopes` of config-declared clients only — a disjoint population from the admin-registry clients `clients validate` surfaces.
- **T-8d validates neither client scopes nor registry wiring**: it probes `sweep-probe-` + 12 random alphanumerics (`apiclient/check.go:57-58,300`) — a scope no allowlist contains, so its 400 is allowlist-or-registry ambiguous. The doc's claim that T-8d covers the provisioned/extra-scope false-verdict classes is therefore false.

## Bottom line

The underlying design (predicate, 0/1/2 contract, stderr-only offenders) is sound and was confirmed by all three reviewers; the failure is that **no revision incorporating F1–F5 and the boundary findings was ever produced**. The current text overclaims runtime agreement on the default deployment (§2, §10.3), documents one quadrant of the false-verdict boundary, pins the wrong env var, leaves the message shape undecided, and points operators at an unreachable command as the mitigation for exactly the classes it cannot detect. Minimal revision required to pass all four asks: (1) reframe §2/§10.3 as static conformance with the pre-enablement workflow, qualified to registry-enabled, built-in, no-extras, same-version; (2) split FM-5 into additions/removals, add enabled-off and version-skew rows, and either tag offender lines with the class or state plainly that output is class-indistinguishable and name the effective-registry admin endpoint as the resolution; (3) fix §3/§7 to `SSO_ADMIN_ADDR`/`SSO_ADMIN_TOKEN` and pin the chosen offender shape (module idiom: `validate failed: scope "…"`) in §7 with U4/U5/E1a asserting it; (4) delete every `sso-ctl check` gate reference, replacing them with the honest statement that provisioned-deployment admin-registry clients currently have no offline gate.
