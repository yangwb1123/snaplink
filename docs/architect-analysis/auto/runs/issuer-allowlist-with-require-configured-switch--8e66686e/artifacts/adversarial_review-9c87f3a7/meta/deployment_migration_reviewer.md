# Validation report: 5-step migration + A15a vs the three `issuer_allowlist` deployments

## Empirical baseline (ran against working tree HEAD `32596d23`)

All three configs were executed through the real loader (`go run ./cmd/sso-server --config=… --validate-only`):

- **`ops/deploy/kustomize/base/config.yaml`, `overlays/prod/config.yaml`, `k8s-distributed/config.yaml` all load exit-0 today with two `issuer_allowlist` warnings each**: (1) `schema violations … server.issuer_allowlist: unknown field` (`config/source.go` → `checkSchema`), (2) `unknown keys detected … unknown_keys=[issuer_allowlist]` (`decodeStrictWithFallback`, `config/source.go:264-278`). Both disappear once the field exists (schema is reflection-generated; strict decode then succeeds on the first pass — no lenient re-decode, same resulting `*Config`).
- **Caveat the design missed**: the configs also carry pre-existing warnings — `version field is unset` on all three, plus `hosted_login is deprecated` on k8s-distributed. A15a must assert absence of the *issuer_allowlist* warnings specifically, not "no warnings".
- **The allowlist rows are uncommitted worktree diffs** (`git diff HEAD` shows `+issuer_allowlist` in all three; kustomize base also changes `issuer: sso-server → cluster URL`). The design's C2 premise holds against the worktree, but A15a must use fixtures, not the live files, so it cannot depend on these in-flight diffs landing.

## The three questions

### 1. Byte-identical switch-off is testable — yes, with two structural notes

- Test hook exists: `TestLoader_UnknownKey_Warns` (`config/source_test.go:236-282`) already proves the slog-capture pattern (non-parallel, process-global `slog.SetDefault` swap). A15a slots in beside it: load a fixture mirroring the deploy `server:` blocks, assert no `issuer_allowlist` warning, `IssuerAllowlist` parsed, `ServerOptions()` = legacy + exactly one `WithIssuerAllowlist`.
- "Boots byte-identically" is only provable via the SDK-level identity tests (A13/A14 in `test/issuer_allowlist_test.go`) — no test today loads any of the 3 files, and **CI does not cover them**: `make config-validate(-all)` (Makefile:155, 400) validates a 7-file list that excludes all three, and suppresses stderr (`2>/dev/null`). So the option-count assertion (`config/security_test.go` pins 1/2/4 — verified) plus A13/A14 are the actual teeth; A15a alone proves load, not bytes.
- No schema golden files exist (`config/schema/` has no testdata); the field enters `Schema()` automatically.

### 2. Warn removal is observable — yes at test level and in boot logs, not in CI

Test-observable via the existing slog-capture pattern; operator-observable at boot. Not CI-observable (files absent from `config-validate-all`, stderr suppressed). If the design wants CI observability it must add the three files to the Makefile loop — worth stating explicitly since the design claims "warning disappears" without noting where that is (and is not) visible.

### 3. Panic-vs-503 divergence and shared normalization are safe for embedded users — with one logic hole closed and one gap

**The divergence is sound, verified by construction**: `sso.DefaultIssuer = "snaplink-sso"` (`shared/core/consts_oauth.go:139`) ≠ cmd default `"sso-server"` (`config_load.go:60`), and `validate()` rejects the sentinel (`config_load.go:183-184`). Therefore on the cmd path `s.issuer == DefaultIssuer` is impossible: strict + allowlist + missing issuer resolves to `"sso-server"` → case-3 panic; strict + mismatch → panic. No `recover()` exists in the cmd boot path (only store goroutines), so the panic crashes the process — loud crash-loop. An SDK embedder who omits `WithIssuer` keeps the sentinel → case-4 boot + 503s. Both legs fail closed; `NewServer` has no error return (`sso.go:58`), so panic is the only construction-time channel and has precedents (`options_grants.go:78`, `accessors_threat.go:242/256`). G2–G4 placements verified (no-store header precedes each gate: `server_token.go:15-17`, `server_login.go:16-18`, `server_mfa.go:193`; G1 before `base := requestBaseURL` and the body-cache lookup at `server_discovery_config.go:62-68`); `errorBody` is a plain envelope with no `resolveIssuer` call, so the 503s carry no `iss` and are oracle-uniform. Entry set `{handleLogin, handleMFAComplete}` confirmed: `wrapAuthorizationResponse` callers are `server_login.go:241`, `server_mfa.go:382`, `server_mfa_trust.go:181+230`.

**The normalization claim is a coordination commitment, not shared code — and the design's own arithmetic fails its gate (blocking):**

- **F1 — Budget rows are internally inconsistent.** Gate is `n > 500` fails (`maintainability_budget_test.go:34`; verified). `sso_wiring.go` 456 + ~45 = **501**, and `config/config_load.go` 498 + 8 = **506** — both cross the committed budget, and `interfaces/sso` is at exactly 60 production files (verified) so no new file is possible. Fix: fit ≤44 net lines in `sso_wiring.go` (tight option bodies; or move the pure `normalizeIssuer` to `shared/core`, which also turns "shared semantics" into literally shared code for the configcmd sibling — both `config` and `interfaces/sso` already import `shared/core`, and `configcmd`→`config`→`shared/core` is legal) and relocate the two conditional appends into a `Config` method in `config/config_server.go` (195 lines, room). `sso.go` 499+1 = 500 exactly passes.
- **F2 — A12 is internally inconsistent.** `WithIssuer` stores the raw value; normalization is comparison-only. `WithIssuer("https://sso.test/")` + allowlist `["https://sso.test"]` boots, but the stamped/discovery issuer is `"https://sso.test/"`, not `"https://sso.test"` as A12 asserts. Either canonicalize the stored issuer at boot in strict mode (a wire delta vs legacy — must be stated) or fix A12's expectation.
- **F3 — Direct contract conflict with the B4-1 sibling, unflagged.** The sibling spec R1/R3 and its design (`add-the-b4-1-…-26aebafe`) still say "never read at boot", "`ServerOptions()` unchanged", "server itself untouched" — contradicted by this design's conditional option emission. Both modules also list the same `config_server.go` field in their Files sections (duplicate-field/landing-order hazard), and the sibling gate is **not implemented** (`cmd/sso-ctl/configcmd/main.go` is 120 lines: `config.Load` only — verified; the in-flight `main_test.go` diff is B4-2 scope-registry, not the issuer gate). Migration step 2 ("run `sso-ctl config validate`") is therefore not executable today; it is a landing-order dependency, and today that command passes trivially with the same warn-and-ignore.
- **F4 — Entry-validity gap at boot.** `validateIssuerConfig` checks membership only; the "entries must be absolute http(s) URLs" contract is enforced only by the unimplemented offline sibling. Strict + `issuer_allowlist: [sso-server]` + unset issuer boots and serves non-URL issuer `"sso-server"` (it is ≠ sentinel, so `denyUnconfiguredIssuer` treats it as configured). Not a Host-derivation hole, but the option/config docs overpromise and "allowlisted by construction" becomes vacuous for garbage entries. Add entry validation to `validateIssuerConfig` (interacts with F1's budget pressure).
- Confirmed-safe: fail-closed normalization rule matches sibling acceptance 7/16 as specified (one trailing `/` trim, literal ports); compat constraint 4's prophylactic-vs-enforced divergence is intended and documented; the three deployments satisfy the future sibling gate (kustomize base: issuer origin == `base_url` origin; prod/k8s-distributed: no `base_url` → coherence skipped).

## Verdict

Migration steps 1/3/4/5 are sound; step 2 depends on the unimplemented sibling (F3). A15a and warn-removal are testable with the existing slog-capture pattern (F5 scoping caveat). The panic/503 divergence is safe for embedded users by construction. **Blocking before implementation**: F1 (budget arithmetic fails the committed gate in two files), F2 (A12 expectation), F3 (sibling contract conflict + landing-order), F4 (entry validation). All line counts in the design's §8 table match the measured worktree exactly; only the addition arithmetic for `sso_wiring.go` and `config/config_load.go` is wrong.
