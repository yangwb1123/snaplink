## 2. Negative cases

- **Reserved-key collision — the strongest test, and the only one that changes currently-observable behavior.** Verified: `buildAccessPayload` copies `subject.Claims` into `Extra` **unscrubbed** (`Extra: subject.Claims`, issue_payload.go:36). A `Claims: {"tenant_id": "evil", ...}` subject today emits `ext.tenant_id`/`ext.roles`. The scrub + top-level emission is a real behavioral change, so "token has no `ext.tenant_id`/`ext.roles` and the top-level claim equals the binding" is falsifiable and non-vacuous. It must also assert the round-trip: `claimsFromPayload` (validate_claims.go:16) and `tenantHintFromClaims` (interfaces/admin/governance.go:478, currently reads `claims.Extra[core.KeyTenantID]`) need the new structured `TokenClaims` fields, or the scrub test passes while the consumer still reads the legacy ext path. The design says "structured-claim precedence with pre-change ext fallback" — but no test for the precedence is named.
- **Allowlist rejection** — constructible (recover-based NewServer panic test; order-independence testable by both option orders). Not named. Note the construction validation can only see `s.issuer`; the actual minted `iss` lives in the token issuer's configured name (`defaultimpl.WithEd25519Issuer`), so the fail-closed mint gate (IssuerNamer) needs its own negative — a signer whose configured name is outside the allowlist must fail minting. That test is implied but not in the counts.
- **Sentinel issuer** — constructible: today `resolveIssuer` returns `requestBaseURL` when issuer is `""` or `DefaultIssuer` (server_discovery.go:251-258); after the change it returns the sentinel. A "never Host" assertion is falsifiable. cmd-side sentinel rejection already exists.

**Hazard the design flagged but under-plans:** `test/trusted_proxy_gate_test.go:265-311` is not "re-pointed" — two of the three tests (`UnsetKnobHonorsForwardedHost`, `TrustedPeerHonorsForwardedHost`) assert **the exact behavior being removed** (issuer derived from X-Forwarded-Host); their expectations invert, and `TestDiscovery_IssuerComesFromWithIssuer`'s meaning changes too since `buildBaseMetadata` seeds `Issuer: base` (server_discovery_config.go:144) with only the MFA-gated `applyMFAIssuerSigning` override (server_discovery_config.go:251-265). The summary's one-line "must be re-pointed" undersells a semantic rewrite of three wire tests.

## 3. Cross-repo testkit tenant-binding 422 gate: enforceable, with conditions

Sink-side pieces all verified present:
- Verifier reads **top-level** `tenant_id` (strict: charset/whitespace rules) and `roles` as a string array — `internal/auth/auth.go:132,178-196` — exactly the claim shapes T-8(a) emits.
- `Ingest` rejects non-empty envelope-tenant mismatch with `ErrTenantMismatch` (service.go:390-398); HTTP maps it to 422 (httpapi/server.go:1033-1035); gRPC aligned (grpcapi/server.go:200-201); unit test exists (service_test.go:170-190). The HTTP handler resolves tenant from `claims.TenantID` (server.go:234,278) — no query override on Ingest.
- The design's in-repo contribution is feasible: `test/testkit/testkit.go` seeds one client with **no TenantID/Roles** (`seedClient`); adding a tenant-binding option + a fixture assertion (mint via `/token` Basic auth or `h.Issuer`, decode, compare) is straightforward and falsifiable.

Gaps that gate **e2e** enforceability (all cross-repo, B1-7/B1-8 — the design is honest that these stay out of scope, but gives no cross-repo acceptance hook):
1. `scripts/mint-token.sh` does not exist.
2. `test/e2e/fullstack.sh` inserts outbox rows directly into Postgres — it never exercises the HTTP API with a bearer token, so no 422 can be observed at the wire level today.
3. `deploy/docker-compose.verify.yml:12` sets `AUDIT_ALLOW_DEV_AUTH: "true"` — T-1.2 requires it false with a real IdP token.
4. No HTTP-level 422 test exists in the sink (only the service-level one).

**Verdict:** The mapping is *constructible* — every implied test and negative case is feasible and falsifiable against the verified code, the reserved-key scrub test is genuinely non-vacuous (ext leakage is observable today), and the 422 gate is enforceable end-to-end once B1-7/B1-8 deliver the sink-side fixture, dev-auth-off, and wire-level assertion — but the deliverable as written is **under-specified**: no test is named, the second rootcov wire test is unidentified (counts drift 3+1 vs 3+2), the handler-level `Client.Roles → Subject.Roles` plumbing has no dedicated test in the counts, the trusted-proxy tests require semantic inversion rather than re-pointing, and the cross-repo gate has no stated assertion that B1-7/B1-8 actually landed. The acceptance mapping should be rejected as incomplete until tests are named with file targets, assertion predicates, and the sink-side dependency stated as an explicit gate condition.
