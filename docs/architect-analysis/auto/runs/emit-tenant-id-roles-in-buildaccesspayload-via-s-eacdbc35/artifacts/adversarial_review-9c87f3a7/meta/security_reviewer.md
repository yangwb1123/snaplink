# Adversarial review — R1/R2/R4 vs AGENTS.md security invariants

Verified against code, not the design's self-report. Evidence base: `infrastructure/defaultimpl/{issue_payload.go,ed25519_types.go,ed25519_issue.go,ecdsa_issue.go,rsa_issue.go}`, `shared/core/types_token.go`, `interfaces/sso/{server_discovery.go,server_discovery_config.go,server_login.go,server_native_sso.go,accessors_feature_gates.go,server_jar.go,server_token_clientauth.go,server_tenant_residency.go,options.go,handlers.go}`, `internal/handler/tokengrant/*` (all 8), `protocols/oauth/handle_register_helpers.go`, `domains/permissions/{types.go,provider.go,handlers.go}`, `interfaces/middleware/request_url.go`, `cmd/sso-server/issuer_test.go`, `config/config_load.go`, `docs/{error-codes.md,openapi.yaml}`.

## 1. Oracle safety

**1.1 `tenant_id` claim — SAFE, verified.** Every one of the 11 `Subject` construction sites sources `TenantID` from `client.TenantID` (operator-set client binding), never from request input; the break-glass site sets it explicitly `""` (accessors_feature_gates.go:260). The DCR path cannot self-assert it: under open registration the body `tenant_id` is dropped (`registrationTenant`, handle_register_helpers.go:147–156, "an anonymous registrant must not self-assign into another tenant"), and a 7592 PUT never changes it. `omitempty` + the T-8-style single-tenant omission test cover the empty case. No existing verifier consumes a `tenant_id` claim — the resource-server residency gate resolves tenant via `claims.ClientID → Client.TenantID` with "TokenClaims carries no tenant" documented (server_tenant_residency.go:319, 350) — so the claim is purely additive; it creates no new oracle and no behavioral change.

**1.2 `roles` claim — SAFE only with an amendment the design does not state.** The design says "fail-open roles outage" but never specifies the outage wire representation. The invariant that must be pinned: a provider outage must produce **byte-identical output to the `ErrUserNotFound`/no-roles case** (claim omitted), with the error logged — AGENTS.md's fail-open row requires *"fail open with audit/logging"*, and the in-tree precedent (`ResolveForLogin`, permissions/handlers.go:110–126) swallows errors, logs non-`ErrUserNotFound` ones, and returns empty slices. If outage emits `roles: []` while no-roles omits the claim (or vice versa), token *contents* become a permissions-store health oracle. The incremental exposure is small (`/roles/me` already reads the same provider), but the byte-identity of the no-roles case is an explicit acceptance, so the collapse must be stated and tested. Also required: `ErrUserNotFound` stays silent (normal case), all other errors logged — mirror `ResolveForLogin` exactly.

**1.3 `ErrIssuerNotConfigured` 503 — acceptable class, but three conditions are unspecified.** A 503 for "server has no configured issuer" is server-state disclosure, not a credential oracle (consistent with existing 503s: `service_degraded`, `hook_timeout`, `quota_projection_unavailable`), and fail-closed is the right class for issuer identification (mix-up prevention). But:

- **(a) Reachability.** With `WithRequireConfiguredIssuer` + boot-time panic, the 503 is dead code at runtime. With `WithIssuerAllowlist` alone it is reachable (unlisted Host-derived issuer). The design never says which. If reachable, it **must be confined to response-stamping surfaces**. The 13 validation/challenge callers of `resolveIssuer` must stay on the legacy resolver: `private_key_jwt` validation (server_token_clientauth.go:135,180 — AGENTS.md's oracle table pins these to `401 invalid_client`), JAR verification (server_jar.go:365 — `invalid_request`), bearer challenges (mesh_authz.go:179/217/253, server_me.go:43/49, server_userinfo.go:135/137 — `401 invalid_token`), and the resource-server `authServers` (server_resource.go:182). A 503 leaking through `/token` client auth would be a **new oracle on a table surface** (Host probing distinguishes "unlisted Host" from "bad client credentials").
- **(b) Mismatch vs unconfigured.** Request-`iss` mismatch must be `400 invalid_request` (RFC 9207 §4); only "server cannot establish its issuer" is 503. The design doesn't state the split. Note the server today performs **no inbound `iss` validation at all** — RFC 9207 is implemented response-side only (stamping in `authzErrorBody`/JARM/FCL). If R4 adds inbound validation, that is a scope expansion needing its own analysis; if not, "RFC 9207 surfaces" must be defined as the stamping set, which the design must enumerate (I count ~15: authzErrorBody/Desc/WithState, finish_login success+error+JARM×2, form_post, oauth authorize ×2, logout, MFA, native SSO, login-gate Realm, FCL iframes, origin_validation JARM ×2).
- **(c) 503 body shape + docs.** An unconfigured server cannot stamp `iss` in the 503 body — the design must forbid the Host-derived fallback from leaking into it (or the strict mode is defeated), keep no-store headers where credential-adjacent, and add the `Err*` to `docs/error-codes.md` (AGENTS.md §5.6 — the design mentions the error, no doc update). Same for the openapi surface if exposed.

## 2. Claim collision / spoofing — no collision path today; two pins required

Verified the top-level claim namespace is server-exclusive: all client-influenced data lands in `ext` (`Subject.Claims` → `Extra`), `_claims_` (`RequestedClaims`), `authorization_details`, `act`; token exchange propagates only `st.claims.Extra` (token_exchange_stages.go:392, token_exchange.go:294); `ProjectIDTokenClaims` and userinfo projection operate only on the `ext` string-map (idtoken_claims.go:17–31); `core.Client` has no free-form claim fields; `GuestRecord.Roles` narrows scopes, never claims (token_exchange.go:446). OIDC §5.5 claims-parameter projection cannot reach top-level claims. So `tenant_id`/`roles` cannot collide with or be spoofed through any existing client-controlled channel.

Pins the design must add: **(a)** `roles` sourced only from `permissions.Provider` keyed `(localSubject, clientID)` — never from client metadata (including any future one); **(b)** document snapshot semantics: a role revoked after issuance stays in the token until expiry (deny-side staleness) — security-relevant given the openapi.yaml:4807 sentence that a policy-bundle sidecar "has the caller's roles from the token." That sentence is the drift: today it is false (roles ride only in the login response, gated on `WithEmbedPermissionsInLogin`); after R2 it becomes true **but not via that option** — the parenthetical must be corrected in the same change or it stays wrong.

## 3. Fail-open vs fail-closed classification

- **`RolesForSubject` fail-open: CORRECT class.** AGENTS.md's fail-open list covers "refresh or ID-token issuance helpers"; `ResolveForLogin` is the exact in-tree precedent. Subject to 1.2 (audit leg + wire collapse). One addition: the lookup lands on the issuance hot path of every user-bound grant (refresh, device, exchange…). A slow provider stalls `/token` even though the error path is fail-open — the design should bound the lookup (context deadline/timeout or cache), and the fail-open tests must cover the outage variant (as the acceptance mapping claims).
- **`resolveIssuerStrict` fail-closed: CORRECT class** for stamping surfaces (issuer identification is a mix-up-prevention invariant; unverifiable → refuse; parallels "signatures/validation… fail closed" and "degraded key state is 503"). **WRONG class** if applied to the validation/challenge surfaces in 1.3(a). The design's failure to enumerate the switch-over set is what makes the classification unverifiable.

## 4. Mode-off byte-identical

- **R4 off-mode: TRUE, trivially** — strict ≡ legacy `resolveIssuer` when no option is set.
- **R1/R2 are not mode-gated.** Byte-identity holds only in the empty-data cases (`TenantID == ""` → omitted; no roles → omitted). That is exactly what the tests must pin: pre-change golden bytes vs post-change bytes for a no-roles single-tenant subject (both nil and empty-slice roles), plus the roles element shape (wire-equality test). R5's goldens are post-change snapshots and cannot prove pre-change identity — the acceptance must retain the empty-case pre-change comparison. Verified mechanics: `json.Marshal` emits declared fields in order and omits `omitempty` fields entirely regardless of declaration position, so existing key order and bytes are preserved in the empty cases; R3 is genuinely regression-only (`kid` already in all three headers, ed25519_issue.go:33, ecdsa_issue.go:37, rsa_issue.go:29 share `buildAccessPayload`).
- Caveat to state: even in the byte-identical empty cases, issuance gains the roles-lookup round trip (behavior/availability change, not wire change).

## 5. Factual defects in the design's own evidence

- **The call-site inventory is wrong: 11 `Subject` construction sites exist, not 10.** The design misses `accessors_feature_gates.go:257` — the **break-glass impersonation token**, which is user-bound (`ID: a.TargetUserID`). R1 survives (TenantID already explicitly `""` there → omitted; "zero call-site changes" property holds across all 11). R2's "9 user-bound sites" is therefore 10, and the design must make an explicit decision: sweep break-glass into `RolesForSubject` keyed under `BreakGlassImpersonationClientID`, or exclude it with documented rationale plus a test. Silent omission means the system's highest-privilege token class carries no roles once resource servers enforce the claim — a potential functional regression for break-glass flows (downstream deny) and an inconsistency.
- "28 `resolveIssuer` callers": confirmed (26 direct + 2 accessor indirections, accessors.go:375, accessors_handlers.go:324). ✔
- **E10 refutation: verified correct** — `DefaultIssuer` = `"snaplink-sso"` sentinel (consts_oauth.go:139), cmd default `"sso-server"` is a guarded non-sentinel (issuer_test.go), `config_load.go:305` wires `WithIssuer`, discovery honors the override (server_discovery_config.go:264), so token `iss` == discovery `issuer` == authz `iss` in the default tree. The re-framing of `require_configured` as opt-in hardening for SDK embedders/untrusted edges is right — and `requestBaseURL`'s `req.Host` fallback when forwarded headers are untrusted (request_url.go) confirms the Host-fallback `iss` is attacker-influenced at untrusted edges, so strict mode closes a real mix-up vector.

## Verdict

- **R1**: pass — property holds at all 11 sites (count corrected); no oracle, no collision, byte-identity in the empty case.
- **R2**: conditional — must add: outage wire-collapse to the no-roles form + audit/logging leg; explicit break-glass decision; per-site local-sub lookup key; roles provenance pin; openapi:4807 doc correction.
- **R4**: conditional — must add: enumerated stamping-surface set with explicit exclusions (private_key_jwt/JAR/bearer challenges/resource-server authServers), 400-vs-503 mismatch split, reachability statement for the 503, no-Host-leak 503 body, `docs/error-codes.md` (+openapi) updates.
- **Mode-off byte-identity**: the scoped claim is sound; tests must pin empty-case pre-change byte identity rather than only post-change goldens.
