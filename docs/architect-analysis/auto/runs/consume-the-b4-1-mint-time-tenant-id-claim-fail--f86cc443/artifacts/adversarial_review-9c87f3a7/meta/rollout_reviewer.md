**Q2 — Gate sequencing: process-only, not mechanical.** Blast radius if R2+R3 land pre-mint: whole bound-client machine plane 403s, quota+retention delivery pauses, `readyz` degrades at 5m MaxLag, IdP quotas go stale-not-wrong; zero data loss, recoverable by completing the roll or reverting. **Q3 — Pre-flight: a genuine gap.** "Register one relay client per tenant" (§4/§6 step 3) is **not expressible**: the relay holds exactly one credential pair (`SNAPLINK_BILLING_QUOTA_CLIENT_ID/SECRET` → one `OAuthTokenSource`), and the claim is the IdP client's single `tenant_id` (`token_client_credentials.go:52`, `config_client.go:24`). Step 3 must branch: single-tenant-per-deployment (zero new surface, matches the e2e fixture) or a follow-up direction for a per-tenant credential surface (conflicts with "no new config keys" + env-only secrets discipline). Detection: `SELECT COUNT(DISTINCT tenant_id) FROM tenant_commerce_quota_outbox` vs the client's `clients[].tenant_id` and the SIGHUP-reloadable `projection_ingress.sources[]`. Verification: per-client mint check (T-8(a) shape), delivery check, zero `reasonAuthorization` after the F5 window.

**Q4 — Monitoring.** The no-oracle pin makes HTTP drift denials unobservable as a class — the honest signals are the durable outbox `last_error = 'quota projection authorization rejected'`, the fixed worker log lines, and readyz. Concrete rules: admin fail-open → WARN on log rate > 0/5m, PAGE at 15m sustained; `reasonAuthorization` → WARN on fresh rows, PAGE when the oldest row exceeds `TTL + skew + maxBackoff + margin` (≈70–75m with defaults) — that duration rule is the F5-vs-F2/F3 discriminator, since F5 self-heals at cache refresh by construction. No new metrics by default; optional bounded counters mirroring the renewal pattern are documented as a fallback.

**Q5 — Rollback: safe under the one-commit packaging, with four rules.** R1 is additive and unaffected; the e2e fixture and R5 docs must stay inside the R2/R3 commit (the fixture hazard is one-directional and self-correcting). The hard hazards are operational: (1) never delete the shared relay client's credentials during migration — an *unbound* shared client is perfectly functional post-revert because the IdP handler never reads the claim; (2) in any combined IdP rollback, billing reverts first (gate-without-mint is the unbounded F1); (3) operational rollback = redeploy previous artifact, tree revert can follow; (4) backlog converges from persisted retry schedules, no replay.
