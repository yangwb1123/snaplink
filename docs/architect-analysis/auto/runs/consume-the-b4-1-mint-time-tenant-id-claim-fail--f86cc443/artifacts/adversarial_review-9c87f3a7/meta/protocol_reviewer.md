# Verification: §4 "No wire/API surface change" claim

**Verdict: the no-wire-change claim HOLDS for the rs embedding — but two of the design's own statements need correction, and one latent parity gap must be acknowledged. Details below.**

## (1) `wireClaims` → `wireIntrospection` embedding: no emitted bytes change — decode-only

- `wireClaims` (`interfaces/ssoclient/rs/claims.go:93-108`) and `wireIntrospection` (`introspect.go:76-81`) are **unexported, decode-only structs**. The only writes into them are `json.Unmarshal(body, &w)` + `w.raw` (second Unmarshal) in `introspectCall` (introspect.go:107-116). A repo-wide grep finds **zero** `json.Marshal` of either struct — the only "wireIntrospection" hits elsewhere are unrelated `cmd/sso-server/build_app_oidc.go` builder functions (`wireIntrospection()`/`wireIntrospectionSigning()` = RFC 9701 signer wiring) and a comment in `options_grants.go:262`.
- The rs package never re-emits claims: `HTTPMiddleware` passes claims via context (`NewContext`/`ClaimsFromContext`, middleware.go:33-46) only; `writeChallenge` emits fixed error bodies/headers.
- **Billing has no introspection endpoint** (zero "Introspect" references in `cmd/snaplink-billing/`). All rs consumers — billing (`rs.Config{Issuer, JWKSCache, ExpectedAud}`, app.go:220-222 → JWT mode), `interfaces/commerce/payment_ingest.go`, `interfaces/metering/auth.go` — read `rs.ClaimsFromContext` from the JWT-validating middleware. **No production caller of `ValidateTokenWithIntrospect` exists outside the rs package itself.** Billing's only `json.Marshal` calls are the retention-policy record (relay.go:170,200) and the projection request body (`http_client.go:96-100`, which already carries `tenant_id` today) — neither serializes claims.
- The introspection **response** bytes are produced entirely server-side (`protocols/oauth/handle_introspect.go` → `map[string]any` body, optional RFC 9701 JWT over that map) and are untouched by R1. The decode struct cannot influence them.

So embedding `wireClaims` cannot expose `tenant_id`/`roles` to any consumer through R1 — the §4 claim holds. (Side note: JWT-mode consumers can already read both claims today via `Claims.Raw`, which is the full decoded payload; R1 merely adds typed projection.)

**Correction required (design §3.1):** "`wireIntrospection` embeds `wireClaims`, so the introspection path projects both claims with **zero extra code**" overstates data availability. The SnapLink AS introspection handler echoes `serving_region` (`populateIntrospectionServingRegion`, `introspect_body.go:52-58`) but **not** `tenant_id`/`roles` — `populateAccessIntrospectionBody` (introspect_body.go:65-99) has no such echo, and `core.TokenClaims` (`shared/core/types_token.go:39`) has **no TenantID/Roles fields**, so the handler structurally cannot echo them without an IdP-side change (TokenClaims + introspect_body + OpenAPI) that the design explicitly excludes ("no mint-side changes"). The R1 doc comments must not say "echoed by introspection" (the design's proposed wording for the serving_region-style comment); they should state this is decode-side projection and the current AS introspection response does not carry these claims.

## (2) RFC 9068 semantics

- **Naming**: `tenant_id` (string) and `roles` (array) are top-level claims with `,omitempty` (`ed25519_types.go:54-64`). Both are **SnapLink extension claims**, not RFC 9068-defined — the mint comments say so explicitly ("SnapLink extension; RFC 9068 has no tenant claim"). RFC 9068 §2.2 defines iss/sub/aud/exp/nbf/iat/jti/client_id/scope (+ optional auth_time/acr/amr/sid); neither `tenant_id` nor `roles` is in it. The design's §3.1 wording "the RFC 9068 mint-time binding claims" is a mislabel — should be "SnapLink extension claims carried in the RFC 9068 access-token profile" (same class as `serving_region`). Cosmetic, but the doc comments are part of R5.
- **Shapes**: `tenant_id` string both directions; `roles` `[]string` → JSON array on both mint and decode. A third-party AS emitting `roles` as a single string would fail `json.Unmarshal` → `ErrTokenMalformed` → reject (fail-closed). Introspection shape: N/A (AS never emits them).
- **no-omitempty on decode**: correct and harmless — decode treats absence as zero. No re-encode path exists for these structs anywhere (see (1)); the RFC 9701 signed-introspection path signs the server-side map, untouched. The concern cannot bite.
- **`claimsWithoutEmittedKeys`**: verified at `issue_payload.go:104-131` — when `subject.TenantID != ""` and/or `len(subject.Roles) > 0`, same-named `ext` keys are stripped so the mint-time literal wins; single-tenant hot path returns the original map identity (zero alloc). "Mint-time literal wins" confirmed.

## (3) JWT/introspection parity + HasTenantID presence == non-empty

- **All ten access-token mint paths stamp `TenantID: client.TenantID` unconditionally**: client_credentials (`token_client_credentials.go:52`), authcode (`token_authcode.go:136`), refresh rotation (`token_refresh.go:292`, `refreshRotatedSubject`), token exchange (`token_exchange_stages.go:399`, `tokExSubject` — the **exchanging** client's binding, matching the design's "IdP-side client binding" semantics), device (`:99`), CIBA (`:124`), jwt_bearer (`:112`), saml2_bearer (`:123`), direct-mint login (`server_login.go:113`, plus `Roles` via `mintRoles`), native SSO (`server_native_sso.go:190`). The hook pipeline wrapper (`accessors_threat.go:367-386`, `cloneHookSubject`) shallow-copies the Subject, preserving TenantID; hooks can only merge `ext` claims.
- The one deliberate exception — break-glass impersonation (`accessors_feature_gates.go:257`, `TenantID: ""`) — is a distinct client ID never bound in billing; if it ever were, the gate fails closed.
- Since the stamp is unconditional and omission is `omitempty`, **claim present ⟺ `client.TenantID != ""`** on every path, so `HasTenantID()` == claim presence. ✓
- **Empty/whitespace**: billing-side binding tenants are validated non-empty and whitespace-free by `ValidateQuotaTenantID` at binding load (`quotabinding/registry.go:37`). IdP-side, DCR honors the operator-vouched `tenant_id` verbatim under InitialAccessToken-gated registration and drops it under open registration (`registrationTenant`, `handle_register_helpers.go:150-158`); no whitespace trim was found on the IdP client field. A whitespace IdP binding would mint `tenant_id: "  "` → `HasTenantID()` true but equality fails → **fail-closed denial (availability only, never a bypass)**. The design's rationale "non-empty by construction (binding identity validation)" is exact for the billing-side binding only; the IdP client field is the loose end — worth one sentence in the design.
- **Parity gap (the one real finding)**: JWT path populated; introspection path always empty for SnapLink-minted tokens (see (1)). Latent today — no production introspection consumer, and the R2/R3 gates all sit on JWT-mode consumers — but the A2 test's "introspection decode with tenant_id/roles" case exercises a shape the AS never emits, and any future introspection-mode consumer applying these gates would deny everything (fail-closed, not a hole, but not parity). The design should state this explicitly rather than claiming "zero extra code" symmetry with `serving_region`, whose AS echo **does** exist.

## (4) `OAuthTokenSource` cache staleness claim — accurate against the code

- **Per-client**: billing builds exactly one source per configured relay client (`buildQuotaTokenSource`, quota_relay.go:433-445 → `NewOAuthTokenSource` with `config.Quota.ClientID`); single token slot, singleflight key `"client"` (`oauth_token_source.go:107-127`). ✓
- **TTL**: `cacheToken` (oauth_token_source.go:213-224) sets `refreshAt = now + min(expires_in, 24h) − min(refreshSkew=30s, lifetime/2)`. `expires_in` = `effectiveAccessTTL` = issuer default `defaultTokenTTL` (1h) or `Client.AccessTokenTTL`. So **"default TTL 1h" is the default, not the bound** — the stale window is `min(expires_in, 24h) − skew`, per-client configurable up to the 24h cap. Minor precision note for §4/F5 wording.
- **Re-bind behavior**: RFC 7592 PUT never changes a client's tenant (`handle_register_helpers.go:150-151`); a re-bind happens via store/admin, and client changes only evict caches (`InvalidateClientCache` → `KindClientChange`, handle_register.go:220) — **outstanding tokens are not revoked**. So after a re-bind the relay's cached token remains signature-valid and carries the OLD `tenant_id` until `refreshAt`; the cross-check rejects → `ErrAuthorizationRejected` → `reasonAuthorization` bounded backoff with the event retained (`classifyPublishError`, relay.go:237-240) → refetch at `refreshAt` mints the new binding's claim → delivery resumes. F5's "≤ TTL" recovery is accurate. Also confirmed: `AccessToken` already enforces per-tenant `source_system` consistency (`TenantSourceID(prefix, tenantID)` vs `binding.SourceSystem`, oauth_token_source.go:105-109), so the per-tenant relay-client migration is mechanically supported.
- The stale comment at `oauth_token_source.go:44-46` is exactly as the design describes and is correctly scoped to a comment-only correction.

## Bottom line

§4's "no wire/API surface change" **holds**: the embedding is decode-only with no re-encode path, billing has no introspection endpoint, and introspection response bytes are produced server-side from an untouched `map[string]any`. Three things to fix in the design before implementation: (a) the R1 doc comments and §3.1 wording must not claim introspection echo or "RFC 9068 claims" — it's decode-side projection of SnapLink extension claims, not echoed by the current AS; (b) the JWT/introspection data-parity gap should be stated as a limitation (A2's introspection case is capability-only); (c) note that an IdP-side whitespace tenant binding fails closed by equality (availability), since "non-empty by construction" is enforced only on the billing side. None of these change the wire claim itself.
