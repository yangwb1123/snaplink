Review written to `docs/architect-analysis/auto/runs/make-iss-a-configurable-allowlist-and-stop-host--d9077730/artifacts/adversarial_review-9c87f3a7/meta/issuer_gate_coverage_reviewer.md`. No production code touched. Verdicts per ask:

**1. Independent enumeration — 12 authorization-response sites, not 8.** I walked every `resolveIssuer`/`ResolveIssuer` consumer (27 in `interfaces/sso` + ~20 in `protocols/`/`domains/` via `Deps`). Family A (RFC 9207 `iss` stamping) = 12 emission points: error envelopes (`authzErrorBody`, `server_discovery.go:268`), providers/home-realm (`server_oauth.go:468/481`), silent renewal (`handle_silent_renewal.go:369`), consent challenge (`server_logout.go:259`), MFA challenge (`server_mfa.go:139`), direct-mint/code-JSON/form_post/JARM-success/JARM-error (`server_finish_login.go` + `origin_validation.go`), MFA-complete errors, native-SSO token exchange (`server_native_sso.go:225`). All 12 funnel through `handleLogin`/`handleMFAComplete`/`handleToken`, so **G2+G3+G4 coverage holds** — but the "8 sites" figure is absent from the deliverable and any reconstruction misses A1/A2/A3/A4/A12.

**2. "No remaining Host-derived leakage" is refuted.** Ungated in the same strict state: `/introspect` (signed-response `iss` + challenge), `/revoke`, `/par`, `/register`, CIBA, `/userinfo`, `/sessions/me`, mesh ext-authz, step-up `realm`, RFC 9728 metadata, SSF config, federation entity config (which embeds `buildOIDCConfiguration`'s Host-derived issuer), login-ui metadata, `/branding` (unauthenticated), FCL iframe `iss`, and the exported `ResolveIssuer` SDK seam — ~29 consumers total. Fix: remove the fallback inside `resolveIssuer` under strict mode (one choke point) or scope the claim.

**3. Fail-mode classification.** Boot panic (strict) and runtime 503 are correct fail-closed choices for the gated surfaces (panic is the only option given `NewServer`'s no-error signature; cmd path has a better precedent at `config_load.go:184`). But the same state behaves fail-open on ~29 ungated surfaces — issuer validation is not uniformly fail-closed. Two factual slips: the gate predicate is never pinned, and the design conflates two sentinels (`sso-server` cmd default vs `snaplink-sso` SDK sentinel at `core/consts_oauth.go:139`).

**4. Credential 503s.** No-store holds structurally (all three handlers stamp `tokenNoStoreHeaders` before any gate). Oracle-safe: uniform 503 before client auth/binding. Residual: gated endpoints 503 while ungated ones serve Host-issuer → config-state fingerprint; `ErrIssuerNotConfigured` needs `docs/error-codes.md` (AGENTS.md §5.6).

**5. Normalization audit.** Key rule: **normalize for membership only, never the stamped value** — `iss` is stamped raw in four independent places; normalizing in `resolveIssuer` alone would break RFC 9207 §2 byte-equality with discovery. Scheme: https-only + the existing `oauth.IsSecureRedirectURI` loopback set. **Ops break found**: `ops/deploy/kustomize/base/config.yaml:12` allowlists `http://sso-server.snaplink-sso.svc.cluster.local:8080` — http non-loopback → panics under strict (the sibling wire review wrongly called this "zero behavior change"). Reject query/fragment/userinfo; pin IDN (reject non-ASCII) and default-port rules. Residual gap: `core.TokenIssuer` has no `Issuer()` accessor, so minted-token `iss` can't be boot-checked against the allowlist.
