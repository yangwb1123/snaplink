# Feature Spec: Security Documentation Consolidation

> Generated by: Architect Agent | For: Implement Agent | Verified by: Reviewer Agent

## 1. Goal

将项目中两份并存且内容不一致的安全策略文档——`.github/SECURITY.md`（GitHub 对外暴露的仓库安全策略）与 `docs/SECURITY.md`（项目文档空间中的安全参考）——合并为单一的、无歧义的权威版本，消除 SLA 声明冲突、内容遗漏和重复维护问题。同时将 `docs/SECURITY.md` 中特有的**安全架构参考表**（Hardened Areas、Fail-Open/Closed 决策矩阵）和**开发者安全检查清单**保留并增强，使其成为项目安全架构的活文档，而非与 `.github/` 版竞争的另一份策略说明。

## 5. 架构分析与设计决策

### 5.1 现状诊断：文档架构债务

当前状态存在三类问题：

| 问题 | 严重度 | 影响 |
|---|---|---|
| **SLA 冲突**：`.github/` 说"3 个工作日确认"而 `docs/` 说"24 小时" | **高** | 安全研究员无所适从；若按更紧的承诺来期望却没有兑现，损害项目信誉 |
| **内容碎片**：`.github/` 有 Operator 加固清单和 Scope 定义，`docs/` 有安全架构表和开发者清单 | **中** | 读者需要交叉阅读才能获得完整图景；容易遗漏关键信息 |
| **无同步机制**：两份文件独立维护，没有 git hook / CI 检查防止 drift | **中** | 差异会随时间累积，最终完全失同步 |

### 5.2 关键设计决策

#### 决策 1：双文件架构 vs 单文件架构

| 选项 | 描述 | 权衡 |
|---|---|---|
| **A：单文件权威（推荐）** | `.github/SECURITY.md` 作为唯一对外策略，`docs/SECURITY.md` 简化为"安全架构参考"，不重复策略细节，通过顶部注释 `> 安全策略见 .github/SECURITY.md` 建立关联 | ✅ 消除 drift；✅ GitHub 自动发现策略位置；⚠️ 读者需要访问两个位置 |
| **B：双文件 + CI 同步检查** | 保留两份文件但内容强制一致；新增 CI 步骤（`scripts/check-security-docs-sync.sh`）逐段比较 | ✅ 保留各自受众的便利；❌ 维护成本高；❌ CI 检查脆弱（段落实质相同但措辞微调就误报） |
| **C：git submodule / symlink** | `docs/SECURITY.md` → `../.github/SECURITY.md` | ❌ 跨目录符号链接在 CI/IDE 中行为不一致；❌ GitHub Web UI 不跟随 |

**推荐 A**：将 `.github/SECURITY.md` 作为策略的单一权威声明，`docs/SECURITY.md` 独立为技术架构参考文档，两者仅相互引用，不重复相同信息。

#### 决策 2：SLA 选择

| SLA 元素 | 推荐值 | 理由 |
|---|---|---|
| 确认时限 | **3 个工作日** | 匹配 GitHub Security Advisories 的工作流；24 小时对于 OSS 项目过于激进，且无专职安全团队 |
| 分类评估时限 | **7 个工作日**（从确认起算） | 与 `.github/` 现有值一致 |
| 修复时限（高危） | **30 天** | 与 `docs/` 现有值一致；`.github/` 也写 30 天 |
| 公开披露 | **协调披露，默认报告后 90 天或修复发布之日（先到者）** | 行业标准做法 |

**结论**：采用 `.github/SECURITY.md` 的时限，因为更保守更可承诺。`docs/SECURITY.md` 中"24 小时"的表述应替换为引用 `.github/SECURITY.md` 的策略声明。

#### 决策 3：PGP 密钥引用

`docs/SECURITY.md` 引用了 `https://snaplink.dev/.well-known/pgp-key.txt`。这是一个好的实践，但：
- 该路径需要在 `interfaces/sso/` 中新增一个实际提供 `.well-known/pgp-key.txt` 的 HTTP 端点（或者在反向代理层静态托管）
- 在策略文档中承诺 PGP 密钥前，必须确认该端点**确实在提供服务**

**建议**：将 PGP 密钥引用移至 `.github/SECURITY.md` 的 Email 备选方案中，并添加说明"PGP 密钥在第三方审计前为可选推荐；一旦部署密钥，24 小时内确认 SLA 将激活。"

### 5.3 安全架构文档的增强方向

`docs/SECURITY.md` 中的安全架构表是目前最有价值的资产。建议将其扩展为项目安全架构的活文档，并新增以下内容：

#### 新增章节建议

```
docs/SECURITY.md 扩展结构（合并后）:
├── 1. 安全策略（引用 .github/SECURITY.md）
├── 2. 安全架构概览
│   ├── 2.1 威胁模型（简要）
│   ├── 2.2 信任边界图
│   └── 2.3 安全域划分
├── 3. 已强化领域（现有表格增强版）
│   └── 每项增加：相关包路径、对应测试文件
├── 4. Fail-Open/Closed 决策矩阵（现有，增强）
│   └── 每项增加：决策背后的具体论证链接（ADR）
├── 5. 开发者安全检查清单（现有，增强）
│   └── 每项标记 [auto] / [manual] + 对应命令
├── 6. Operator 部署安全清单（从 .github/ 迁移）
│   └── 增加：默认值、检查命令、常见错误配置
├── 7. 依赖供应链安全
│   ├── 依赖扫描策略
│   └── SBOM 生成
└── 8. 安全评审流程
    ├── 代码审查中的安全关注点
    └── 安全变更的 PR 标签规范
```

### 5.4 与项目架构的关系

安全文档的架构应当反映代码的物理架构：

```
项目代码架构                     安全文档映射
┌──────────────────┐           ┌──────────────────────┐
│ interfaces/sso   │◄─HTTP───►│ 威胁模型：攻击面      │
│   └─ handlers.go │           │ └─ 端点保护清单       │
├──────────────────┤           ├──────────────────────┤
│ protocols/oauth  │◄─逻辑───►│ 协议安全（Oracle-leak）│
│ protocols/oidc   │           │ └─ 各协议加固表       │
├──────────────────┤           ├──────────────────────┤
│ security/*       │◄─能力───►│ 安全原语（JWT/JWE/DPoP）│
├──────────────────┤           ├──────────────────────┤
│ defaultimpl/*    │◄─实现───►│ 存储安全（SQLite/记忆）│
├──────────────────┤           ├──────────────────────┤
│ infrastructure/* │◄─集成───►│ 运维安全（KMS/Redis） │
└──────────────────┘           └──────────────────────┘
```

> 每项安全机制在文档中应标注其代码位置（包路径 + 关键文件），降低从策略到实现的跳转成本。
